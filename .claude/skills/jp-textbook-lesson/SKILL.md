# 教材课文精听/默写练习页生成

给一套教材课文材料（截图 + 音频，按"会话/课文/生词"分文件夹），生成一个密码保护、
不进导航的练习页：三个 tab（会话/课文/生词），假名注音 + 中文翻译 + 语法笔记，
播放时逐词跟读高亮，支持默写/填空练习模式，右下角悬浮迷你播放器。

这个 skill 复用 `jp-listening-page`/`jp-meeting-listening-page` 的全部工具链和页面
基建（`transcribe.py`/`refine_boundaries.py`/`validate_boundaries.py`/`build_page.py`/
`listening-page.css`/`listening-page.js`/`private-gate.js`/默写填空练习模式），**跟
它们的核心区别**：

- 那两个 skill 处理的是**录音本身就是唯一信源**，日语原文靠 Whisper 转写再人工/
  Agent 校对得到，有"转写不可靠、需要核对/筛选"的问题。
- 这个 skill 处理的是**教材**——日语原文已经印在书上、截图里，是 100% 准确的
  ground truth，不需要"校对 Whisper 转写"这一步，Whisper 只用来给已知文本配
  时间戳（打时间戳草稿 + `refine_boundaries.py` 精修边界）。这让流程明显变简单：
  没有"两轮 Agent 产出标准答案"，也没有"筛选可信句子"。
- 教材音频通常拆成**多个独立文件**（会话/课文/生词各一段），不是一份连续录音，
  页面却要合成一个（tab 切换、悬浮播放器统一控制）。见下面"多段音频怎么合成一个
  页面"。
- 这个 skill 生成页面时固定传 `build_page.py` 的 `--data-driven`（另外两个 skill
  不传，保持原来"内容直接烘焙进 HTML"的行为不变）——教材内容比听力转写更容易
  事后订正（改翻译措辞、调整语法笔记、订正读音这类小改动很常见），`--data-
  driven` 把内容单独存成同目录下人类可读的 `data.js`，改内容不用碰 HTML、也
  不用重新走一遍生成流程，配套的渲染逻辑在共享文件 `docs/js/page-renderer.js`
  里（`listening-page.js`/`listening-page.css` 之外新增的第三个共享文件）。

- `docs/private/textbook-sjp-zg-l11/` — 《标准日本语》中级第11课（若者の意識、
  漫画とアニメ，会话/课文/生词三个tab，144个生词）。踩的坑集中在"生词边界
  收紧"（章节标题也有发音不能默认跳过、大量生词条目开头/结尾带静音或连着
  下一个词、单词测试 tab 引用的音频 id 跟真实生词 id 对不上）这几类，
  都记在下面"常见坑"一节里。
- `docs/private/textbook-sjp-zg-l12/` — 《标准日本语》中级第12课（方言と共通語，
  会话/课文/生词三个tab，90个生词）。这一课踩的坑主要集中在"生成完页面之后
  的边界修复"这个环节——用户实际听页面反馈了好几轮问题，牵出了"手工改边界
  忘记同步 `char_times`""两句都被切短、中间死区""同音字密集段落对齐失败"
  这几类新坑，以及新增的 `trim_clip_silence.py`（生词音频静音裁剪工具）。
  后续又发现了假名注音分段不准（多段汉字词、々符号、片假名混合词、语法
  笔记占位符〜）和跟读高亮粒度太粗（一个 pykakasi 分词只有一个时间戳）
  两类问题，牵出 `_split_kana_segments()`/`tokenize_ja()` 的算法改进——
  这两类都记在下面"常见坑"一节里。
- `docs/private/textbook-sjp-zg-l13/` — 《标准日本语》中级第13课（スピーチの
  依頼、日本の人口が減っている——少子化，会话/课文/生词/単語テスト四个tab，
  89个生词条目，含6条无词性标签的补充搭配）。这一课踩的新坑：①
  `transcribe.py` 并行跑多段时会在同一个 `chunks_tmp` 临时目录上冲突（work
  目录只看输出 json 的路径，同一课的会话/课文/生词三段如果输出都在同一个
  `work/<slug>/` 下，会共用同一个 `chunks_tmp`，并行跑会互相删对方正在用的
  chunk 文件而崩溃）——必须串行跑，不能像分析阶段那样图省时间开多个
  `run_in_background`。② 生词表如果语速较快、词间停顿短于 `cluster_tokens.py`
  默认的 `gap_thresh`（0.2秒），会把好几个词错误合并成一个 cluster（真实案例：
  89个词只合出13个cluster），这种情况下"生词边界收紧"不能走"以粗位置为中心
  搜索窗口"这条路，改成直接把连续 word-level 转写的**原始**（未 cluster）
  token 喂给 `align_group()`，一次性对整份生词表做字符级 diff 对齐，比逐词
  开窗口搜索更稳。③ `build_page.py` 的 `cut_segments()` 现在会探测已有文件的
  实际时长跟 `enriched.json` 里的期望时长（`end-start`）对不上才重切——这意味着
  **`trim_clip_silence.py` 裁剪过的文件，只要之后为了改别的句子边界重新跑一遍
  `build_page.py`，会因为"实际时长（裁剪后）≠期望时长（未裁剪）"被判定为
  "对不上"而被整个目录批量重切，静默撤销掉全部裁剪结果**（真实案例：修
  5个生词的边界后重新跑 `build_page.py`，误以为只会重切这5个文件，实际
  89个生词文件全被打回未裁剪状态）。正确顺序：所有边界类修复都做完、
  确认不再需要整体重新跑 `build_page.py` 之后，`trim_clip_silence.py` 才作为
  最后一步跑；如果生成完页面后又发现个别句子边界要改，用共享工具
  `tools/listening/recut_clips.py <combined音频> enriched_combined.json
  docs/private/<slug> <id...>` 只重切这几个 `id` 对应的文件（不经过
  `cut_segments()`/`build_page.py`），不要为了改一两句边界重新跑一遍整个
  `build_page.py`；音频切完别忘了配套跑 `patch_sentence_tokens.py`（见下面
  l14 案例）同步 `data.js` 里的跟读高亮时间戳，两者是分开的两步，缺一不可。
- `docs/private/textbook-sjp-zg-l14/` — 《标准日本语》中级第14课（恩師、日本の
  就職活動，会话/课文/生词/単語テスト四个tab，88个生词条目）。**这一课的源
  材料app截图第一次自带了逐句中文翻译**（会话/课文每句日语下面直接印着对应
  的中文，用户提前提醒了"会话和课文都有中文翻译了哟"）——跟前面几课"教材
  没有逐句翻译，`zh` 字段自己翻"不同，这一课直接抄录截图里的官方翻译，不用
  自己现译，翻译质量和用词也更贴合教材原文（比如"面接は話す場であり"官方
  译"面试是发表意见的场所"，比直译"面试是说话的场所"更准确）。**这不是这个
  skill 的默认假设，遇到新一课时要先看一遍截图有没有中文翻译再决定要不要
  自己翻译，不能想当然认为教材都没有翻译**。这一课的生词表语速依然较快，
  沿用 l13 那套"整段word-level转写+一次性`align_group()`对齐全部生词"的
  方案（这次88个词一次成功，0对齐失败），没有引入新坑。furigana全量复核
  新发现3处此前完全没覆盖过的读音坑，写法上都是"孤立单字默认读音 vs 紧跟在
  特定前置词/数字后面的不规则读音"这个反复出现的模式的新实例，不是新的坑
  类型：
  - **"の日"（"〜的那天"，比如"休みの日""雨の日"）该读ひ**，pykakasi 默认
    给孤立"日"字读にち。已有 `("その","日")→"ひ"` 这条固定搭配，但"の日"是
    更通用的同一条规律（前面究竟是"その"还是别的词不重要，只要紧跟在
    "の"后面单独成词就该读ひ），直接按 `prev_orig=="の"` 判断，一次覆盖，
    不用像"その日"那样局限于固定搭配。
  - **"〜を後にする"（推迟，往后放，这一课的生词条目之一）这个惯用语里的
    "後"该读あと**，pykakasi 默认给孤立"後に"读のちに（"後に"单独作副词
    "之后"时确实两种读音都存在，跟"その後"是同一类真歧义——但"後にして/
    にした/にします"这个固定惯用语只有あとに这一种读法）。用 `next_char`
    是不是"し"（"して/した/します"这几个后续活用形的共同起始假名）判断是
    不是这个惯用语，不影响"後に，"这类真正表示"之后"的独立副词用法——**这
    条规则暴露了 `audit_furigana.py` 自己的一个盲区：`_scan_live_text()`
    调用 `_resolve_hira()` 时没有传 `next_char`（一直默认 `None`），导致
    这类"要看下一个字符才能判断"的订正规则，在这个审核脚本里显示成"没
    生效"（误导人工复核，让人以为改的规则没起作用），但页面真正生成时
    （`build_page.py` 自己的 `tokenize_ja()` 正确传了 `next_char`）其实是
    生效的——单靠审核脚本的显示结果验证订正规则会被这类参数漏传坑到，
    真正要验证订正规则生不生效，得直接调用 `tokenize_ja()` 现场测一下**，
    已经把 `next_char` 计算逻辑同步补进 `_scan_live_text()`，以后这类规则
    在审核脚本里也能正确显示。
  - **"1次/2次/3次"这类"数字+次"表示"第N次/第N轮"时该读じ**（一次試験＝
    いちじしけん），孤立的"次"字 pykakasi 默认给つぎ（"次の駅"这种表示
    "下一个"的独立名词用法确实读つぎ，但那时前面不会紧跟数字）——跟
    "人/位/間/歳"是同一类坑，用 `prev_ends_with_digit` 判断，一次覆盖。
  三处都已经补进 `_resolve_hira()`，`後`/`次` 两个字也补进了
  `DANGER_KANJI`（`月日方上下中分時気家物目手口力名音色間位歳君` 之外新增）。
  **这一课发布之后用户实测又反馈了两轮问题，牵出这个 skill 目前为止最大的
  两条经验教训**，按时间顺序记录：
  1. 用户反馈"会话第1节第1句/第2节第2句/第2节第6句结尾音长了，把下一句的
     开头弄进来了""第2节第1句开头音短了"——4处真实边界bug，用RMS能量剖面
     核实真实起音位置后直接ffmpeg重切（第一轮修复，见下面第2条之前）。
  2. **紧接着用户又反馈"会话和课文，没有严格按照句子来分哟，很多都是几句
     刚在一起的"**——这一课（以及之前每一课）第1步"读截图抄原文"时，习惯性
     地按截图/口语一整个"说话轮次"或者一整段抄成一张卡片（比如"ありがとう
     ございます。では，お邪魔します。"两句合一张、"それはよかった。そうそう，
     大学の時の友達からは，今でも連絡があるかい。"两句合一张），**没有意识到
     这个 skill 从来没有明确写过"卡片必须严格按语法句（每个"。"/"？"）切分"
     这条规则，一直凭直觉按"一轮对话/一个自然段落"分卡片**。用户点出来之后
     回头看，这一课17句会话里有9张卡片其实装了2~4个语法句，10句课文里有5张
     卡片装了2~4句——不是个别情况，是这一课多数卡片都存在这个问题。**这不
     只是"卡片粒度"的偏好问题，直接跟第1条边界bug是同一个根**：句子越长、
     内部包含的语法句越多，`refine_boundaries.py` 内部切分点算法（按字数
     比例插值+文本对齐）出错的自由度越大，这次4处真实bug全部出在"一张卡片
     塞了好几句"或者"题目分组内部切分点"这类位置，不是巧合。**新规则**：
     第1步抄原文时，`text` 字段必须是单个语法句（以"。"/"？"/"！"结尾，
     不能是一整个说话轮次/一整段），每个语法句独立配一条 `zh` 翻译（教材
     原文如果是整轮翻译成一句中文，需要自己按语义拆开——大多数时候能找到
     自然的拆分点，比如"それはよかった。そうそう，大学の時の友達からは，
     今でも連絡があるかい。"官方译"那就太好了。对了，大学时代的朋友们现在
     还有联系吗？"直接按句号拆成两条）。这条规则同时也让单词测试例句来源
     核实（第6a步的 `occurrences.json`）更干净——原来长句子里如果一个词的
     `blank` 在同一句里出现两次要专门处理（见"常见坑"），拆成单句之后这类
     冲突大幅减少（这次"申し込み"这个词原来在同一句里出现两次要挑更长的
     blank 避开，拆句之后两次出现天然分到了两个不同句子里，不用再特殊处理）。
  2.5. **修复第2点的拆分需要整个重新走一遍第2~6步（重新分配草稿时间戳、
     `refine_boundaries.py`、`validate_boundaries.py`、`merge_sections.py`、
     `build_page.py`），不是小改**——草稿时间戳可以按"题目分组的粗跨度不变，
     组内按新的（更多、更短的）句子列表按字数比例重新分配"这个办法批量生成
     （不用重新一句句核对），`refine_boundaries.py` 会在这个草稿基础上重新
     对齐，草稿准不准不影响最终精度。`vocab_words_quiz.json`/`occurrences.
     json`/`sentences.json` 也要跟着重建——生词的 `id` 偏移量变了（会话+课文
     总句数从27变成51，生词起始id从28变成52），`occurrences.json` 里的
     `idx` 全部要重新定位到拆分后的新句子列表。
  3. **拆分重建之后，用同样的方法核实这4处已知边界又跑出了几乎一样的新
     bug（id7"これ"这次算成21.93，仍然比RMS验证的真实起音21.64晚；text
     里"これは，就職活動を…"这句的edge_start，不管拆分前拆分后都稳定算成
     46.3，但RMS验证真实起音在45.80，差了0.5秒）——这说明"把长句拆短"
     本身不能自动修复这类edge_start计算偏差，只是降低了这类偏差发生的
     概率（这次32+19个句子里仍然复现了同样的问题，只是数量上比长句版本少）。
     真正定位这类bug最终只能靠RMS能量剖面（详见"常见坑"新增的一条），
     不能假设"句子拆短了、多轮独立验证过了，这类问题就不会再出现"。**这是
     这个 skill 目前踩过的所有坑里，最直接反驳"一次性修复就能一劳永逸"这
     种想法的案例**——同一类边界精度问题，在同一课里，用两种不同的句子
     切分粒度独立触发了两次，累计三轮全量校验（第一次生成、按用户反馈修复、
     拆分重建后再验证）才收敛。
  4. **用户看完第3轮修复的结果后直接反问"你有没有使用之前 skill 啊？感觉和
     之前的质量相比，差太远了"——逐句核实下来，这句话完全站得住**，暴露出
     两类新问题：
     - **`verify_clips.py` 的整体相似度校验，对"局部缺失但整体还能对上"这类
       边界bug几乎无效，这一课至少4处真实bug是靠人工按用户反馈直接核实才
       抓到的，不是自动化脚本抓到的**——这一点 SKILL.md 早就记录过（"课文
       段首句开头被切"那条坑），但这次做拆分重建之后的复核时，只对少数几个
       有先验证据的点做了完整的 RMS/直接转写核实，其余十几处"看起来可能有
       问题"的信号（`validate_boundaries.py` 的 tail_gap 警告、自己写的
       word-level/RMS 扫描脚本标出来的"边界落在词中间"）都归类成"大概率是
       已知的良性模式"就没有逐条深挖——**这是明知道"局部缺失不会拉低整体
       相似度"这条结论，却在实际操作时又退回到"自动化校验通过=大致没问题"
       的心态，知道和真正做到是两回事**。用户反馈的4处真实bug（会话第1节
       结尾/ところで，どうだい/ええ这句/じゃあ无理も言えない起后面全错）
       没有一处在这之前的自查里被主动发现，全部是用户自己听出来的。
     - **给已经确认修好的边界，在后续因为别的原因（这次是合并"ええ"/"いいえ"
       这两句）重新跑一遍 `refine_boundaries.py` 全量对齐时，会被这次全新
       的对齐结果悄悄覆盖回原来的错误值，而且不会有任何提示**——`align_
       group()` 每次都是从头对整个题目分组重新计算，不知道"这个位置之前
       人工核实过、有一个更可信的手动订正值"这回事。真实案例：会话id1/id2
       （王さん开头被切）、id7（これ开头被切）这两处第一轮就已经用 RMS
       核实修复过，但因为要合并"ええ"/"いいえ"这两句、需要整个重新走一遍
       `refine_boundaries.py`，这两处修复在重新对齐时被静默覆盖回了跟第一轮
       同样的错误值（8.5、21.97），而我只顾着验证这次新发现的问题（id13/14），
       没有意识到需要把所有此前手动订正过的边界重新核对一遍。**教训**：
       任何一次触发"整个题目分组重新走 `refine_boundaries.py`"的操作（不管
       原因是拆分句子还是合并句子），完成之后要把**这个题目分组内此前所有
       手动订正过的边界值**都重新核对一遍是否还生效，不能只验证这次操作
       直接导致的那一个变化点——最稳妥的做法是维护一份"这一课手动订正过
       哪些边界、订正后的值是多少"的清单，每次全量重新对齐之后照着清单
       挨个核对，而不是凭记忆挑几个测。
  5. **同一课后续又暴露了三条更细的方法论问题，写进了新增的共享工具
     `tools/listening/audit_boundaries_rms.py` 的文档字符串（用法细节见
     该文件），这里只记结论**：① 用 RMS 能量剖面判断某个边界"是否落在
     语音内部"时，**命中的百分比小（比如5~10%）不能当成"可忽略"直接跳过**
     ——有一处一开始被判成"6%、可忽略"，后来证实是用户真能听出来的
     真实bug（重新做更细粒度分析后发现真实起音比边界早了0.09秒，这个
     量级人耳完全可以察觉）。② 检测到"边界落在一段连续语音burst内部"，
     **不能凭"离哪句更近"就认定这段burst是哪一句的内容，必须另外跑一次
     覆盖前后几秒的word-level转写来确认burst的真实身份**——这一课有一处
     边界，第一轮判断成"这两句之间就是纯静音、没有真实分界点"（因此把
     两句合并成一张卡片），第二轮虽然发现了这段声音的存在，却想当然把它
     归给了相邻的已知句子，两轮判断错误的根源相同：看到一段能量剖面，
     没有先去确认它到底对应哪个词，就凭"挨着哪句最近"下结论；只有真的
     跑了一次word-level转写、发现"相邻那句的内容早在这段burst开始前就
     已经结束了"，才推翻了两轮的错误假设，找到这段burst其实是一个独立、
     太短促而没被Whisper转写成词的应答词（"ええ"）。③ **能量剖面必须用
     10ms（或更细）帧长，20ms 会把"上一句尾音+短促应答词+静音+下一句
     开头"这类挤在一起的内容全部糊成一个burst，看不出内部其实还有独立
     的短促内容**——这类几乎不带停顿、持续时间可能只有150~200毫秒的
     应答词（"ええ""はい"这类），是这个坑最容易复现的场景。
  6. **这一课因为反复重新生成 `audio/` 目录（同一个 slug 下先后至少4次
     完整rebuild，每次的句子切分/编号都不一样），暴露了一个跟内容本身
     无关、但会让用户测试结果显得"混乱不可信"的问题：网站的音频客户端
     缓存（Cache Storage API，`docs/js/listening-page.js` 里的
     `AUDIO_CACHE_NAME` 那一层）按 URL（`audio/seg-NNN.mp3`）为键**，
     不会因为服务器上的文件内容变了就自动失效——同一个URL在这一课的
     历史上先后对应过完全不同的句子/生词内容，用户如果在某一次rebuild
     之后测试过、浏览器缓存了旧内容，之后哪怕服务器早已更新成正确版本，
     还是会继续放出缓存的旧音频，表现成"你都说修好了，我这边还是不对"
     ——曾经有一次用户反馈的"这句音频是课文的，完全搞错"，直接对比服务器
     文件字节内容后确认服务器版本完全正确，唯一合理的解释就是浏览器缓存
     了这一课最早期rebuild时同一个URL位置对应的课文内容。**排查方法**：
     每次同一课在同一次会话里做过不止一轮 `rm -rf audio/` + `build_page.py`
     重新生成之后，用户反馈"修了但还是不对"时，第一件事是用 `curl` 直接
     拉取线上的 `data.js`/`audio/seg-NNN.mp3`、跟本地已提交版本比对字节
     内容（不经过浏览器），排除"服务器端其实没问题、只是客户端缓存过期"
     这种可能，再决定要不要继续深挖服务器端。确认是缓存问题时，建议用户
     用无痕窗口测试或者清除这个站点的 Storage，不要让这类"虚假的复现"
     牵着继续瞎改已经正确的边界。
  7. **这一课踩完上面第4点"手动订正被静默覆盖"这个坑之后，把"维护一份
     清单、每次全量重新对齐后照着清单挨个核对"这条教训直接落地成了工具**，
     不再依赖记性：`tools/listening/apply_manual_overrides.py`（用法见上面
     第4步"人工核实过的边界订正"）——清单本身就是脚本的输入（`manual_
     overrides_<mondai>.json`，按 `text` 精确匹配），"照清单核对"变成
     "重新跑一遍脚本"，不用人工挨个回忆判断。同时把这一课反复出现的"改完
     边界之后现写一个几十行小脚本同步 `data.js` 的 `tokens`""改完边界之后
     手工换算这一段在合并音频里的偏移量再拿 `ffmpeg -ss -t` 重切"这两个
     一次性套路，分别抽成了 `tools/listening/patch_sentence_tokens.py`
     （见"生成页面"一节）和 `tools/listening/recut_clips.py`（见"生词音频
     静音裁剪"上方那条 l13 案例），下一课再遇到同类问题不用现写。
  8. **发布之后用户又反馈了4个生词（ごく/焦る/ブラック/海面）的音频边界问题，
     排查中意外发现了一个比这4处边界更大的坑：`audit_furigana.py` 对生词表
     的审核分支从 `--data-driven` 成为唯一用法之后就一直没跟着更新，长期
     处于"看起来在跑、实际零覆盖"的状态**，按发现顺序记录：
     - **诊断这4处边界时的新技巧**：直接对着 `combined8.m4a`+对应 `enriched_
       combined.json` 里的 `start`/`end` 用 RMS/word-level 分析，其中"ごく"
       是真的边界算错（align_group() 对齐偏差，跟以前的坑同一类），但
       "焦る"/"ブラック"/"海面"三个怎么分析都对不上——最后是**用 `faster_
       whisper` 转写时顺手打印的 `info.duration` 发现的**：这三个词在磁盘上
       的 `seg-NNN.mp3` 实际时长（0.39s/0.45s/0.60s）跟 `enriched_combined.
       json` 里 `end-start` 算出来的期望时长（1.66s/1.48s/1.24s）完全对不上
       ——说明这几个文件是被**后来某次独立操作**（这次是 `trim_clip_silence.
       py` 用 -35dB 阈值裁剪时判断过猛，把真实内容也裁掉了）改过的，而不是
       `enriched.json` 记录的边界本身有问题。**以后排查"生成完之后又报出来的
       生词边界问题"，第一步应该是先比较磁盘文件实际时长和 `enriched.json`
       期望时长（`ffprobe`/`faster_whisper` 的 `info.duration` 都能拿到），
       对不上就说明要找的是"文件后来被改过"而不是"原始边界算错"，两类问题
       排查方向完全不同，不比这一步会在错误的坐标系里分析半天**（这次先
       套用 l14 当天 RMS 分析那一套排查了很久都没发现问题在哪，直到偶然
       印出 duration 才恍然大悟）。三处最终都用 `recut_clips.py` 直接从
       `combined8.m4a` 按 RMS+word-level 核实过的真实边界重切，绕开了已经
       裁剪过的旧文件。
     - **同一轮用户还反馈"茶色い"注音错误**，排查发现 `_split_kana_
       segments()` 把"茶色"的注音截断成"ちゃ"（应为"ちゃいろ"）——根因
       跟"低"字（`_KANJI_MIN_MORA` 表）完全同一类 bug：默认假设每个汉字
       至少1拍，但"色"训读いろ是2拍，搜索紧跟的送假名"い"时在"茶色"自己
       读音的第一拍"い"（ちゃ**い**ろ）就撞上了。补一条 `"色": 2` 进
       `_KANJI_MIN_MORA` 表就修好了，跟"低"是同一个表、同一套修法。
     - **真正的大发现在往下查"这种bug为什么全量读音复核没抓到"的时候**：
       `audit_furigana.py` 对没有 `char_times` 的生词条目，读的是 `enriched.
       json` 里的 `furigana` 字段（这是更早期非 `--data-driven` 页面路径的
       产物），而不是现场重算——**但 `--data-driven` 模式下 `build_page.py`
       的 `sentence_to_data()` 根本不读这个字段**（有 `kana` 就现场跑
       `_split_kana_segments()`，没有就现场跑 `tokenize_ja()`），这个脚本
       审核的和页面实际渲染的从一开始就是两套独立计算、没有任何保证一致。
       一查 l14 的 `enriched_combined.json`：**88个生词条目的 `furigana`
       字段全部是 `None`**（这一课生词表走的是"整段word-level转写+一次性
       `align_group()` 对齐"这套自定义流程，从来没调用过 `build_vocab_from_
       wordlist.py`，从来没填过这个字段）——`_scan_prebaked_furigana()`
       对着 `None` 只会返回空列表，**不报错、不警告，跟"审过了、全部正确"
       在报告里长得一模一样**。回查 l13（同样用了这套自定义生词流程）
       也是89个生词条目 `furigana` 全部 `None`——也就是说**这个 skill 有
       生词表的每一课，只要用的是"整段对齐"这套（现在的）标准流程，生词表
       的读音就从来没有被这个审核脚本真正检查过，包括之前提交记录里写着
       "补做全量读音复核"的那几次**（那几次真正抓到的3处bug——君/李/歳——
       全部来自句子分支，生词分支全程静默、没人发现）。已经修好
       `audit_furigana.py`（`_scan_vocab_entry()` 严格复现 `sentence_to_
       data()` 的真实分支：有 `kana` 走 `_split_kana_segments()`，没有走
       `tokenize_ja()`），并加了一行覆盖计数（"本次共处理 N 句 + M 条生词"），
       **以后这类"某个分支的输出一直是零"不会再悄悄看起来像"零问题"**。
       用修好的脚本重新全量复核了 l14（88条生词，除了茶色い都正确）和 l13
       （89条生词，工作目录还在），l13 发现3处疑点，如实报告给用户而不是
       擅自改，结果只有1处是真bug：`出生`生词条目读しゅっしょう，句子里
       "出生率"读しゅっせい，两个读音单独看都合法（这个词本来就有两种
       读音），跟"その後"那次是同一类"值得跟用户确认、不是脚本能判断对错"
       的情况，核实完两处各自都对，不是bug；`年月`同理（生词条目读ねんげつ，
       句子里读としつき），受限于 Whisper 对常见词组倾向直接输出汉字，没能
       用转写确认实际读音，留给用户后续人工核实。**`後方づけ`（あとかた）
       这一条，音频反复核实（含用假名强制转写）听起来确实是"あと片付け"，
       跟译文"善后，整理，收拾"（对应"後片付け"）语义也吻合，判断成`方`是
       `片`的转写typo，实际改了（`後方づけ`→`後片付け`，含 tokens/blanks/
       quizSentence/单词测试quiz条目共5处）——用户随后明确反馈"後方づけ"
       才是对的，已经 `git revert` 撤销**。教训：**这类"文字内容本身对不对"
       的判断（不同于"读音标注对不对"），音频转写只能提供旁证，不能当成
       独立于教材截图/用户确认之外的定论依据**——第1步"读截图抄原文"如果
       已经完成、原文是从截图抄下来的，音频转写跟抄录文字对不上时，优先
       怀疑是转写本身不准（同音字、方言、语速快等因素都可能让 ASR 输出
       跟教材实际印刷的字不一致），而不是反过来去改教材原文；真要改动
       教材原文本身（不是改读音标注），必须让用户看着原始截图确认，不能
       单凭音频转写的"听起来像"就动手。l10/l11/l12 的工作
       目录已经按约定清理，没法重新跑完整审核，退而求其次直接扫了一遍
       已发布 `data.js` 里有没有"汉字段字数 > 假名段字数"这种截断特征
       （这次"茶色い"bug 的典型信号），没有发现新的可疑条目，但**这不等于
       这三课的生词表被真正审核过**，只是一个廉价的事后代偿检查，不能当成
       跟"用修好的脚本重新全量复核"同等可信。

## 参数

输入参数是**一个目录路径**，形状约定为：

```
<课程目录>/
  会话/    （或"對話"等，取决于教材命名——按实际文件夹名识别，不强求这个字面值）
    *.jpg/*.png     课本截图（可能不止一张，按文件名顺序读，但见下面"截图排序坑"）
    *.m4a/*.mp3     这个部分的录音（应该只有一个）
  课文/
    ...同上结构...
  单词/
    ...同上结构...
```

有几个子文件夹、分别叫什么名字，直接读目录列出来，按文件夹名映射成 tab 标签
（不强制"会话/课文/单词"这三个字，教材不一样命名可能不同，比如"對話"/"本文"/
"語彙"，照抄实际文件夹名）。只出现其中一部分文件夹（比如没有"单词"）也正常处理，
tab 数量跟着文件夹数量走。

标题、密码、输出 slug——按下面"0. 默认值怎么定"处理。

## 0. 默认值怎么定

跟 `jp-listening-page`/`jp-meeting-listening-page`一致的原则：**有先例可循时不逐项
问，没有先例（新教材系列第一课）时要问**。

- **slug**：`textbook-<书名缩写>-<课号>`，缩写没有先例时问用户（第一个案例是
  `textbook-sjp-zg-l10`——sjp=标准日本语，zg=中级，l10=第10课）。同一本书后续课
  沿用同样的缩写规律，只换课号，不用再问。
- **密码**：复用全站统一密码哈希（跟 `docs/private/index.html` 枢纽页、N2 系列
  共用一份），从任意现有私有页面的 `<div id="gate" data-hash="...">` 摘，
  `build_page.py` 用 `--password-hash` 传。
- **枢纽页**：这个 skill 的默认值是**独立枢纽页**（`docs/private/textbook/
  index.html`），不混进 `docs/private/index.html`（第一个案例里用户明确要求
  "单独做一个枢纽页"，后续确认过"课程要有一个总的入口页，而不是每课一个"）——
  **不管哪本教材/哪个系列，都只用这一个枢纽页**，都加进同一份卡片列表，不用
  再问、也不再建新的枢纽页。
- **tab 顺序**：照抄源材料自己的 tab 顺序（第一个案例是 会话→课文→生词，来自
  app 截图里"会话/课文/语法与表达/生词/练习"的顺序，只取有材料的那几个）。
- **语法与表达/练习 tab**：如果用户没提供对应的文件夹，不生成这两个 tab，不用
  临时编内容凑数。
- **默写/填空练习模式**：直接继承共享 JS/CSS 里已有的默写/填空模式，不用为这个
  skill 单独实现——`docs/js/listening-page.js`/`docs/css/listening-page.css` 已经
  支持，`build_page.py` 生成的页面结构（`.seg-card`/`.seg-notes`）天然兼容。

## 日志记录（贯穿下面每一步，包括跑的每一个脚本）

`docs/private/<slug>/LOG.md`——从第1步开始，每一步实际做的操作都追加一条
记录：读了哪些截图、跑了哪个脚本（命令+一句话结果摘要，比如"跑了
`refine_boundaries.py`，×处对齐失败，人工核实后……"）、发现了什么问题、
怎么处理的、用户反馈了什么、怎么修的。**这份文件放在 `docs/private/<slug>/`
下（不是 `tools/listening/work/<slug>/`），因为它是这一课唯一保证长期存在
的目录**——`work/` 目录是脚本产出的中间文件（草稿json/临时音频），按现有
约定不提交，事后经常被清理（真实案例：l10/l11/l12 的 `work/` 目录后来都已
清空，想回查"当初这一课到底跑没跑过某个校验步骤"完全无据可查，只能靠
不完全可靠的记忆），`docs/private/<slug>/` 才是每一课唯一必然跟着内容一起
提交、永久保留的地方，日志必须放在这里才真正有长期价值。这份文件跟
`data.js`/`audio/` 一样正常提交进 git，不用额外处理。

**不是为了留痕而留痕**——这条规则直接针对这个 skill 反复踩过的"跑了
校验≠做了校验"这类坑：`audit_furigana.py --all` 这类全量人工复核步骤，
事后经常说不清楚"当时到底有没有真的逐行看过"，日志里明确写"跑了
`audit_furigana.py --all`，N句+M条生词，逐条核对，发现X处问题"，比
事后凭记忆回答"应该跑过吧"可信得多，也方便下次同一课再出问题时，先
查日志而不是从头重新调查一遍。每条记录不用逐字抄命令输出，摘要即可，
但**必须包含跑没跑、看没看这个层面的信息**，不能只记"生成页面成功"这种
没有信息量的条目。

## 整体流程

### 1. 读截图，抄下 ground-truth 原文

**不用 OCR 工具，直接用 Read 工具读图**（Claude 自带视觉能力，比接一个额外 OCR
依赖更可靠，尤其教材截图里经常混着日语/中文/假名读音，一般 OCR 分不清版式）。
按文件夹分别读：

- **会话/课文类**（整段对话/文章）：把每张截图里的文字原样抄下来，保留说话人
  标签、场景说明（通常是中文，用括号或斜体标出）。场景说明/中文旁白不当成日语
  听写句子（后面第3步会跳过，见"中文旁白怎么处理"）。
- **生词类**（词条列表）：每条格式通常是"假名（汉字）[词性] 中文释义"，抄的时候
  分开记：`text`（喂给 `ruby_html()` 生成假名注音用的原文——有汉字就填汉字形式
  比如"観光地"，纯假名/片假名词条就原样填比如"スケジュール"）、`zh`（连词性
  标签一起抄，比如`"[名] 观光胜地，旅游胜地"`，帮助记忆）。

**截图排序坑（已踩过）**：滚动截屏工具导出的文件名时间戳顺序**不一定**等于
滚动/阅读顺序——真实案例（textbook-sjp-zg-l10）里`单词/`文件夹三张图的文件名
序号是 489<490<491，但实际内容顺序是 489→491→490（490 结尾有"下一个生词表"
的过渡语，491 的内容明显接在 489 后面）。**不要假设文件名数字顺序=阅读顺序**，
每张截图读完后要看内容是否和上一张自然衔接（词条列表看是否跟前一张的最后一条
语义连贯、对话看是否是同一场景的下一句），衔接不上就重新排列，排完序在后面
第2步"跟 Whisper 粗转写核对顺序"那一步还有一次交叉验证的机会。

### 2. 每段音频跑 Whisper 打时间戳草稿

```bash
python tools/listening/transcribe.py <部分>/<音频文件> <输出.json> --model medium
```

多个部分（会话/课文/生词）**各自独立跑**，`run_in_background: true`（并行跑省
时间）。这一步的转写文本**不用来校对原文**（原文已经从截图抄下来了，比 Whisper
的转写准），只用来：

1. 交叉验证第1步排的顺序对不对——转写文本即使个别字听错，大体的词/句顺序应该
   跟截图抄下来的 ground-truth 顺序一致，如果对不上说明第1步排序或转写本身有
   问题，回去核对（真实案例里就是靠这一步确认了"489→491→490"这个顺序）。
2. 生词表：转写出来的 segment 数量应该约等于词条数量（真实案例：99个词条对
   100个 Whisper segment，多出来的1个是句尾静音处的典型 Whisper 幻觉"ご視聴
   ありがとうございました"，删掉后精确 1:1，位置索引对应即可拿到每个词的粗
   时间戳，不用跑 `refine_boundaries.py`——单词粒度不需要逐字符高亮，粗时间戳
   够用，省一大截处理时间）。segment 数量对不上时，回去听一下差异出现的位置，
   通常是某条截图抄漏/多抄，或者 Whisper 把两个词合并识别成一个 segment。
3. 会话/课文：粗时间戳只是给 `refine_boundaries.py` 当起点用的草稿，不需要精确
   到句——但**不要偷懒直接按"整段平均分"分配粗时间戳给每一句**，那样如果某句
   实际很长、某句很短，草稿边界可能整个偏到相邻句子的范围外，`refine_
   boundaries.py` 的算法是"以整道题（这里=整个 tab 内的一个 question 分组）的
   粗边界为窗口重新做一次转写"，草稿窗口偏差太大会导致窗口漏掉真实内容或包含
   进下一组的内容。做法：对照 Whisper 转写文本，把已知的句子在文字上跟转写
   片段做粗略比对，按转写片段的时间戳分配（一句可能跨好几个转写 segment，也
   可能好几句共享一个 segment，都要跟着转写内容手动split/合并着分配，不是纯
   算比例）——这一步麻烦但值得做，直接决定 `refine_boundaries.py` 那一步的
   輸入质量。

### 3. 中文旁白/章节标题怎么处理

会话类材料里常见的中文场景说明/旁白（比如"（王风和山田坐在沙发上，翻开日程
表。）"）**不当成一句要听写的日语**，从 `enriched.json` 的 `sentences` 里直接
跳过（连对应的音频时间段也不切）——这段旁白占的音频时长依然存在于原始录音里，
只是不给它生成 `.seg-card`，播放时这段时间就是两句真实日语对话之间的一小段
空白，不影响功能。**不要**为了保留旁白硬凑一个"没有日语原文"的卡片，那会破坏
默写/填空模式假设"每个 `.seg-card` 都有 `.seg-ja`"的前提。

**但每段音频开头的日语章节标题（比如会话的"若者の意識"、课文的"漫画とアニメ"）
不能直接套用"旁白就跳过"这条规则不检查就默认跳过**——这两者看起来都是"正文
之外的东西"，但标题通常是**真的用日语念出来的**，旁白通常不是。真实案例
（textbook-sjp-zg-l11）：第一版直接假设标题也该跳过，用户反馈"会话和课文的
标题也是有发音的哟，现在都没有"——回去用 word-level 转写探一下每段音频最
开头几秒，两个标题都清清楚楚地被念出来了。**规则改成**：第2步跑完粗转写后，
去看这一段最开头几秒的转写内容是不是就是章节标题本身，是的话按普通句子一样
处理（配假名、翻译，塞进第一个 question 分组的最前面，一起走 `refine_
boundaries.py`），不是（比如真的只有沉默、或者是中文旁白）才跳过。

### 4. 组装 `enriched.json`（会话/课文用 `refine_boundaries.py`，生词跳过）

**每条 `sentences` 记录的 `text` 必须是单个语法句（以"。"/"？"/"！"结尾），
不能是一整个说话轮次或者一整段——这条规则不是可选的排版偏好，是真实踩过坑
才定下来的（textbook-sjp-zg-l14）**：早期几课都习惯性地按截图/口语的"一轮
对话"或"一个自然段落"抄成一张卡片（比如"ありがとうございます。では，お
邪魔します。"两句合一张），用户反馈"没有严格按照句子来分"之后才发现——
句子越长、内部包含的语法句越多，`refine_boundaries.py` 内部切分点算法出错
的自由度越大，这跟同一课踩到的好几处真实边界bug是同一个根，不是巧合。
每个语法句独立配一条 `zh` 翻译（教材原文如果是整轮翻译成一句中文，需要
自己按语义拆开，大多数时候能找到自然的拆分点，比如官方译"那就太好了。对了，
大学时代的朋友们现在还有联系吗？"直接按句号拆成两条对应两个日语句子）。
拆成单句还有一个连带好处：第6a步"单词测试"例句核实时，一个词的 `blank`
在同一句里出现两次需要特殊处理的情况会大幅减少（拆句后天然分散到不同句子）。

会话/课文两段：按"每道题=一个 question 分组"的结构（可以按场景/段落分
question，比如会话分"商量行程"/"电话预订"两组，课文按自然段分"第1段"~"第4段"
——这样侧栏导航更有用，一个 question 分组内部通常包含好几个语法句/卡片），
`mondai` 统一填这一段对应的 tab 标签（比如"会话"），
写好 `text`（截图抄下来的原文，单个语法句）/`zh`（自己翻译，教材通常没有逐句翻译，跟其它
听力页一样的翻译尺度——信达为主不追求文学化）/`notes`（只在真正有语法点的
句子写，寒暄/短句留空，跟 `jp-listening-page` 一样的详略度标准）/`speaker`
+`speaker_kana`（会话类材料每句前面印着的说话人名字，比如"王"/"担当者"，
有就填，没有的独白/课文句子不填）。**说话人不要拼进 `text` 里再喂给
`ruby_html()`**（`build_page.py` 的 `sentence_card_html()` 会把 `speaker`
单独渲染成 `.seg-speaker`，用绝对定位放在卡片左侧内边距的空档里，跟读模式
常驻显示、默写/填空模式自动隐藏——拼进 `text` 的话说话人会被当成日语原文的
一部分参与跟读高亮/默写比对/填空挖空，都不合适，见 `docs/css/listening-
page.css` 里 `.seg-speaker` 的注释）/`blanks`（**每一句都必须有，不是可选**——
见下面单独一条说明）。然后：

**`blanks` 每句必填，不能因为"这句没有语法点"就跳过**：真实案例
（textbook-sjp-zg-l13/l14）：会话/课文两个tab合计80句，一开始只给2句配了
`blanks`，用户直接问"为啥课文和会话的填空这么少？你有没有好好做过？"——
诚实的答案是没有，当时把"没有语法点就不写"理解成了"大部分句子可以不写"，
实际上没有真的逐句判断。用户明确了规则：**有语法点的句子，挖语法点；没有
语法点的句子，挖这句的主要动词或名词，不能因为没有语法点就不出填空题**。
具体做法：
- 有语法点（值得写 `notes` 的句子）：`blanks` 挖这句原文里真实出现的语法点
  文字（不是抄 `notes` 里的抽象说明），比如某句语法点是「〜というわけでは
  ない」，句子里实际出现的文字是"というわけではない"，就写 `"blanks":
  ["というわけではない"]`——`blanks` 才是决定"挖哪段、答案是什么"的唯一
  数据源，`notes` 只是提交完所有空之后展示给用户看的解释文字，互不影响。
  一句有多个语法点就在列表里按顺序都写上。
- 没有明显语法点的句子（寒暄语/简单陈述句）：挖这句的主要动词或主要名词
  （比如标题句"日本の就職活動"没有语法点，就挖"就職活動"），`notes` 可以
  留空，不强求每个纯词汇挖空都配一段语法解释。
- 无论哪种情况，`blanks` 里的文字必须是这句原文（`text` 字段，不是 `zh`
  翻译）里能找到的**精确子串**（不含首尾标点），生成/patch 之前先用代码
  确认一遍（`if blank not in text`），不要凭印象手写就假设一定对得上。

```bash
python tools/listening/refine_boundaries.py <这段音频> enriched_raw.json enriched_refined.json
python tools/listening/validate_boundaries.py enriched_refined.json enriched_final.json
```

#### 人工核实过的边界订正：`apply_manual_overrides.py`（后续每次重新跑 `refine_boundaries.py` 都要补跑）

`refine_boundaries.py` 每次都是从头对整个题目分组重新对齐，不知道"这个位置
之前用 RMS/word-level 人工核实过、有个更可信的订正值"这回事——这一课如果
中途因为别的原因（合并/拆分句子、改了某句 `text`）要重新跑一遍 `refine_
boundaries.py`，之前已经核实修好的边界会被这一次重新对齐悄悄覆盖回错误值。
真实案例（textbook-sjp-zg-l14）：会话里两处已经用 RMS 核实修复过的边界
（"王さん"开头/"これ"开头），因为后来要合并"ええ"/"いいえ"这两句触发了一次
新的 `refine_boundaries.py`，在没人记得要回去重新核对的情况下被静默覆盖回
原来的错误值，直到下一轮用户反馈才发现——用户当场指出"你有没有使用之前
skill啊？感觉和之前的质量相比，差太远了"。

做法：**每次改完一批边界、确认是真实bug并且用 RMS/word-level 核实过正确值
之后，随手把这条订正记进这一课工作目录下的 `manual_overrides_<mondai>.json`**
（不存在就新建，按 `text` 原文精确匹配，不是按 `id`——`id` 会在每次 resplit/
合并之后重新编号，`text` 只要这句话没被拆分/合并/改写就不会变，是跨多轮
重新生成依然稳定的锚点）：

```json
{
  "これ，つまらないものですが……。": {"start": 21.60, "char_time_first": 21.65},
  "あれ，そんなに気を使わなくてよかったのに。": {"end": 27.44, "char_time_last": 27.44}
}
```

```bash
python tools/listening/apply_manual_overrides.py enriched_refined.json manual_overrides_dialogue.json enriched_final.json
```

`start`/`end` 决定音频真正切在哪（最要紧的一项），`char_time_first`/`char_
time_last` 可选，给了就精确覆盖跟读高亮第一个/最后一个字符的时间戳（不给
只做"越界就夹回边界内"的保底处理，精度不如显式指定）。**放在 `validate_
boundaries.py` 之后跑**（订正的是最终边界，不希望被 `validate_boundaries.py`
的重叠裁剪逻辑又动一次）。之后哪怕这一课因为别的原因要重新跑一遍 `refine_
boundaries.py`，也只需要在新的 `validate_boundaries.py` 输出上再跑一遍本
脚本，之前核实过的订正就自动重新生效，不用凭记忆一条条回去重新核对。

生词表：不跑 `refine_boundaries.py`（单词粒度不需要逐字符跟读高亮），但
**必须**跑一遍收紧边界（见下面"生词边界收紧"），不能直接把 `transcribe.py`
分块转写的粗 segment 时间戳当最终结果——真实案例（textbook-sjp-zg-l11）：
直接用粗 segment 时间戳的话，144 条里绝大多数都有明显问题（开头带几秒纯
静音、结尾被切短、甚至连着下一个词的音），用户听了三四轮才挑出来，每轮
都还有漏网的（包括我自己手工核对时读错 token 边界、把"彼ら"看漏了"ら"字
这种低级错误）——**人工挨个核对 144 个词条不现实，必须用自动化脚本收紧+
自动化脚本校验，人工只做"看报告决定信不信"这一步**，见下面两小节。这一步
最开始用共享工具 `tools/listening/build_vocab_from_wordlist.py` 生成一版
初稿（`char_times` 留 `null`，`ruby_html()` 退化成纯 furigana 展示，不影响
使用）：

```bash
python tools/listening/build_vocab_from_wordlist.py vocab_words.json transcript_vocab.json enriched_vocab.json \
  --drop-hallucination "ご視聴ありがとうございました"
```

`vocab_words.json` 是自己按截图整理的词表（格式见脚本文档字符串：`group`/
`text`/`zh`/可选的 `kana`——有 `kana` 就用这个读音包 `<ruby>`，不用 `kana`
就走 `ruby_html()` 自动转换，遇到熟字训容易读错的词一定要填 `kana`，见"常见
坑"）。`--drop-hallucination` 传要从转写结果里剔除的幻觉文本（人工通读
transcript 发现，可重复传多个）。脚本会自检"词表条数 == segment 数"，对不上
直接报错退出（不悄悄错位对应）——**数量对上了也不代表完全没问题**，`transcribe.
py` 分块转写偶尔会把两个词的音频粘连成一个 segment（表现是这个 segment 的
时长明显长于同类词条），这种情况总数可能刚好还是对的，只是从这个位置起内容
错位，见"常见坑"，跑完建议打印一份"词表 vs segment 文本"的逐位置对照表人工
过一遍，尤其留意时长异常的条目。

**跑完之后无论如何都要再跑一遍 `validate_boundaries.py`**（哪怕跳过了 `refine_
boundaries.py`）：

```bash
python tools/listening/validate_boundaries.py enriched_vocab.json enriched_vocab_final.json
```

——`transcribe.py` 分块转写在块边界上偶尔会切出时间戳相邻重叠的 segment，
生词表直接照搬这些粗时间戳的话，重叠部分会让前一个词的音频尾巴多播出后一个
词的开头（真实案例踩过5次），`validate_boundaries.py` 的重叠裁剪不依赖
`refine_boundaries.py` 有没有跑过，跑这一步零成本，务必不要省。

#### 生词边界收紧（必须，不是可选优化）

`transcribe.py` 的粗 segment 时间戳只保证"位置对得上第几个词"，不保证切得
紧——真实案例（textbook-sjp-zg-l11）：直接部署粗时间戳，用户实测发现大量
词条要么开头带几秒静音、要么结尾被切短、要么连着下一个词的音，这不是个别
偏门词条，是**多数词条都有的系统性问题**。收紧步骤：

1. 对整段生词朗读音频跑**一次连续的** word-level 转写（不要手动切块传给
   `transcribe.py`，那样在块边界上会重新引入前面提到的粘连/重叠问题）：
   ```python
   segs, info = model.transcribe(audio, language="ja", word_timestamps=True, vad_filter=False)
   # 存成 start\tend\ttoken 每行一条，供下一步用
   ```
2. 用 `tools/listening/cluster_tokens.py` 的 `load_and_cluster()` 把这份
   word-level 转写按间隔合并成"词"级别的 cluster——**不要**直接对 Whisper
   拆出来的单字 token 各自转假名再比较，见下面"pykakasi 单字转换复合词坑"。
3. 对每个生词条目，以它当前（粗）的 `[start, end]` 为中心，从合并后的
   cluster 里按由窄到宽的多个 margin（比如 1.2/2.0/3.0/4.0 秒）依次搜索，
   用 `refine_boundaries.py` 的 `align_group()`（喂假名读音而不是原始汉字，
   同样是为了避开同音异字/复合词转换问题）算出这个词在窗口内真实内容的起止，
   取第一个"结果时长在合理范围内"（比如不超过读音长度×0.65+0.8秒，读音很
   短的词给个 1.2 秒左右的下限）的结果。开头留 ~0.12 秒、结尾留 ~0.15 秒
   缓冲。这一段没有现成脚本封装（每次教材词表构成不同，直接现写一个几十行
   的脚本比硬套一个通用参数化工具更快），但技术组合是固定的（本 SKILL.md
   这次踩坑后总结出来的）：`cluster_tokens.py` 负责分词，`align_group()`
   负责窗口内精确对齐。
4. 收紧完之后跑 `validate_boundaries.py` 清理收紧过程中新引入的相邻重叠/
   零时长（**这一步几乎必然会暴露一些"两个相邻词都收紧到了同一段音频"的
   冲突**，是正常现象不是 bug，逐个人工核实真实边界重新分配即可）。
5. **收紧完不代表就对了，必须再跑一遍"生词校验"（见下面）**——这一步只是
   缩小人工要处理的范围，本身不保证输出正确。

**排查信号：两个相邻 token 的 end/start 时间戳完全相等（零间隔）**，不能
直接当成"这两个词/字之间真的没有停顿，照抄这个点当边界"——真实案例：
"見込み"最后一个字"み"的 token 一路延伸到跟下一个词"主演する"的开头
完全衔接（零间隔），第一次收紧时我直接采信了这个零间隔当边界，结果用户
反馈"見込み后面的音频过长，把下一个词的音弄进来了"。**用
`ffmpeg -af silencedetect=noise=-30dB:d=0.3` 或者 `vad_filter=True` 重新
探测这个区间有没有真实的静音段**，这次真实案例里两个词之间其实有将近
3秒的真实停顿，Whisper 的 word-level 时间戳只是把这段停顿错误地"吞"进了
前一个词的 token 里（这跟前面"两个连续朗读、中间没有真实停顿的词"那条坑
刚好是相反的错误方向，同一个"零间隔"表象背后可能是两种完全相反的真相，
必须用静音检测或者 VAD 重新确认，不能凭 word-level 时间戳本身的表象
猜测）。

### 5. 多段音频怎么合成一个页面

`build_page.py` 只接受**一个** `audio_path` 参数（`cut_segments()` 对着这一个
文件用 `ffmpeg -ss/-t` 切每句），但教材天然是每个部分一份独立音频。这一步不用
现写脚本，用共享工具 `tools/listening/merge_sections.py`——一条命令同时做完
"拼接音频"+"按偏移量平移各段时间戳"+"合并成一份 enriched.json"：

```bash
python tools/listening/merge_sections.py combined.m4a enriched_combined.json \
  --section 会话.m4a enriched_dialogue_final.json \
  --section 课文.m4a enriched_text_final.json \
  --section 单词.m4a enriched_vocab_final.json
```

`--section` 按最终 tab 顺序传，每个都是"这一段的原始音频 + 这一段的
`enriched_final.json`"，可以传任意多段。拼接用的是 ffmpeg 的 `concat` filter
（不是 `concat` demuxer——后者要求几个文件编码参数完全一致，比较脆弱，filter
版本更稳）。

**关键原则：传给 `--section` 的每个 `enriched_final.json` 必须是对着它自己
那段原始音频（不是合并后的 `combined.m4a`）跑完 `refine_boundaries.py` 算出来
的**——那个脚本内部会对着传入的音频文件重新截取一段做 word-level 转写，如果
传的是拼接文件、时间戳却是本段自己的本地坐标系（没先平移），会截到完全无关
的音频位置；反过来如果先平移了时间戳再传拼接文件去跑 `refine_boundaries.py`，
则该脚本本身没有"平移量"的概念，同样会出问题。正确顺序是「各自原始音频 + 本地
时间戳」→各自跑完精修→`merge_sections.py` 一步到位完成拼接+平移+合并。

#### 生成页面之前：扫一遍高危字读音（必须，不是可选优化）

```bash
python tools/listening/audit_furigana.py enriched_combined.json
```

人/月/日/方/上/下/中/分/時/気/家/位 这类极常用单字读音随上下文剧烈变化，是
pykakasi 误读的重灾区，且这类错误不影响整体阅读理解，人工通读页面时很容易
看走眼漏过（详见"常见坑"一节）。这一步在跑 `build_page.py` 之前做，**报告
里每一条都要逐行人工确认**（不是扫一眼"大致正常"就跳过，是每一行都用自己
的日语知识核对这个字在这句/这个词的语境里到底该读什么音）：
- 读音不对——照 `build_page.py` 里 `_TOKEN_READING_OVERRIDES_BY_PREV`/
  `_UNCONDITIONAL`（固定搭配）或 `_resolve_hira()`（能提炼出通用规律的，比如
  "人"/"位"这类"孤立成词时怎么读、紧跟数字时又该怎么读"，优先加通用规则，
  不要碰到一种新句式就机械地加一条固定搭配，见"常见坑"一节的完整心路历程）
  订正（会话/课文句子）；生词条目走词表 `kana` 字段。
- 改完之后**重新跑一遍这个脚本，而不是只信自己刚才手动验证过的那一句**——
  改的是共用的订正逻辑，可能影响到报告里其它没打算动的行，要看一遍改完之后
  的完整报告确认没有引入新问题。
- 这一步**是这个 skill 里跟人工听音频核实音频边界同等级别的必做项**，不能
  因为"文字看起来通顺"就跳过，本节列出的这几个字历史上全部是真实发现的坑
  （不是假设性风险），而且都是分好几轮才发现全的（先发现"人"→"月/抜く/
  さっと"→"位"，每一轮自己以为审完了，结果还有漏网的），说明**审一遍就
  假设"这类问题解决了"是不成立的，每次新增课程内容都要重新走一遍这个流程，
  不能凭上次审过的经验就默认这次也没问题**。

#### 生成页面之前：全量读音复核（必须，不能只依赖高危字表）

```bash
python tools/listening/audit_furigana.py --all enriched_combined.json
```

`DANGER_KANJI` 高危字表只能覆盖"已经在某次真实案例里踩过坑的字"，**专有
名词（人名/地名/作品名）这类读音完全没有通用规律可循，天生不可能靠字表
覆盖**——真实案例（textbook-sjp-zg-l11）：《千と千尋の神隠し》里的人名
"千尋"被 pykakasi 猜成せんじん（该读ちひろ），"尋"这个字根本不在高危字表
里，标准的 `audit_furigana.py`（不带 `--all`）完全不会命中、不会提醒复核，
这条 bug 全靠人工用自己对这部电影的了解才发现（Claude 本身认识这个作品、
知道女主角叫"千尋/ちひろ"，这类知识判断脚本做不到，只有真的通读一遍才能
用上）。**这一步不是"扫一遍找出问题字"，是把这份 `enriched.json` 里全部
一两百条带汉字的读音都读一遍，凭自己的日语知识逐条判断对不对**，重点留意：
- 人名/地名/作品名这类专有名词——读音没有规律可循，孤立看"字对不对"没有
  意义，必须动用具体知识（这个词是不是自己认识的人名/地名/作品/角色名）。
- 同一个字/同一个词条在这一课内前后读音是否一致——真实案例：这一课里
  "その後"作为两条不同的生词分别读音标成そのご和そのあと，正文句子里的
  同一个词又读成のち，三种读音都是"その後"在不同语境下的合法读法（不能
  简单说哪个是错的），但同一课内出现三种不一致的读法本身值得停下来跟用户
  确认是不是有问题（比如是不是词表条目重复了、要不要统一）——**这类"各自
  看都不算错，但放在一起显得矛盾"的情况，脚本没法判断对错，遇到了如实报告
  给用户，不要自作主张合并/删除生词条目**。
- 跟前面"高危字扫描"那一步一样，**这一步跑完不代表"以后不用再跑"**，每次
  新增课程内容都要重新走一遍。
- **生词表和会话/课文重名的词，读音必须以生词表为准，不能让 pykakasi 在
  句子里另外猜一遍**——真实案例（textbook-sjp-zg-l13）："年月"生词条目
  人工核实过读ねんげつ，但课文句子"長い年月が必要だろう"里 pykakasi 默认
  猜成としつき，两边不一致，一开始误判成跟"その後"是同一类"多个读音都
  合法、只是碰巧不一致"，用户指出这不是歧义，该以生词表读音为准。这条
  规则现在已经内建进 `build_page.py`（`tokenize_ja()` 的 `vocab_readings`
  参数，`build_lesson_data()`/`patch_sentence_tokens.py` 会自动从这一课的
  生词表构造这份映射并传入），**不用再靠人工发现一个改一个**——但只做
  "整个 pykakasi 分词结果跟生词原文精确匹配"，生词表里跨好几个 pykakasi
  token 的词组（比如"無理を言う"这类动词短语）不会被这条规则覆盖，仍然要
  靠 `_TOKEN_READING_OVERRIDES_*` 手动加规则。**这条规则实质上收窄了"その
  後"那类"多个读音都合法"的适用范围**——如果生词表里真的有同一个词文本
  对应两条不同读音的条目（"その後"当初就是这种情况：一条生词读そのご、
  另一条读そのあと），`{生词原文: 读音}` 这个简单映射没法表达"这个词该用
  哪条"，会按 Python 字典构造时最后遍历到的那条为准（不可控），遇到这种
  真正的多义生词条目重复，应该先跟用户确认要不要把生词表本身合并/拆分成
  不冲突的写法，不能指望这条自动规则处理歧义。
- **跑完先看输出末尾"本次共处理 N 句 + M 条生词"这一行，确认 N/M 都跟这一课
  实际的句子数/生词数量级对得上，再去看命中列表**——真实案例（textbook-sjp-
  zg-l13/l14）：`audit_furigana.py` 生词表分支曾经因为读了一个 `--data-driven`
  模式下根本用不到的字段（历史遗留），对这两课的生词表全部返回空结果，报告
  看起来"审过了、全部正确"，实际上是**完全没处理任何生词条目**，这个bug
  一直存在到"茶色い"读音被截断成"ちゃ"这个真实问题被用户发现才暴露。现在
  脚本已经修好并且会打印这行覆盖计数，但"跑了脚本"不等于"这份数据真的被
  脚本看过"，这一行就是用来验证这件事的，不能跳过。

### 6. 生成页面

```bash
python tools/listening/build_page.py combined.m4a enriched_combined.json docs/private/<slug> \
  --title "标准日本语中级第N课：<课文主题>" \
  --subtitle "来源：《标准日本语》中级第N课（会话/课文/生词）。逐句配假名注音、中文翻译与语法笔记，播放时逐词跟读高亮，支持默写/填空练习，悬浮迷你播放器支持暂停/继续/循环。" \
  --password-hash <摘的哈希> \
  --side-nav-label "" \
  --data-driven
```

**`--side-nav-label ""` 不能漏**——`build_page.py` 的侧栏分类标签默认是「小問」
（继承自 JLPT/会议听力页的問題→小問结构，那边是对的），但教材课文页侧栏挂的
是章节/生词表这类内容，不是「問題」，沿用「小問」文不对题——教材课文页固定
传空字符串把这个标签隐藏掉，只留列表本身，不需要一个不准确的分类词。

**`--data-driven` 是这个 skill 的固定用法，一定要传**——不传的话内容（每句
原文/翻译/笔记/填空/说话人）会直接烘焙进 `index.html`，之后想改任何一个字
都得在一整份生成好的 HTML 里定点 patch（正则找到具体位置改），既容易改错
地方、又没法一眼看出"这一课到底有哪些内容"。传了这个 flag 之后，`build_
page.py` 只生成一个精简的 `index.html`"壳"（密码门/tab栏/悬浮播放器这些
固定 UI），内容单独写进同目录的 `data.js`（pretty-print，每个字段一行），
页面打开时由 `docs/js/page-renderer.js` 在浏览器里把 `data.js` 渲染成
跟以前完全一样的页面结构——**以后想改内容（改翻译、改填空目标、订正读音、
改说话人），直接改 `data.js` 里对应字段就行，不用碰 HTML、也不用重新跑
一遍生成流程**。`data.js` 里每句的 `tokens` 数组就是 `ruby_html()` 内部
分词+读音订正的结果（`{"text":原文,"kana":读音,"t":跟读高亮时间戳}`），
想订正某个字的读音，直接找到对应 token 改 `kana` 字段就行。**但如果是边界
（`start`/`end`/`char_times`）改了，`tokens` 里每个字/词的绝对时间戳 `t`
也要跟着重算——`data.js` 是静态数据，`enriched_combined.json` 改了不会自动
带动它更新**，用共享工具批量重算并原地覆盖，不用手改：

```bash
python tools/listening/patch_sentence_tokens.py docs/private/<slug>/data.js enriched_combined.json <id...>
```

### 6a.（必须）单词测试 tab：填空/听音频写假名/中文写假名/日文写中文

**这一步不是可选优化，是每一课都要做的**——早期几课（textbook-sjp-zg-l10/
l11）都做了，textbook-sjp-zg-l12 这一课当时忙着修音频边界/假名注音/跟读
高亮这几个问题，一直没顾上做这一步，事后才补（补的过程踩了几个新坑，见
下面"常见坑"），之后每一课生成完页面就该顺手把这个 tab 也建了，不要拖到
事后单独补。

生词表凑够之后，可以再加一个"単語テスト"tab（第 4 个 tab，跟会话/课文/生词
平级），四类题目每次全量都做一遍（不抽样），错题次数记 localStorage，下次
优先做之前错过的——`listening-page.js`/`listening-page.css` 里的 quiz 引擎是
共享的，任何页面只要在生成时传了 `--quiz-json` 就自动获得这个 tab，不用改
共享文件。**每道题必须真的答对过才算这一轮完成**——用户明确要求"保证当前
这一轮的所有题目都做对，如果没有做对的题目，就继续放出来做，直到做完"：
答错的题不计入本轮已完成数（`completed`/进度分子不变，只有错题计数(括号里
的数字)会涨），而是被重新塞进队列末尾，之后还会再考一次，一直考到答对
为止（`docs/js/listening-page.js` 的 `doCheck()`/`doneCountThisRound()`）。
这是这个共享 quiz 引擎的通用行为，改的是共享文件，不需要也不应该针对
某一课单独处理。

单词测试还会按"全部/会话相关/课文相关/其他单词"分成四个分类分别测试，每个
分类各自独立记进度和错题（不是共用一份）——分类直接复用下面第1步已经人工
核实过的例句来源（`occurrences.json` 的 `src` 字段是"dialogue"还是"text"，
`authored_examples.json` 里的词固定是"其他"），**不是拿词典基本型重新去匹配
会话/课文原文**（那样会因为活用形不一致而匹配不上，或者匹配错，见下面
"常见坑"）。这意味着**第1步的人工例句核实工作，同时决定了单词测试的题目
素材和分类结果**，不需要再单独做一遍分类。

1. **给每个生词找一个例句**——优先用会话/课文里真实出现的句子（哪怕是活用
   形，比如动词读成て形/た形/ます形都行，不强求跟词典形一模一样），真的没
   出现过的词再人工补写一句（教材程度、跟原文风格一致）。
   - 提取会话/课文纯文本（`(ja, zh)` 二元组数组）——`--data-driven` 生成的
     页面直接读同目录 `data.js` 里 `tabs[].questions[].sentences[]`，每句
     的 `tokens` 数组拼出 `text`（`t["text"] for t in s["tokens"]` 直接
     join，不用管 `kana`）、`zh` 字段就是翻译，都是结构化数据，不用正则
     从 HTML 里抠。
   - **"这个词是否真的出现在这句里"绝对不能用脚本模糊匹配后直接采信**——
     汉字词干/假名活用的自动匹配极易出现假阳性，见下面"常见坑"，唯一可靠
     做法是把候选句子全部打印出来人工过一遍确认。
   - 产出两份人工核实过的 JSON：`occurrences.json`（`{word_id: {src, idx,
     blank}}`，`src`/`idx` 指向会话/课文数组里的具体句子，`blank` 是这句里
     实际要挖空的原文片段）和 `authored_examples.json`（`{word_id: {ja, zh,
     blank}}`，人工补写的例句），两份合起来必须覆盖生词表里的每一个词、且
     不重复覆盖同一个词。
2. `python tools/listening/build_vocab_quiz_data.py vocab_words.json
   sentences.json occurrences.json authored_examples.json quiz_data.json`——
   合并成 `build_page.py` 能吃的数据，会硬检查覆盖是否完整、`blank` 是否真的
   是对应句子的子串。
3. 生成页面时加一个参数：
   ```bash
   python tools/listening/build_page.py combined.m4a enriched_combined.json docs/private/<slug> \
     --title "..." --subtitle "..." --password-hash <哈希> \
     --quiz-json quiz_data.json
   ```
4. 本地测试见下面第 7 步——重点看"填空题"的挖空是不是真的挖对了地方（不是
   挖到句子的其它部分）、"日文写中文"的词性标签（`[名]`之类）判分时有没有
   被正确剔除、"错题记录清零"按钮点了之后队列顺序是不是真的重排了、切换
   "会话相关/课文相关/其他单词"分类时题目数量对不对得上（`occurrences.json`
   里 `src=dialogue`/`src=text` 的词数 × 4，`authored_examples.json` 的词数
   × 4）、切走再切回来进度和错题数是不是真的独立保留（不会互相污染）。

**给已经发布、`quiz_data.json` 是旧版脚本生成（词条没有 `category` 字段）
的页面补上分类**：不需要原始的 `occurrences.json`/`authored_examples.json`
（这些工作文件按约定不提交，经常已经清理掉），用
`python tools/listening/backfill_quiz_category.py docs/private/<slug>/index.html`
先看预览（不传 `--write` 不会改文件），确认几个分类的数量看起来合理
（大致符合"这一课词表规模"的量级）之后再加 `--write` 真正写回。原理见脚本
文档字符串——利用"占了真实出现的词，`sentence` 字段就是页面上会话/课文里
逐字匹配得到的原句；人工补写的词，`sentence` 天然匹配不上任何一句"这个
既有的区分特征反推分类，不需要重新做一遍人工核实。

**给共享文件（`build_page.py`/`listening-page.js`/`page-renderer.js`）新增的
功能，只对"之后新生成"的课生效，不会自动回填到已经发布的课**——真实案例：
"生词填空模式借用单词测试例句"这个功能实现时是对着 l13 这一课在跑，`build_
page.py` 改完之后当场用 `build_lesson_data()` 重新生成了 l13 自己的
`data.js`（当时 l13 的 `tools/listening/work/` 工作目录还在，能直接重新
跑），l10/l11/l12 这三课当时没有一起改，`data.js` 还是旧版结构，没有
`quizSentence` 字段——用户后来点开 l12 反馈"填空模式没生效"才发现。**这类
"改的是共享渲染逻辑，但内容数据本身也要跟着升级"的功能，改完 `build_page.
py` 之后要么把每一课的 `data.js` 都重新生成一遍，要么专门写一个像 `backfill_
quiz_category.py` 那样的迁移脚本补量产课**——判断标准：如果新字段的值可以从
`data.js` 自己已有的其它数据反推出来（这次是从顶层 `quiz` 数组的 `sentence`/
`blank` 字段，跟对应生词卡片同一个 `id`），不需要原始工作目录（早已按约定
清理），写个迁移脚本批量补：`python tools/listening/backfill_quiz_sentence.py
docs/private/<slug>/index.html [--write]`，同样是先看预览、确认数量对得上
这一课生词表规模之后再 `--write`。**每次给共享文件加新功能后，记得过一遍
现存的每一课，看是不是也需要补这一步**，不能只满足于"这次改的这一课测过了"。

### 6b. 自动化校验全部音频（必须，生成页面之后、本地人工测试之前）

#### 生词音频静音裁剪（有生词表就强烈建议做，跑在 `verify_clips.py` 之前）

生词表的每个词条为了"宁可留一截静音也不敢切掉真实内容"，`align_group()`/
手工核实出来的边界天然会留比较宽的缓冲——单看某一条不算错，但整批下来
大量条目前后加起来能有好几秒静音，真实语音往往只占一两秒。真实案例
（textbook-sjp-zg-l12）：90条生词平均单条时长4.73秒，用户反馈"大部分单词
发音前后都有很多空白，上一课也这样"——这是每一课都会复现的系统性问题，
用共享工具 `tools/listening/trim_clip_silence.py` 统一收紧：

```bash
python tools/listening/trim_clip_silence.py docs/private/<slug>/audio
```

用 `ffmpeg silencedetect` 探测每个已经切好的 `seg-XXX.mp3` 文件里真正有
声音的范围，按这个范围重新裁剪、直接覆盖原文件，前后各留一点缓冲
（`--pad`，默认0.12秒）。**只能对生词条目的音频文件跑，绝对不能跑在
会话/课文的音频上**——那两类句子的跟读高亮 `t` 是"绝对时间戳 − 这句
自己的 `start`"算出来的相对值，音频文件内部 t=0 隐含约定等于这句的
`start`，直接裁掉文件开头一截会让这个约定失效、高亮全部往后飘，而
`data.js` 里存的 `t` 不会跟着变。**调用前一定要确认目录/文件范围只包含
生词条目**（`seg-<生词起始编号>.mp3` 到最后一个，不是整个 `audio/`
目录）——真实案例里第一次图省事直接对整个 `audio/` 跑，把会话/课文的
音频也裁了，补救是重新跑一遍 `build_page.py` 生成干净音频，再把生词
范围单独复制到临时目录、只对临时目录跑这个脚本，裁完复制回去覆盖。

裁剪用的静音阈值（默认 `-35dB`）是启发式参数，对个别发音轻/收尾快的
短词可能裁得比预期激进（真实案例：一个词条裁完之后从"能大致听懂"退化成
"完全听不出内容"）——**跑完这一步不能跳过下面的 `verify_clips.py`
全量重跑**，靠自动比对确认没有把真实内容裁掉，不能假设"用了阈值探测就
一定安全"。

**这条警告后来被证明还不够充分**：真实案例（textbook-sjp-zg-l13）—
`verify_clips.py` 全量跑了两轮（都显示"通过"或者只标出少数几条），用户
实际逐条听完之后还是反馈了9个词条开头/结尾发音缺失，后来排查发现
`trim_clip_silence.py` 的 `-35dB` 是**绝对**阈值，对这批录音里整体音量
偏低的词条系统性地判断失误——不是"个别发音轻的词条"这种偶发情况，是
一批词条同时受影响，而 `verify_clips.py` 的相似度比对**恰恰查不出这类
问题**：裁掉的只是词首/词尾一两个音节，转写出来的其余部分依然大体正确，
整体相似度不会掉到判定阈值以下（这跟前面"课文段首句开头被切"那条坑是
同一类"局部缺失但整体相似度撑得住"的检测盲区，只是这次发生在生词表而
不是课文句子）。**更可靠的裁剪方法**：不要依赖 `trim_clip_silence.py`
这种"整个目录用同一个绝对阈值扫一遍"的粗粒度工具，改成对每个词条单独
算一份逐帧 RMS 能量剖面（`wave` 模块读 PCM，50ms 一帧，`20*log10(rms/
32768)`），阈值取"这段自己的峰值往下 30dB"（相对阈值，不是固定的
`-35dB` 绝对值——不同词条/不同录音批次的整体音量基准可能差好几十dB，
绝对阈值对音量偏低的词条形同虚设，相对阈值才能跟着这段自己的实际响度
走）。裁剪完不能只看"这个词条自己裁得对不对"，还要留意**词条之间是不是
在原 `align_group()` 窗口内完全找不到静音可裁**——真实案例：6个词条
（退学/ブーム/ペット/愛情/外交/仕組み）用相对阈值扫描后发现窗口里几乎
没有静音（100%都判定成"语音"），这不是"这个词条运气好没有多余静音"，
而是窗口本身的位置就有问题（跟"课文段首句"那条坑同一个诱因）——对这类
"整个窗口找不到静音"的词条，要单独扩大范围重新做一次 word-level 转写+
`align_group()` 精确定位（喂假名读音），不能因为"至少没有明显的裁剪痕迹"
就假设窗口本身是对的。

`build_page.py` 每次重新生成都会用干净（未裁剪）的音频重新切一遍
`audio/` 目录，裁剪结果不会保留——**这一步要放在最后一次 `build_page.py`
之后、提交之前做**，中途如果因为改边界之类的原因又重新跑了一次
`build_page.py`，裁剪需要重新做一遍。

**相对阈值版本本身也不是终点，textbook-sjp-zg-l14 暴露了比 l13 更严重的
一次系统性翻车**：用户反馈"採用試験"这一个词条边界不准，顺着查发现整个
生词表（88条）里有**86条**的实际裁剪后时长跟 `enriched_combined.json` 记录
的原始（裁剪前）边界对不上，全量批量转写核实后，其中十几条内容被裁剪
裁没了真实音节，听写结果全是乱码（比如"服装"退化成"くそー"、"灰色"退化
成"アイロ"、"福建省"退化成"検証"，规律都是**词首辅音被切掉**）——这不是
偶发的"个别词条运气不好"，是**这一课几乎整个生词表都被裁剪工具动过手，
而且相对阈值本身对某一类词还是系统性地判断失误**：`ふ`/`は`/`し`这类
清辅音（unvoiced consonant）起头的音节，能量天然比后面的元音/浊音低不少，
如果比这个词条自己的响度峰值低超过 `--rel-db`（默认20dB），"取最长连续
响度区间"这条逻辑会直接把这段清辅音开头排除在"真实语音"之外，当成静音
裁掉——参数本身没有算错，是这类清辅音开头的词从声学上天生就会被"相对
阈值+最长连续区间"这套逻辑误判。**排查方法**（比人工一条条听音频高效
得多）：
1. 比较磁盘上每个 `seg-NNN.mp3` 的实际时长和 `enriched_combined.json` 里
   `end-start` 算出来的期望时长，对不上（`ffprobe`/`faster_whisper` 的
   `info.duration` 都能拿）就说明这条被裁剪工具动过（不代表一定裁坏，
   只代表被动过、值得重点复核）。
2. 对全部生词条目批量跑一遍转写，人工过一遍"听写结果明显不像这个词"的
   条目（不要求转写完全准确——生词表里同音字/片假名选字这类噪声本来就多，
   见下面第3点——只挑真的**听不出原词**的那些）。
3. **孤立单条 clip 转写本身不可靠，不能直接采信"转写跟原词不一样=内容
   被裁坏了"**——这一课复核时至少一半"听写异常"的条目，用带足够前后文
   （从 `combined.m4a` 上按原始边界前后各扩 1.5~2 秒切一段）重新转写一遍，
   结果都是干净、完整、正确的（比如"恩師"孤立转写成"温室"、"納期"孤立
   转写成"大きい"，带上下文都能正确转写出"恩師"/"納期"）——这类只是短
   词孤立转写的固有噪声，不是真实bug，逐条都要用带上下文的转写交叉验证
   过再下结论，不能看到"转写不对"就直接认定是裁剪坏的。
4. 确认真的被裁坏之后，**最快的修复不是重新调裁剪参数再裁一遍，是直接
   放弃这一轮裁剪、用 `recut_clips.py` 从 `combined.m4a` 按 `enriched_
   combined.json` 记录的原始（裁剪前）边界重新切**——这一课绝大多数词条
   的原始边界本身没问题（`build_page.py` 生成时"宁可留一截静音也不敢切
   真实内容"这条设计原则依然生效），真正的问题只出在裁剪这一步，回退到
   裁剪前的状态比重新调参数重裁一遍更快也更可靠。少数几个原始边界本身
   也有问题的词条（这一课是"ごく"，`align_group()` 对齐偏差），要单独用
   RMS+word-level 核实出正确边界再重切，不能跟其它词条一起被动回退。
5. **这次的教训不是"改进裁剪算法"（已经从绝对阈值改成相对阈值，仍然
   翻车），是"裁剪工具的启发式参数不管怎么调都不可能对所有词条完美，
   跑完必须无条件做一次全量内容校验，不能只做 `verify_clips.py` 的相似度
   校验"**——这条在 l13 已经写过一次，l14 的规模（86/88条被动过，十几条
   真被裁坏）证明这条警告当时没有被真正落实成"每次跑完裁剪都做"的固定
   动作，只停留在文字记录上。**以后只要跑了 `trim_clip_silence.py`，跑完
   必须做上面第1步的时长对比 + 第2步的全量转写扫描，这是固定步骤，不是
   遇到用户反馈才去做的补救措施。**

#### 全量转写比对

`build_page.py` 切完 `audio/` 目录之后（生词裁剪完的话，裁剪也做完之后），
**先跑一遍 `tools/listening/verify_clips.py`，再开始人工点开页面测试**——
真实案例（textbook-sjp-zg-l11）：
没有这一步之前，"抽查几个位置就当测完"漏掉了大量问题，用户前后反馈了四五轮
（会话第1句开头被切、第3句混进第2句、课文第3段首句被切、两个标题没声音、
生词144条里多数边界不准，中间我自己人工核对生词边界时还看错过 token 把
"彼ら"的"ら"字漏掉），每轮都还有新漏网的。**人工抽查在这个量级的数据上
（29+ 个句子/词条同时存在的教材页）不可靠，必须让脚本转写全部音频、自动
比对，人工只看报告决定信不信**：

```bash
python tools/listening/verify_clips.py \
  tools/listening/work/<slug>/enriched_combined.json \
  docs/private/<slug>/audio \
  tools/listening/work/<slug>/verify_report.txt
```

报告分 EMPTY（完全没识别到内容）/LOW_SIMILARITY（识别读音跟期望文本对不上）/
LEAD_SILENCE（开头疑似留白过长）三段，**EMPTY 和相似度很低（<0.2）的
LOW_SIMILARITY 条目几乎总是真实 bug，优先处理**；相似度中等的、LEAD_SILENCE
的需要人工判断（可能是识别噪声/词本身就有停顿，不是全都要改）。这个脚本本身
跑起来比较慢（每条都要重新转写一次，上百条数据可能要十几到几十分钟），**用
`run_in_background: true` 跑，不要卡在这一步等**。

修复任何一条时，**不要复用之前生成的、可能本身就有问题的 word-level 转写
文件去人工读时间戳**（真实案例：这次直接读现成转写文件里的 token 边界，
手滑把"彼"当成了整个"彼ら"、漏看了后面的"ら"字，把错的时间戳当成"已核实"
写了进去）——**每次修复都单独针对可疑区间跑一次新的、够宽的 word-level
探测**（`ss` 往前多留几秒当上下文，`-t` 给够长），确认清楚了再改，改完这
一条最好单独再喂回 Whisper 转写一次确认内容对得上，不要因为"已经很仔细看过
printout了"就跳过这一步复核。

改完一批之后，重新跑一遍第4/5/6步（`validate_boundaries.py` → `merge_
sections.py` → **先删 `audio/` 再** `build_page.py`），再跑一遍
`verify_clips.py` 确认新问题清空、没有引入新的（收紧边界时经常会把相邻两个
条目都往同一段音频收紧，制造出新的重叠/冲突，见"生词边界收紧"那一节），
如此反复直到报告干净，而不是改一轮就直接部署。

#### 会话/课文（有多句/多子句的题目分组）：`verify_clips.py` 之外再跑一遍逐边界 RMS 审计（必须）

`verify_clips.py` 校验的是"这一句整体转写出来的内容对不对"，**查不出"句尾
多切进下一句开头几十到几百毫秒"这类局部边界误差**——丢的只是开头/结尾一
两个音节，整句转写依然完整、相似度依然很高，不会触发任何警告。真实案例
（textbook-sjp-zg-l14）：`verify_clips.py` 全量跑了两轮、报告都干净，用户
仍然听出来好几处真实边界问题（"あれ，そんなに気を使わなくてよかったのに"
结尾多切进了下一句"いいえ"的开头、"そうかい"结尾多切进了下一句"まだ"的
开头），说明这一类 bug 只有专门针对边界本身做检查才能发现：

```bash
python tools/listening/audit_boundaries_rms.py \
  tools/listening/work/<slug>/enriched_dialogue_final.json \
  <这一段原始音频文件> \
  tools/listening/work/<slug>/audit_dialogue.txt
```

（会话/课文各跑一次，分别传各自的 `enriched_*_final.json` 和各自的原始
音频文件——传合并后的 `enriched_combined.json` 会因为坐标系是合并后的
绝对时间、但传的音频还是单段原始文件而对不上，见第5步"多段音频怎么合成
一个页面"的坐标系规则。）报告列出所有"边界正好落在一段连续语音内部"的
可疑点，**每一条都要人工核实，脚本本身的文档字符串里记录了四条真实踩过、
容易再犯的教训（不能凭百分比大小筛掉、不能凭"离哪句近"猜burst身份、
帧长不够细会把短促应答词糊掉、RMS本身也会有假阳性必须用给够上下文的
word-level转写交叉核实），核实前务必先读一遍**。这一步不是
`verify_clips.py` 的替代，是补充——两个都要跑，分别覆盖不同类型的 bug。

#### 会话/课文/生词全部边界：`audit_boundaries_quietpoint.py` 算法级检测（必须，替代"人工核实 audit_boundaries_rms.py 的可疑点"这一步里最不可靠的部分）

真实案例（textbook-sjp-zg-l15，发布后连续三轮用户反馈"尾音过长/头音
被吞"）：`audit_boundaries_rms.py` 标记出可疑边界之后，按它文档字符串
建议的"用 word-level 转写交叉核实"，多次得出错误结论——① 转写时间戳
本身系统性偏晚/偏早（同一个"それ"字，narrow window转写在不同切点全部
报成"从这里开始"，跟真实起音差了0.1秒以上都不报警）；②"两段响-静-响
的双峰"形状被误判成"两个不同句子各自的起振"，实际是同一个词内部促音
っ天然带的短暂停顿（"決して"），改错方向反而更糟。**这些坑不是这一课
独有的，是"用语言模型的时间戳去验证语言模型自己切出来的边界"这个方法
本身的结构性缺陷**——两者共享同一套偏差来源，容易互相"印证"出错误结论。

`tools/listening/audit_boundaries_quietpoint.py` 换一个不依赖转写文本的
判据：纯用能量剖面回答"这个边界之前一小段时间内，音频有没有真正安静
下来过、安静到几点几秒"，物理测量不会有语言模型那种系统性偏差。**这一步
现在是必做项，跟 `verify_clips.py`/`audit_boundaries_rms.py` 同等级别**，
而且**必须覆盖会话/课文/生词全部tab**（不只是`audit_boundaries_rms.py`
原来只覆盖会话/课文这两类"有多句题目分组"的材料）：

```bash
python tools/listening/audit_boundaries_quietpoint.py \
  tools/listening/work/<slug>/enriched_dialogue_final.json <会话原始音频> \
  --report tools/listening/work/<slug>/quietpoint_dialogue.txt
python tools/listening/audit_boundaries_quietpoint.py \
  tools/listening/work/<slug>/enriched_text_final.json <课文原始音频> \
  --report tools/listening/work/<slug>/quietpoint_text.txt
python tools/listening/audit_boundaries_quietpoint.py \
  tools/listening/work/<slug>/enriched_vocab_final.json <生词原始音频> \
  --report tools/listening/work/<slug>/quietpoint_vocab.txt
```

（跟 `audit_boundaries_rms.py` 一样，传各自的 `enriched_*_final.json` +
各自的原始音频，不要传合并后的 `enriched_combined.json`。）

**生词表尤其容易大规模命中，不是例外情况**：真实案例里 104 个生词零
间隔首尾相连，一次扫描 103 个内部边界，**96 个都命中**（多数偏晚
0.1~0.3秒，少数超过40dB的剧烈跳变）。根因是 `refine_boundaries.py` 的
`biased_split_time()` 计算切分点时，虽然设计上"偏向让下一个词/句多分到
停顿"，但计算基准（前一个词/句的 Whisper 词级结束时间戳）本身经常系统性
偏晚——这不是这一个函数的 bug，是"相信 Whisper 自己给的词尾时间戳"这个
前提在生词表这种零间隔连续朗读材料上格外不成立（自然停顿本来就短，
系统性偏差占比更明显）。**任何用 `align_group()` 对齐过的生词表都可能
受影响，不只是这一课**——以后每一课生词表生成完，这一步都不能省，不能
假设"这次的语速/录音条件跟上次不一样，应该没事"。

命中之后可以放心 `--fix` 批量修正（不用像手工改边界那样逐条先人工核实
再动手）——新边界=独立测量出的真实安静点+0.02秒缓冲，这个新边界**只
可能落在已经确认安静的位置**，不可能反过来切进上一句/上一词还在响的
真实内容里，最坏情况只是多给下一句/下一词留了一点点无害的静音缓冲，
不会制造新的内容丢失，所以批量修正的风险跟"人工估一个大概值就动手"完全
不是同一个量级。`--fix` 只改 `start`/`end`，句子（不是生词）如果带
`char_times` 不会跟着重算，改完还是要照常走 `recut_clips.py` +
`patch_sentence_tokens.py`（生词条目没有 `char_times`，只需要
`recut_clips.py`）。

**改完不能只信这个工具自己报告"改好了"，还要做下面这一步终验**：

#### 拼接相邻已发布 clip 整体转写——目前发现的最可靠终验方法

真实案例（textbook-sjp-zg-l15）：修复过程里反复出现"以为改对了、其实
方向错了或者幅度不够"的情况，包括同一处边界被连续判断了三四轮才收敛。
最终稳定下来靠的是同一个方法：**把两个相邻的、已经发布的 `seg-NNN.mp3`
文件直接拼接（`ffmpeg -f concat`）成一个文件，整体喂给 Whisper 转写**，
不依赖任何"猜边界在哪、猜这段该算哪一句"的假设——转写结果里，下一句
的第一个词出现在拼接后时间轴的哪个位置，直接跟"上一个clip自己的真实
时长"（`ffprobe -show_entries format=duration`，不要用自己写的
`ffmpeg -i` 探测脚本，见下面这条坑）比较：如果那个词出现的时间点早于
上一个clip的真实时长，说明这个词的开头被上一个clip偷走了一部分。这个
方法比"孤立转写单个clip"（短clip转写本身不可靠，详见"常见坑"）、也比
"narrow window转写猜起始点"（同一个词在不同窗口切法下能给出相差0.1秒
以上的不同起始时间估计）都更可信——因为它测的是"已经发布的真实文件"，
不是"某种假设下重新切出来的窗口"。**generate 页面之后，凡是
`audit_boundaries_quietpoint.py --fix` 批量改过的边界，都应该抽样用
这个方法做终验**（不用每一处都测，测覆盖到修改最密集的几个题目分组/
生词表分段即可），而不是只信任自动化工具自己的报告。

**配套的一个工具坑**：自己写的"用 `ffmpeg -i` 读 stderr 里的 Duration
行解析时长"的方法，比 `ffprobe -show_entries format=duration` 系统性
偏大约0.02~0.04秒（mp3容器本身的编码器延迟/填充导致，`ffmpeg -i` 报的
是容器层时长）。真实案例：这个偏差一度让排查者误以为某处边界还差
0.04秒没修干净，差点对一个已经修对的边界又多改一次——**凡是要精确
比较"clip真实时长"的场合，一律用 `ffprobe -show_entries format=duration
-of default=noprint_wrappers=1:nokey=1`，不要自己写 `ffmpeg -i` 解析
stderr 的土办法**。

### 6c. 做了单词测试 tab 的话：校验 quiz 里的 id 跟真实音频对不对得上（必须）

```bash
python tools/listening/verify_quiz_ids.py docs/private/<slug>/index.html
```

（`--data-driven` 生成的页面会自动检测同目录的 `data.js` 并从里面读数据校验，
`--fix` 也会正确写回 `data.js` 而不是 HTML——两种页面格式都不用额外传参区分。）

`verify_clips.py` 校验的是音频文件本身的内容对不对，**校验不了"单词测试
tab 引用的是哪个音频文件"这一层数据链接**——単語テスト的"听音频写假名"
题型靠 `quiz_data.json` 里每个词条自己的 `id` 拼 `audio/seg-{id}.mp3`
（见 `listening-page.js` 的 `audioSrcFor()`），这个 `id` 必须跟"生词"tab
里同一个词自己卡片用的 `id` 完全一致，否则播放的是完全不相关的另一段
音频（真实案例 textbook-sjp-zg-l11：**全部 144 个生词条目的 `id` 都比
真实音频编号小了 35**——`vocab_words.json` 喂给 `build_vocab_quiz_data.py`
时，`id` 字段用的是"生词自己从1开始编号"，没有加上前面会话+课文占用的
编号偏移，导致单词测试里"听音频写假名"这一整类题目播放的几乎全是错误
内容，用户点开真的听了才发现。这个 bug **流水线每一步单独看都不会报错**
——`build_vocab_quiz_data.py` 只检查 occurrences/authored 覆盖是否完整、
`blank` 是不是子串，不检查 `id` 对不对得上最终生成的音频文件；`verify_
clips.py` 检查音频内容本身没问题（因为它压根不知道"这段音频还被单词测试
引用了、引用得对不对"）。**只有真的连起来交叉比对才能发现，必须作为独立
一步跑，不能假设"前面每一步都没报错=最终结果没问题"**。

这个脚本按文档顺序比对"生词 tab 里每张卡片真实用的音频编号"和"quiz_data
里按顺序排列的词条"，不依赖固定偏移量（不同课偏移量不一样，取决于这一课
会话+课文一共多少句）也不按文字匹配（同一课里可能有重名词条，比如"その後"
出现两次、读音还不一样，按文字查字典会被这类重名搞乱，按文档顺序位置对应
才可靠）。命中不一致时，`--fix` 直接把算出来的正确 `id` 写回页面，只改
`id` 字段，`category`/`sentence`/`blank` 不受影响。**这一步在生成
`--quiz-json` 页面之后必须跑，是跟 `verify_clips.py` 同等级别的必做项**。

### 6d. 校验"填空"练习模式：`blanks` 字段里的每个空是不是这句原文的真实子串（必须）

```bash
python tools/listening/verify_blank_answers.py docs/private/<slug>/index.html
```

（同样自动检测 `data.js`，两种页面格式通用。）

"填空"练习模式挖哪几个空、正确答案是什么，**直接来自第4步 `blanks` 字段**
（`--data-driven` 页面原样放进 `data.js` 每句的 `blanks` 数组，旧式页面渲染
成 `.seg-card` 的 `data-blanks` 属性），不是靠
正则从 `notes` 里猜——这是这个 skill 早期版本踩过一连串坑之后改的架构：
最早直接从 `seg-notes` 的「...」引号里正则抓文字当挖空目标，猜不出两类
场景（notes 写抽象占位字母比如"AでもBでも"、notes 引用词典型但句子里是
活用形），而且猜错了完全不报错，只有打开填空模式点开每一句才会发现，
一课几十句语法点人工挨个点效率很低。现在 `blanks` 是内容作者写 enriched.json
时显式指定的原文子串，不存在"猜错"这回事，**唯一可能出的问题是打字时手误**
（多打/少打了一个字，导致这段文字在原文里根本找不到——`listening-page.js`
运行时会在控制台打 warning，但不会有任何界面提示，这个空会悄无声息地不
出现，没人会主动去翻控制台）。这个脚本批量检查每张卡片 `data-blanks` 里
每一条是不是这句 `seg-ja` 纯文本的真实子串，生成/手改完 `blanks` 之后跑
一遍，不用打开浏览器逐句核对。

报告格式很简单——`OK` 就是全部条目都能精确匹配；报出来的每一条都需要改
`blanks`（对着报告里打印的"这句原文是……"，把打错的地方改成原文里真实
出现的那段文字），没有"不一定是bug、人工判断要不要紧"这种模糊地带（旧版
脚本有这个问题，因为旧架构本身就有"合理但不精确匹配"的灰色情况，新架构
下不存在，报出来的就是真的错了）。

**这一步在生成页面（不管有没有做单词测试 tab，只要给任何一句写了 `blanks`
字段就该跑）之后必须跑，是跟 `verify_clips.py`/`verify_quiz_ids.py` 同等
级别的必做项**。

### 6e. 校验生词表 `zh` 字段有没有混入词条原文（必须）

```bash
python tools/listening/verify_vocab_zh.py docs/private/<slug>/index.html
```

生词表抄写截图时，"词条+释义"两栏并排的格式（尤其是"〜"开头的语法后缀
类词条）容易把整行（含左边的词条原文）一起抄进 `zh` 字段——真实案例
（textbook-sjp-zg-l12，用户自己在编辑模式里发现并改正）："〜問目　第〜题，
第〜个问题"这行，`zh` 该只保留"第〜题，第〜个问题"，结果把左边的"〜問目"
也一起抄了进去，变成"〜問目 第〜题，第〜个问题"；"〜以内　〜以内"这行更
明显——`zh` 直接抄成了跟词条本身完全相同的"〜以内"，等于没有真正的中文
释义。这个脚本检查"`zh` 以词条原文开头、后面还紧跟着一段明显不同内容"
这个模式，生成/手改完生词表之后跑一遍。

**跟"`zh` 完全等于词条本身"（比如"〜量"这条的 `zh` 就是"〜量"）不是同一
回事，后者是正常情况**（教材对这类语法后缀本来就没有额外中文释义，脚本
不会报告）——**只有"开头是词条原文、后面还跟着别的内容"这种明显是抄录时
多带了一段的情况才会被标记出来**，报出来的每一条基本可以确定是真的抄错了
（去掉开头重复的词条原文那一段，只留后面真正的释义）。

### 6f. data-driven 页面自带一个网页端编辑模式，用户可以自己校对+改内容

`--data-driven` 生成的页面（`docs/js/edit-mode.js`/`edit-mode-restore.js`，
跟 `page-renderer.js` 一样是共享文件，任何 `--data-driven` 页面自动带这个
功能，不用额外配置）自带一个轻量编辑器：设置面板里有个"✎ 编辑模式"开关，
打开后每张卡片右下角出现一个 ✎ 小图标（单独 stopPropagation，不影响点击
卡片本身播放音频——跟读/默写/填空任何模式下都能一边听音频校对一边编辑），
点图标弹出一个 JSON 文本框，显示这句的 `speaker`/`speakerKana`/`tokens`/
`zh`/`notes`/`blanks` 字段（`id`/`audio` 不可编辑，避免手滑改坏结构性
字段），改完点"应用"当场生效（直接改的是内存里的 `window.LESSON_DATA`，
同时记一份到 localStorage，刷新页面/下次打开还在）。设置面板里还有"导出"
按钮，把当前（带着所有修改的）`LESSON_DATA` 整个下载成一份新的 `data.js`。

**这个功能是给用户自己校对内容用的，不是这个 skill 生成流程要做的事**——
生成页面时不用管这个，它是共享文件自带的能力。用户如果说"我在页面上改了
内容，导出了一份 data.js 发给你"，直接用这份文件替换 `docs/private/<slug>/
data.js`，跑一遍 `git diff` 看清楚具体改了哪几句、有没有意外改动，确认
没问题（尤其看一眼 `verify_blank_answers.py`/`verify_quiz_ids.py` 还过不
过）再提交，不用重新走生成流程。

## 常见坑

- **两个连续朗读、中间没有真实停顿的词，边界之间可能出现一段"两边都不属于"
  的死区，卡掉后一个词的开头**——真实案例（textbook-sjp-zg-l10，生词表
  "たっぷり"/"つかる"）：真实录音里"たっぷり"读完紧接着就是"つかる"（word-level
  转写显示两者完全衔接，没有间隙），但当初简单按 Whisper 粗 segment 1:1 对应
  分配的时间戳是"たっぷり"[159,161]、"つかる"[162,164]——161到162这一整秒
  两边都没占到，而"つかる"真实内容其实从161.34就开始了，等于"つかる"这段
  音频从162.0开始切，白白丢了开头0.66秒。**这跟前面"内部切分点卡在词中间"
  不是同一种坑**：那种是切分点位置本身估错了（比如银湯/戦闘那次），这种是
  两个粗 segment 之间本来就有"缝隙"（不是重叠，是空档），而真实语音里这两个
  词根本没有停顿——**排查信号**：如果 A 词的 end 和 B 词的 start 之间有明显
  间隔（比如1秒），但 A、B 是简单朗读的词表条目（不像句子之间会有自然停顿），
  值得怀疑这个"间隔"是不是真实存在，还是粗 segment 切分本身留下的空档，
  用 word-level 转写核实这两个词之间到底有没有真实停顿，没有的话把边界重新
  对齐到词真正的分界处。
- **恢复被删除的工作目录数据时，只重建"骨架"（重新转写+重新跑 refine/
  validate）是不够的，之前每一次手工排查后的具体修正值也必须逐一重新应用，
  漏一个就会让某处的问题"复活"**——真实案例：`tools/listening/work/<slug>/`
  按约定删除后，重新走一遍转写+`build_vocab_from_wordlist.py`+`merge_
  sections.py`+`build_page.py`能正确重建出"骨架"，但骨架本身不包含之前手工
  核实过的边界修正（这些修正是在 refine_boundaries.py 跑完之后、脚本能自动
  产出的结果之外，靠 word-level 转写另外核实、手动改时间戳补上的），重建时
  凭记忆挨个重新应用这些修正，容易漏掉某一处（真实案例漏了课文"また銭湯
  といって"那句已经修过的边界，导致这句音频又变回了8.15秒的错误版本）。
  **补救办法**：重新生成完页面之后，不要只抽查几个位置就当作完事，用
  `git show HEAD:<音频相对路径>` 把新生成的每个音频文件跟上一次已提交的
  版本逐个比时长，只有真正打算改的那几个位置应该显示为"不同"，其余应该
  完全一致——这一步能可靠揪出"重建时漏应用了某个旧修正"，比凭记忆自查靠谱。
- **句子内部的切分点（不是段落/场景的外边界）也会犯"多切/少切半个词"的错，
  且这个错法跟外边界裁切是两种不同的病因，各自的修法也不一样**——真实案例
  （textbook-sjp-zg-l10，用户实际听出来的问题）：课文里"銭湯"这个词在同一段
  里反复出现，Whisper 每次都稳定地误听成"戦闘"（读音一样せんとう，汉字不同）。
  `align_group()` 靠 `difflib.SequenceMatcher` 按**字符**对齐"期望文本"（真实
  汉字"銭湯"）和"识别文本"（误听的"戦闘"），这两个字符串在"銭湯"出现的位置
  必然对不上（字都不一样），对齐算法在这些位置的把握变弱，切分点就可能算
  偏——真实表现是把"戦"（銭湯的前半个音）错分给了上一句，下一句从"闘"（后半
  个音）开始，听感上是"上一句结尾多出半个字的杂音、下一句开头缺了半个字"。
  **这跟前面"段落外边界窗口开早了/晚了导致整段开头被吞"是两个不同的坑**：
  外边界坑是"窗口本身看不到那段音频"，`refine_boundaries.py` 自己的对齐质量
  提示（"0 fallback"）完全查不出来；这个内部切分点的坑是"窗口能看到，但因为
  文字不匹配算偏了一点点"，同样不会被"0 fallback"提示揪出来（对齐整体覆盖率
  仍然够）。**排查方法**：怀疑某处内部切分点不准时，把这道题的完整原始音频
  （不是精修时那个按 group 截出来的小窗口，是这一段的完整音频文件）整个跑一遍
  word-level 转写（`WhisperModel(...).transcribe(audio, word_timestamps=True)`），
  在可疑边界附近找"相邻两个词之间间隔明显变大"的自然停顿（比如间隔 ≥0.35秒），
  把这个停顿的中点当作订正后的边界——**不要**试图用"文字内容匹配"去找正确
  位置（这道题的文字本来就是导致算法出错的根源，跟着文字匹配走会重蹈覆辙），
  纯粹按"语音本身哪里有停顿"来判断更可靠。
- **发现类似问题后，不要用同一个固定阈值/固定缓冲量的规则批量"自动修复"**——
  真实教训：写过一版"句尾最后一个字符时间戳比倒数第二个跳变超过0.8秒，就把
  边界收回到倒数第二个+0.3秒缓冲"的通用脚本，套到已经用真实转写核实过的一处
  （正确答案是往回收约2秒）上，算出来的值反而会把这句自己最后一个词的尾音也
  切掉——同一类"跳变"symptom 背后每处的"真实跳变量"完全不同（有的该收回0.3
  秒，有的该收回2秒以上），没法用一个固定公式套所有位置，每一处都得找真实的
  自然停顿位置来定，或者至少要跟"离旧边界最近的自然停顿"这类基于实际语音
  数据的方法比对，不能凭经验数字瞎猜。
- **`refine_boundaries.py`/`validate_boundaries.py` 在 Windows 上打印非日语
  汉字（简体中文）的 mondai/question 标签会崩溃**——这两个脚本原本没有
  `transcribe.py` 那样的 `sys.stdout.reconfigure(encoding="utf-8")` 保护，
  Windows 控制台默认 cp932（Shift-JIS）编码，日语假名/汉字（比如"問題1"/
  "1番"）大多能编码，但简体中文特有字形（比如"话"的简体写法，繁体/日语写作
  "話"）不在 cp932 字符集里，一旦 mondai/question 标签用简体中文（这个
  skill 的 tab 标签"会话"/"课文"/"生词"就是简体中文，跟 JLPT/会议录音那两个
  skill 一直用的日语标签"問題1"/"会議"不一样），`print()` 到控制台直接
  `UnicodeEncodeError` 崩溃，即使对齐计算本身没问题——已经在两个脚本里补上
  跟 `transcribe.py` 一致的 UTF-8 stdout/stderr reconfigure，一次性修好，
  以后同类中文标签不会再触发。
- **截图导出文件名的时间戳顺序不等于阅读顺序**——见上面第1步，滚动截屏工具
  可能因为截了两张离得很近/回滚重截等原因导致文件名序号跟真实滚动位置不同步，
  排完序一定要跟第2步的 Whisper 粗转写做一次内容连贯性交叉验证，不要只信
  文件名排序。
- **滚动截屏也可能整条漏拍——不只是顺序错，是内容真的缺了一条**，比上面
  那条"顺序错位"更隐蔽，因为总数对不上会被发现，"漏拍+总数刚好还是对得上"
  不会。真实案例（textbook-sjp-zg-l10）：生词表"壷"和"お/ご〜申し上げる"
  两张截图之间，滚动截屏漏拍了中间的"試着する"这一条——用户听录音发现"壷
  后面的词对不上"才暴露出来。这次为什么"数量校验"完全没查出来：Whisper
  分块转写在块边界上把"試着する"和"お/ご〜申し上げる"两个词的音频粘连转写
  成了一个 segment（表现是这个 segment 长达7秒，明显长于其它同类词条的
  1~3秒——这个异常在当时就被注意到了，但没能确定原因，只归因于"可能是
  '试穿'这类词本来就要读两遍示范用法"这种合理化解释，没有深挖），这一个
  过长 segment 让"截图抄下来的词数"和"Whisper 识别到的 segment 数"凑巧还是
  1:1 对应，掩盖了"其实少抄了一个词、多算了一个 segment"这个事实。**排查
  信号**：`enriched.json` 里如果有某个词条的时长明显超出同类词条（比如生词
  表里大多数词 1~4秒，突然冒出一个 7 秒的），先怀疑"这个 segment 是不是
  实际包含了不止一个词的音频"，而不是先假设"这个词本来就要读比较久"——
  真做过一次这段音频的 word-level 转写核实之后往往能看清楚（真实案例里
  转写结果是"し・ちゃ・く・する"，第一次看没认出来是"試着する"，回头再看
  才对上）。发现确实漏了词之后，找截图来源（用户/教材）确认这个词的读音和
  释义，插入到正确位置，把原来那一个粘连 segment 按真实词级转写重新切开
  （而不是简单假设"数量对得上就没问题"）。
  **补录：插入漏掉的词之后，第一次修复仍然不够——用小窗口（9秒）重新转写
  时只捕捉到了"お、ご"两个字就结束，把"お/ご〜申し上げる"的 end 定在了
  82.0，实际这个词一直说到 86秒才真正结束（"もうしあげる"本身就读了将近
  4秒）。窗口切得太小、师傅刚好在窗口边缘截断了后半个词，得到的仍然是错误
  边界——这个错误边界又连锁导致后面"札幌/片道/光/合図する/算数/解く/表示/
  ローマ字/満足"一串词的时间槽全部错位，用户听录音又发现了一次（"这个单词
  被分成了三段…导致后续单词和音频全部错位"）。**教训：核实一个可疑边界时，
  转写窗口要留够余量，宁可切宽一点（比如20~40秒）也不要卡着"预期这个词
  应该在哪结束"来切，卡太紧本身就会把真实边界切在窗口外，产出的仍然是
  错误数据，而且这次的错误看起来"已经修过了"，更容易被当成解决了**。同一
  次深挖里，还顺带发现"お世話になります"（另一个原始重叠 segment 的"第二
  个词"，之前只做过 `validate_boundaries.py` 的重叠裁剪、没有单独做过
  word-level 核实）也有类似但没那么严重的偏差（真实只有2.88秒，不是6秒），
  同样用词级转写核实修复了。**这次的经验是：原始5对重叠 segment 里"第二个
  词"都属于同一类风险最高的位置（重叠说明 Whisper 在那附近的分块转写本来
  就不可靠），仅凭一次"数量对上了""时长看起来还算合理"的检查不足以确认
  它们真的正确，值得针对这几个位置都单独做一次 word-level 核实**——精确到
  "生词表里每一条都要单独核实"目前没有做到，这是已知的覆盖局限，后续如果
  再发现类似问题，同样按这个思路（宽窗口 word-level 转写 + 找自然停顿）
  排查。
- **中文旁白/场景说明不能当成 `.seg-card`**——默写/填空模式的实现假设了"每个
  `.seg-card` 一定有 `.seg-ja`"，硬塞一个没有日语原文的卡片会在这两个模式下
  表现异常（默写模式会要求用户"听写"一句空白/占位文本）。
- **生词条目不需要 `refine_boundaries.py`，但仍然要跑 `validate_boundaries.py`
  ——这是两件不同的事，漏了后者会真的做出有问题的音频**。单词粒度的逐字符
  跟读高亮价值很低（一个词通常只有一两个音节，高亮意义不大），而 `refine_
  boundaries.py` 对每个 question 分组要重新跑一次 word-level 转写，几十上百
  个单词逐一处理会明显拖慢流程，所以直接用 Whisper 粗转写的 segment 时间戳
  （去掉幻觉 segment 后按顺序一一对应）就够用——**这部分判断没错**。但真实
  案例（textbook-sjp-zg-l10，用户实际听出来的问题）：`transcribe.py` 按固定
  时长分块转写，相邻两块之间有重叠，个别词恰好卡在块边界上时，会被相邻两块
  各自转写出一个 segment、时间戳互相重叠（比如"壷"[74.0,77.0] 和紧接着的
  "お/ご〜申し上げる"[75.0,82.0] 重叠了2秒）——生词表直接用这些粗 segment
  时间戳，从没跑过 `validate_boundaries.py` 的"相邻句重叠就前向裁剪"这一步
  （这一步不依赖 `refine_boundaries.py` 有没有跑过，只要有 `start`/`end`/
  `mondai` 字段就能跑），重叠部分让"壷"的音频尾巴多播了"お"的开头一截，
  "お/ご〜申し上げる"的音频开头也带了"壷"的尾音——真实案例里5个词条都踩了
  这个坑（`python validate_boundaries.py enriched_vocab.json enriched_vocab_
  fixed.json` 一条命令就修好了全部5处，`build_vocab_enriched.py` 里少跑了
  这一步是纯粹的疏忽）。**跳过 `refine_boundaries.py` 不等于可以跳过
  `validate_boundaries.py`，生词表的 `enriched.json` 组装完之后一定要过一遍
  `validate_boundaries.py`（哪怕跳过它自己就有的对齐/语速/句尾跳变那几项
  高级检查用不上，光是"重叠裁剪"这一步就值得跑）**。
- **多段音频不能直接把 `enriched.json` 时间戳按比例硬凑**——见上面第5步，
  必须先在各自本地坐标系里跑完 `refine_boundaries.py`，再统一平移合并，
  顺序不能反。
- **生词条目按顺序 1:1 对应 Whisper segment 之前，一定要先核对"顺序本身对
  不对"，不能只信截图的视觉排版顺序**——真实案例（textbook-sjp-zg-l10）：
  截图里"お/ご〜申し上げる"这一条视觉上排在"◆生词表2"标题**之前**，我据此
  把它归到了生词表1的末尾；但实际录音里这个词是排在"壷"**之后**才念的（跟
  生词表2的其它练习词混在一起）。因为总数凑巧还是对的（99词对99个非幻觉
  segment），这个位置错误不会在"数量校验"那一步暴露，而是从插错的那个位置
  开始，后面所有词条的读音/含义跟音频整体错位一位，人耳一听就能发现"这个词
  怎么读的是别的词"。**核对方法**：把 ground-truth 词表按顺序跟 Whisper 粗
  转写逐条打印对比（不只是数量，是每一条的内容），碰到明显对不上的位置就是
  排序错了，回去核实真实顺序——不能只做一次"总数相等就当排序没问题"的粗检查。
  **这条现在不用完全靠人工了**：`build_vocab_from_wordlist.py` 会自动把每条
  词的读音跟对应 segment 识别出来的读音比相似度，差得远的位置会打印警告（按
  读音比不按字面比，"社内"被听成"车内"这类同音异字不会被误报）——但这只是
  缩小人工复核范围的辅助信号，不是完全替代人工过一遍，"时长正常但内容错位"
  这个坑，就是当初没做这层校验时漏掉的真实案例（见下一条）。
- **"时长正常"不代表"内容对得上"，生词表 segment 的内容本身也可能错位到了
  别的位置，纯靠"时长是否异常"这一条检查完全抓不出来**——真实案例
  （textbook-sjp-zg-l10，用户听出来的问题）：ビタミン/立て直す/体重/相当/
  天才 这5个词条最终的音频时长都在正常范围（1~2秒），不像"粘连"那样偏长，
  但内容其实是错的——体重对应的音频实际内容是"20"、相当是静音、天才是
  "はい"（都是从别的位置错位过来的），另外两个是真实词的开头被切掉了一点。
  这批词条当初是用 `build_vocab_from_wordlist.py` 的简单位置 1:1 对应生成的，
  没有做过内容校验，问题从生成那一刻就存在，一直没被发现，直到用户实际点开
  这几个词才暴露。**排查方法**：怀疑某个词条对不上时，把当前部署的
  `seg-NNN.mp3` 单独喂给 Whisper 转写一遍，看识别出来的内容跟词条本身像不
  像（这次直接转写发现内容离谱到跟词表完全不沾边，一眼就能确认是错的，不用
  纠结"是不是听感问题"）；确认真的错了之后，回到原始生词朗读音频（不是切
  好的小片段）做一次干净的分段转写（`vad_filter=False`、不给 word_timestamps
  的句子级转写就够，比逐字符 forced-alignment 更抗噪声），按预期词序对出
  正确的时间段重新切一次，切完同样喂回 Whisper 转写确认内容对上了再部署。
  **后续预防**：`build_vocab_from_wordlist.py` 现在会自动做读音相似度校验
  （见上一条），这类"内容错位但时长正常"的问题以后会在生成阶段就被打印出来
  提醒复核，不用再等用户实际点开才发现——但这次的5个词条是历史遗留数据（
  当初生成时还没有这层校验），已经手工核实修复，不需要再处理。
- **段落/场景分组的外边界如果是手工估的时间点（不是直接抄 Whisper 某个干净
  segment 的边界），必须留足安全冗余，否则会产生"开头几个字被裁掉"的静默
  裁切 bug，而且这个 bug **不会**被 `refine_boundaries.py` 的"0 questions
  used proportional fallback"这类质量提示暴露出来**——真实案例（同上）：
  课文第4段（"また銭湯といって…"）的组边界（第一句起点）是我在"きている
  また銭湯といって安い値段で入浴"这个跨两句的 Whisper segment 里手工目测
  切分出来的，估早了将近2秒；`refine_boundaries.py` 对第4段单独重新转写时，
  这2秒真实内容根本不在它拿到的音频窗口里，所以不管对齐算法多好都不可能
  把边界定位到窗口外——alignment 质量本身没问题（照样显示"0 fallback"），
  问题出在窗口本身给窄了。判断一个外边界是不是"直接抄了某个干净 segment
  的边界"（安全）还是"手工在合并 segment 里估的分割点"（有风险）：凡是后者，
  一律往外多留 1~2 秒冗余（往前挪起点/往后挪终点），冗余不会带来副作用（
  `refine_boundaries.py` 的对齐算法会自动跳过窗口里不属于这道题的多余内容），
  但冗余不够会导致这类静默裁切、只能靠人工试听发现。
- **改完时间戳/文本、重新跑 `build_page.py` 生成同一个输出目录之前，必须先
  删掉旧的 `audio/` 目录**——`build_page.py` 的 `cut_segments()` 发现某个
  `seg-NNN.mp3` 已经存在就直接跳过重切（这是为了正常流程里"只改翻译/笔记不
  改时间戳"时不用重新切一遍音频的优化），但这意味着**哪怕 `enriched.json`
  里的时间戳已经全部修正，已经生成过的旧音频文件也不会刷新**——页面会呈现
  "文字/翻译是新的，但点开一听音频还是旧的、对不上"这种更隐蔽的错误（本身
  在检查 HTML 文本内容时完全看不出来，只有实际播放或者比对音频文件时长才能
  发现）。每次因为修复边界/重新排序而重新跑 `build_page.py` 时，先
  `rm -rf docs/private/<slug>/audio` 再跑，或者确认这是第一次生成（目录还
  不存在）。
- **pykakasi 对罕见组合/熟字训读音容易读错**——比如"女将"整词读おかみ（不是
  "女"+"将"各自的音读拼起来）、"スケジュール表"里的"表"该读ひょう（孤立
  出现的"表"最常见读音是おもて）、"その日"里孤立的"日"该读ひ（不是にち）、
  "20日"是不规则读法はつか（不是にじゅうにち）、"入っ"（五段动词"入る"的
  促音变词干）pykakasi 有时会输出无效假名"いっっ"。**教材场景比 JLPT 真题/
  会议录音更容易踩到这类坑**，因为生词表本身就是在教这些容易读错/需要专门
  记忆读音的词，读错的展示效果尤其糟糕（教读音的地方读音本身是错的）。修法
  分两种：① 生词表条目——`vocab_words.json` 里给这个词条加一个 `"kana"`
  字段存正确读音，`build_vocab_enriched.py` 里的 `furigana_for()` 会优先用
  这个字段而不是让 `ruby_html()` 自动转换；② 会话/课文里的普通句子——`ruby_
  html()`（`build_page.py` 里）现在有一个手动订正表（`_TOKEN_READING_
  OVERRIDES_BY_PREV`/`_TOKEN_READING_OVERRIDES_UNCONDITIONAL`），按"上一个
  token 是什么+当前 token 原文"或者"当前 token 原文本身"匹配，命中就覆盖
  `rt` 显示的读音（不改 `orig`，不影响跟读高亮的字符时间戳对齐）——遇到新的
  误读组合，往这个表里加一条就行，不用碰算法本身。**这个表是全站共用的**
  （所有 29+ 个页面都调用同一个 `ruby_html()`），加错误覆盖会影响所有页面，
  加之前确认清楚触发条件不会误伤其它上下文（比如"表"的覆盖限定在紧跟在
  "スケジュール"后面才生效，不是无条件覆盖每一个孤立的"表"字）。
- **人/月/日/方/上/下/中/分/時/気/家/物/目/手/口/力/名/音/色/間 这类极常用单字，
  训读/音读/量词读音随上下文剧烈变化，是 pykakasi 误读的重灾区，光靠"生成完
  页面人工通读"很容易看走眼漏过**——这些字每一课都反复出现好几遍，读多了容易
  审美疲劳，而且错误往往不影响整体阅读理解（读错一个字不妨碍看懂整句中文
  翻译），人工校对时注意力天然会往"这句翻译对不对"上偏，而不是逐字核对读音。
  真实案例（textbook-sjp-zg-l11）：「同世代の人」的"人"（独立名词，该读ひと）
  被 pykakasi 默认读成にん（数量词/复合词读音，比如"三人"才该读にん）；
  「1か月」的"月"（时长量词，该读げつ）被默认读成がつ（日历月份读音，比如
  "1月"才该读がつ）。这两条被用户实际听页面发现后才修复，说明"生成后人工
  通读"这一步对这类坑基本无效。**应对方法有两层**：① 事后发现了就照上面的
  方式加订正表条目；② **更重要的是主动扫描，不要等用户/自己读页面才发现**——
  新增了 `tools/listening/audit_furigana.py`，把 `enriched.json` 里每一句/
  每个生词过一遍，凡是命中"高危字表"（脚本里的 `DANGER_KANJI`，就是这条列出
  的这些字，不是穷举，遇到新的常见误读字往里加）的字都打印出来（带前后
  token 上下文），生成一份几十行的短报告，人工扫一遍确认每条读音对不对，
  比读整页渲染结果找错快得多也不容易漏——**在跑 `build_page.py` 之前，
  `enriched.json`（会话/课文/生词）都应该先过一遍这个脚本**。这个脚本内部
  区分了两种读音来源（不能一律重新跑 pykakasi 了事，见脚本文档字符串）：
  有 `char_times` 的句子（`ruby_html()` 现场渲染）——重跑一遍跟 `ruby_html()`
  完全同款的分词+订正表逻辑；没有 `char_times` 的生词条目（直接用 `enriched.
  json` 里已经存好的 `furigana` 字段，可能来自词表 `kana` 字段的人工订正）
  ——直接从这个字段里正则抠出实际读音，不重新计算，否则会对"已经人工订正过、
  实际渲染是对的"生词条目产生假阳性（真实案例：生词"〜力"当初已经人工订正成
  读りょく，脚本如果无脑重新跑 pykakasi 会得到默认的ちから，误报"读音不对"，
  实际页面渲染的就是订正过的りょく，根本没问题）。
  **"人"这个字后来又证明了一次"窄规则不够用"**：最初只加了 `("の","人")→
  "ひと"` 这一条固定搭配（只覆盖"の"单独成词紧跟在"人"前面的情况，比如
  "同世代の人"），但 grep 已发布页面时发现 `dingliehui-260714` 的"他の人"
  也是同一个 bug——这条没被窄规则覆盖，因为 pykakasi 把"他の"合并成了一个
  token，"の"根本不会单独出现；顺着这个思路人工核对 `textbook-sjp-zg-l10`
  又额外找到4处（"いる人""する人""のない人""忙しい人"，前面接的是动词/
  形容词连体形，压根不含"の"）。**这说明"人"的正确读音规律其实是通用的**：
  孤立成词的"人"（不是"外国人""成人""大人""人気"这类已经被 pykakasi 自己
  合并成多字 token 的复合词）几乎总是该读ひと，只有紧跟在数字后面表示数量
  （"3人""20人"）才该读にん/じん——于是把这条从"字典里加案例"改成了
  `build_page.py` 里的一个通用函数 `_resolve_hira()`：`orig=="人" 且
  prev_orig 不是数字 → ひと`，一次性覆盖所有这些前置形态，不用再遇到一种
  新的"人"前面接的词形就加一条。`audit_furigana.py` 也同步改成调用同一个
  `_resolve_hira()`（而不是自己再维护一份判断逻辑），避免两边的读音判定
  逻辑长出分歧。**这个订正逻辑是全站共用的——改完之后要意识到影响面不止
  当前这一课**：这次除了当次在改的课，还顺手 grep 了全站已发布页面，确认
  `dingliehui-260714`（2处）和 `textbook-sjp-zg-l10`（4处）都有同一个 bug。
  这两个页面的 `enriched.json` 工作文件已经按约定清理，没法直接重新跑
  `build_page.py`，改用**直接在已发布的 `index.html` 里手工替换对应的
  `<rt>にん</rt>` 为 `<rt>ひと</rt>`**（纯展示文本，不涉及音频，风险低，
  比重建整条 pipeline 更稳妥）——发现订正逻辑影响到别的已发布页面时，要
  跟用户说清楚具体是哪几处、打算怎么修，由用户决定要不要连带处理，不要没
  打招呼就顺手改一堆不在本次任务范围内的旧页面。
- **无论订正表/规则写得多通用，"人工审核环节"依然不能省**——这是这一系列
  读音 bug 反复给出的结论：先加窄规则（`("の","人")`）→漏了没有独立"の"的
  场景→改成通用函数覆盖所有非数字前置的情况，每一轮"自动化改进"都是在人工
  发现具体反例之后才补上的，脚本永远只能覆盖"已经想到的模式"，覆盖不了
  "还没出现过的新场景"（比如未来某天冒出一个"人"前面接数字但还是该读ひと的
  特例，现在的规则会漏判）。`audit_furigana.py` 的定位很明确：**降低人工
  审核的成本（从"通读整页找错"降到"扫一遍几十行的高危字报告"），不是消灭
  人工审核这一步**——报告里每一条终究要靠人工用日语知识判断对不对，脚本
  只负责"别让人漏看"，不负责"替人下结论"。**这个结论后来又被验证了一次**：
  同一课里"第２位"的"位"被 pykakasi 默认读成くらい（"大概/左右"，比如
  "3人くらい"），实际该读い（名次量词，"第２位"=だいにい）——跟"人"是完全
  同一种坑（阿拉伯数字紧跟汉字量词，量词被拆成孤立 token 后读错；汉字数字
  版本"第一位"会被合并成一个 token，不受影响），修法也一样：加进
  `_resolve_hira()`，条件是"前一个 token 的最后一个字符是不是数字"（不能用
  `prev_orig.isdigit()` 整串判断——"第２"是"第"+"２"合并成的一个 token，
  整串不全是数字，必须看最后一个字符）。这是同一课里发现的**第4处**这类
  读音 bug（人×2、月、位），且是分好几轮才发现全的——每发现一批、自己都
  一度以为"这下应该审完了"，结果下一轮又冒出新的。**这进一步印证上面的
  结论：跑完 `audit_furigana.py`、订正表/规则改完之后，不能就此假设"这类
  问题解决了"，每次生成新课程内容都要重新走一遍"跑脚本→逐行人工核对"的
  流程，不能凭上一课审过的经验就默认这一课也没问题**。
  **这个系列后续又发现了两条相关但独立的坑**（真实案例
  textbook-sjp-zg-l13，人口统计课文）：①`"万人"`——pykakasi 把数字紧跟着的
  "万人"两个字合并成一个 token 整体读ばんにん（"万"的罕见读音，比如"万暦"
  这类专有名词才用得上），但"〜万人"这个统计场景（"7,550万人""1万人"）几乎
  总是该读まんにん——不限定 prev_orig，直接无条件覆盖"万人"→"まんにん"就够
  （没找到"万人"该读ばんにん的真实场景，跟"日本"→"にほん"是同一类可以放心
  无条件覆盖的情况）。②`"1人"/"2人"`——阿拉伯数字"1""2"紧跟"人"是不规则读法
  ひとり/ふたり（不是常规的いちにん/ににん），但汉字数字写法"一人"/"二人"
  pykakasi 自己的词典本来就读对（会整体合并成一个 token，不拆成"一"+"人"，
  不受这条规则影响）——只有阿拉伯数字写法才会被拆成独立的"人"token、默认
  读成にん。3人及以上没有这个不规则读法，仍然正常读にん/じん，只需要在
  `_resolve_hira()` 里给"人"这个判断分支单独加两条"prev_orig=='1'/'2'"的
  特例，插在"数字+人→にん"这条通用规则之前。**这两条不是靠通读 `audit_
  furigana.py --all` 报告发现的**——两处读音看着都"正常"（不在高危字表里，
  `audit_furigana.py`（不带 `--all`）完全不会命中），是核对生词表音频边界
  时顺手拿 pykakasi 现场测试"这几个数字统计相关的词读音对不对"才意外测出来
  的，说明这类"统计课文里数字+量词"的固定搭配，即使全量复核也未必能靠"读
  一遍看合不合理"主动发现，遇到统计类课文时值得专门用 pykakasi 挨个测一遍
  文中出现的"数字+汉字量词"组合。
- **`audit_furigana.py --all` 跑出报告只是完成了"必须"里的一半——报告摆在
  眼前不看等于没跑**：真实案例（textbook-sjp-zg-l13）——`--all` 全量复核
  这一步确实执行了，报告也生成了、也读过了（29行完整列出了这一课带汉字的
  全部读音，"億[人→ひと]で"就在其中一行），但审的时候重心全放在"跟危险字表
  对得上的几个已知坑"上，对报告里其它没被自己预设"这里大概率有问题"的行，
  只是扫一眼觉得"看着还行"就翻过去了，没有真的逐条用日语知识核对每一个字。
  用户后来指出："65億人"读成ひと明显不对，还追问"对于注音，你需要人工审核

  问题"——这句话点得很准：**"这条 skill 要求做全量复核"和"这次真的做了全量
  复核"是两件事，跑了命令、生成了报告，不等于真的执行了"逐条用日语知识判断

  默认读くん（人名后缀"田中くん"那个读法），但对话里"君の頼みだ""君と町子
  さんが"都是第二人称代词用法，该读きみ；②人名"李"（"上海の李さん"）
  pykakasi 按训读猜成すもも（水果"李子"），该读り（跟"千尋"→"ちひろ"同一类
  专有名词读音坑）；③"歳"紧跟数字表示年龄（"25.0歳""26.0歳""27.8歳"）
  pykakasi 默认给とし（"お歳"这种独立问年龄场景才对），该读さい——跟"人/

  不能只对照自己脑子里已经想到的几个可疑点去报告里找，要真的从第一行读到
  最后一行，每一行都停下来问自己"这个字在这句/这个词的语境里真的读这个音
  吗"，读完整份报告之前不能提前判定"审完了"。
- **`DANGER_KANJI` 高危字表这类"按字过滤"的自动化手段，天生覆盖不到专有
  名词——这类词的正确读音不是靠"这个字容不容易读错"的统计规律能推出来的，
  必须动用具体知识**，用户直接指出了这一点："汉字在不同句子中发音不同的
  情况，你（指 Claude）是完全可以分辨出来的呀"——这句话点破了此前的自动化
  思路有个盲区：一直在优化"怎么用脚本/规则缩小人工要看的范围"，却没有意识到
  Claude 本身具备直接判断读音对不对的知识，不需要先靠脚本筛出"高危候选"才能
  审。真实案例（textbook-sjp-zg-l11）：《千と千尋の神隠し》（《千与千寻》）
  这句话里的人名"千尋"被 pykakasi 猜成せんじん，"尋"不在高危字表里，标准
  扫描完全不会命中——但 Claude 知道这部电影、知道女主角叫"千尋/ちひろ"，
  只要真的通读一遍全部注音（不是只看脚本挑出来的"高危"子集），凭这个知识
  当场就能判断出来这条错了。**应对方法**：`audit_furigana.py` 新增 `--all`
  参数，不再按高危字表过滤，把这份 `enriched.json` 里全部带汉字的读音（连
  同完整原句上下文）都打印出来，供逐条人工全审——高危字表那一版仍然保留
  （处理量小、能快速定位已知规律的问题），但**全量复核这一步不能省，是
  高危字表扫描的补充而不是替代**，两步都要跑（见"生成页面之前：全量读音
  复核"一节）。全审时还顺带发现一个不属于"读错"、但值得跟用户核实的问题：
  同一课里"その後"作为两条不同的生词分别读音标成そのご和そのあと，正文里
  同一个词又读成のち——三种读音单独看都合法，但同一课内三种不一致的读法
  本身可疑（可能是词表条目意外重复），**这类"各自看都不算错但放在一起显得
  矛盾"的情况脚本判断不了对错，遇到了如实报告给用户，不要自作主张合并/
  删除生词条目**。

- **"这个词是否出现在某句里"不能用汉字词干/假名子串做自动模糊匹配后直接
  采信，假阳性率很高**——真实案例（textbook-sjp-zg-l10，单词测试 tab 的例句
  来源核实）：① 单字符汉字词干最危险，"入れる"（いれる，"放入"）的汉字词干
  只有"入"一个字，会误匹配到"入浴"（にゅうよく，完全不同的词）；"光"
  （ひかり，"光线"）会误匹配到"観光地"里的"光"字；这类误匹配几乎总是"这个
  单字符恰好是另一个复合词的一部分"，跟目标词本身是不是真的出现无关。
  ② 只有假名的语法搭配词（比如"お/ご〜申し上げる"这种敬语句型）如果直接按
  单字符"お"/"ご"去匹配，几乎所有句子都会命中（"お"极为常见），等于完全
  失去了筛选能力。③ 后缀类词条（比如"〜所"，读しょ，"…站/…处"）即使匹配到
  了包含同一个汉字的句子，也可能是那句里这个字用的是完全不同的读音/词义
  （"ある所ばかり"里的"所"读ところ，是"地方"的意思，不是后缀"しょ"），
  字形一样不代表用法一样，必须连读音/词性一起核对，不能只看字面。**排查
  方法**：写自动匹配脚本时可以用来"缩小候选范围"，但候选结果必须整份打印
  出来人工过一遍，不能脚本判定"匹配上了"就直接写进最终数据——尤其警惕单
  字符汉字词干、纯假名助词/敬语片段、后缀类词条这三类，凡是这三类给出的
  "匹配成功"结果都要重点复核。真实案例（textbook-sjp-zg-l12）又踩了几类
  新的假阳性，逐条人工核实候选句子时要连带排查：
  - **候选句子里出现的是这个词的复合词/派生词，不是这个词本身的用法**——
    "披露する"（宣布，动词）只匹配到"披露宴"这个复合名词，句子本身根本
    没把"披露"当动词用；"言葉に甘える"这个惯用语只匹配到"言葉"的泛义
    名词用法，不是这个惯用语本身。字面包含目标词的字符串，不代表句子在
    演示这个词的这个用法/词性。
  - **同一串汉字在不同语境下是完全不同的词**——生词表里的"中国"指日本
    的"中国地方"（广岛冈山一带），候选匹配命中的却是"中国は多民族
    国家で"这种指"中华人民共和国"的句子，字面撞了但完全是另一个意思，
    这种情况光看字面绝对判断不出来，必须动用具体知识（这个词在这一课
    语境下到底指什么）。
  - **单字符动词词干（言/聞/思之类）匹配到的候选几乎全是假阳性**——
    "言い間違える/言い返す/聞き返す/思い返す"这几个复合动词，词干只有
    一个字，几乎能命中任何含"言う/聞く/思う"这几个基础动词的句子，逐条
    看下来没有一条是在演示这几个复合动词本身，这类词条几乎总是要走人工
    补写这条路，不用指望候选匹配。
- **给单词测试的填空题选例句/挑 blank 时，目标词/短语在同一句话里如果
  出现不止一次，必须换一句只出现一次的，或者改用更长/更靠后的一段文字
  当 blank 避开重复——不然填空只会挖掉第一处，句子里剩下的那一处等于
  直接把答案摆在眼前**。真实案例（textbook-sjp-zg-l12）：候选句子"中国は
  多民族国家で，民族によって使用する言語が異なっている。"里"民族"出现了
  两次（"多民族"里一次、独立成词一次），"共通語（東京方言）では…"、
  "これを「保管して」と聞き間違えて，要らないものを大切に保管して
  しまった"这两句里"共通語"/"保管して"也各自出现两次——如果直接拿这类
  句子当例句、blank 就填最直觉的那一小段，填空组件按"替换第一处匹配"
  的逻辑挖空，句子里后面还留着的那一处会原样显示出来，等于剧透。**排查
  方法**：`occurrences.json`/`authored_examples.json` 写完之后，跑一遍
  "每个 blank 在自己对应的句子里出现次数是否恰好为 1"的检查（`sentence.
  count(blank) == 1`），不等于 1 的要么换一句原文里只出现一次的、要么把
  blank 改成更长/更靠后、能唯一定位的一段文字（比如"保管して"改成
  "保管してしまった"），要么干脆改成人工补写一句干净的例句。
- **给"日文写中文"这类题型判分时，词典释义前面的词性标签（`[名]`/`[动3]`
  之类）必须先剥离，剩下的部分再按顿号/逗号/分号切成多个"任一对即算对"的
  选项**——词性标签是抄词典时带的元数据，不是释义内容，原样保留会让判分
  逻辑要求用户连词性标签一起打出来（不合理），且第一个逗号前的内容如果
  混进了标签会破坏切分。`listening-page.js` 里 `POS_RE` 这个正则专门处理
  这个剥离，加新题型/改判分逻辑时如果涉及 `zh` 字段，记得复用这个正则，
  不要重新发明一遍。
- **`build_vocab_quiz_data.py` 早期版本里，没有显式 `kana` 字段的词条会
  直接退化成 `kana = text`（词的原文本身），而不是真的转换出一个假名读音
  ——这个 bug 影响所有"没显式填 kana"的词条，不是个别偏门情况**（已修复，
  见下）。真实案例（textbook-sjp-zg-l10，用户在"单词测试"tab 的"根据中文
  写假名"题里发现"〜食"这条无论怎么打都提示答案是"〜食"本身，不是假名
  しょく）：生词表里**大多数词条本来就没有显式 `kana`**——`vocab_words.json`
  只有 pykakasi 默认转换会猜错的词（熟字训、多音字，比如"女将"会被猜成
  じょしょう）才需要显式填 `kana` 覆盖，其余词条（这次真实案例里的"〜食/
  〜名様/〜付き/〜千万/〜年制/〜氏/お世話になります"全都属于这一类——
  pykakasi 默认转换本来就是对的）完全不需要显式 `kana`，靠 `build_page.py`
  的 `ruby_html()` 走 pykakasi 转换就能拿到正确读音显示在生词卡片上。但
  `build_vocab_quiz_data.py` 组装"单词测试"数据时，对没显式 `kana` 的词条
  没有走同一条 pykakasi 转换路径，而是直接拿 `text` 本身当 `kana`——生词
  卡片上显示的假名是对的，"单词测试"tab 里同一个词的标准答案却是错的，两处
  数据看着来自同一份词表、实际早就分叉了。**修复**：`build_vocab_quiz_
  data.py` 现在有一个 `kana_for()`，没有显式 `kana` 时会真的调用
  `build_page.py` 里那个共享的 pykakasi 实例（`_kks`）+ 同一张手动订正表
  （`_TOKEN_READING_OVERRIDES_*`）转换一遍，是跟生词卡片显示同一条路径，
  不会再分叉。转换时还要注意两个细节：① 只有含汉字的 token 才用假名替换，
  片假名外来语（"スケジュール"这类）本来就没有另一套平假名读音，原样保留
  不转换（第一版加了 pykakasi 转换但漏了这条判断，把"スケジュール"转成了
  "すけじゅーる"，一次性影响10个片假名词条，靠拿脚本重新生成的完整100条
  数据跟已经人工核实过的线上数据全字段比对，比出了这批新差异才发现）；
  ② "〜"这种词典占位符号最后要从结果里去掉（不对应实际发音，"〜食"读
  しょく不读〜しょく）；"お/ご"这种二选一的敬语前缀（比如"お/ご〜申し上げる"）
  没法自动算出唯一读音，脚本会直接硬报错，要求这条必须显式填 `kana`，不会
  悄悄拼出一个大概率错误的猜测。**排查方法**：怀疑"单词测试"里哪个词的
  假名答案不对时，直接跑一遍 `build_vocab_quiz_data.py` 用同一份
  `vocab_words.json` 重新生成，跟当前部署的数据逐字段比对，比人工一个个
  检查快得多也不容易漏。
- **`vocab_words.json` 里的 `id` 字段如果用错了编号体系（生词自己从1开始编，
  而不是接着会话+课文占用的编号往后排），单词测试里"听音频写假名"这一整类
  题目会播放完全不相关的音频，而且这个 bug 流水线每一步单独看都不会报错，
  只有真的点开听才能发现**——真实案例（textbook-sjp-zg-l11）：用户在单词
  测试"会话相关"分类里做到"わけ"这个词的"听音频写假名"题，播放出来的却是
  完全不同的一句话（"若者は日本のものと外国のものを区別していないような
  気がします"，这是另一句对话，压根不是"わけ"这个词）。查下去发现不是这
  一个词的问题——**这一课全部 144 个生词条目的 `id` 全都比真实音频编号
  小了 35**（35 正好是这一课会话+课文两个 tab 合起来的句子数）。根因是
  `vocab_words.json` 的 `id` 字段用的是"生词表自己从1开始编号"，而"生词"
  tab 的真实音频文件编号是接着会话+课文的编号往后排的（会话+课文占了
  1~35，生词从36开始）——两套编号体系不一致，但两边巧合地"看起来都是
  合理的整数"，没有任何一步会因为这个不一致而报错：`build_vocab_quiz_
  data.py` 只检查 occurrences/authored 覆盖是否完整、`blank` 是不是子串，
  完全不知道也不检查这个 `id` 最终要拼出的音频文件是否真的存在对应内容；
  `verify_clips.py` 检查的是每段音频文件本身内容对不对，压根不知道"这段
  音频还被单词测试引用了、引用的对不对"这层关系。**这类"数据链接错误"（
  A处理流程产出的数据被B处理流程引用，但引用的钥匙对不上锁）天生不会被
  "检查这份数据本身对不对"的校验发现，必须专门做"交叉引用一致性"校验**。
  修复用了新增的 `verify_quiz_ids.py`（按文档顺序比对生词 tab 卡片的真实
  音频编号和 `quiz_data.json` 里词条的顺序，不依赖固定偏移量、也不按文字
  查字典——同一课里可能有重名词条，比如这一课"その後"出现了两次、读音还
  不一样，按文字匹配会被搞乱，按文档顺序位置对应更可靠），已经作为"6c"
  写进必做流程，`--quiz-json` 页面生成后必须跑这一步，不能假设"前面每一步
  都没报错=最终结果没问题"。**修好 id 重新发布之后还带出一个连锁问题**：
  用户浏览器里旧的错题/进度记录是按旧（错误的）id 存在 localStorage 里的，
  页面更新后这些 key 对应不上任何一个现在真实存在的词，变成孤儿记录——
  `totalErrorCount()` 之类的统计函数是直接累加/统计整个 errors 对象，不会
  区分"这个 key 现在还对不对得上一个真实词"，孤儿记录会让"累计错误数"这
  类显示比"仅错题"队列里真实能筛出来的题目数更大（真实案例：显示
  "1 / 7(9)"，队列只有7道真实能匹配上的错题，累计错误数却被孤儿记录污染
  成了9）。**这不是这一次 id 修复独有的问题，是"数据结构变化后旧本地存储
  变孤儿"这一类问题的通用表现**，`listening-page.js` 里加了 `pruneOrphans()`：
  每次加载某个分类的错题/进度状态时，自动清掉 key 对应的 wordId 不在当前
  词表里的孤儿记录（清完立刻存回 localStorage，不是只在内存里筛一下），
  用户不需要手动点"清除使用记录"就能自愈，以后再出现类似的词表结构变化
  （id 重新编号、词条增删）也能自动处理，不用每次都单独写一次性清理逻辑。
- **pykakasi 对 Whisper 拆散的复合词单字 token 各自转换会得到错误读音，
  拼起来跟这个复合词真正的音読完全对不上**——真实案例（textbook-sjp-zg-l11）：
  生词"真実"（音読しんじつ）在 word-level 转写里被 Whisper 拆成"真"+"実"
  两个独立 token，如果直接对每个单字各自跑 `pykakasi`，"真"被猜成训读
  "まこと"、"実"被猜成训读"み"，拼起来"まことみ"跟真实读音"しんじつ"完全
  不沾边——这不是 pykakasi 本身的 bug，是孤立单字缺少复合词上下文，本来就
  该猜训读（`to_hiragana("真実")` 整体转换是对的，输出正确的"しんじつ"）。
  这个坑不止影响"真実"这一个词，**任何"按假名读音做内容比对/对齐"的逻辑，
  只要输入源是 Whisper 拆散的单字 token，就有同样风险**（比如"生词边界
  收紧"那一节里用读音做窗口内容匹配）。**修法**：不要对 Whisper 输出的
  单字 token 各自转换，先用 `tools/listening/cluster_tokens.py` 的
  `load_and_cluster()` 把间隔很小（同一个词内部的相邻 token）的 token
  合并成完整的词/复合词字符串，再对合并后的整串转换。
- **不要为了让 `kana` 字段"看起来干净"就把教材原文里的多写法/异写条目
  （比如"た/たんぼ（田/田んぼ）"这种一个词条给出两种写法的情况）简化成只
  保留一种**——真实案例（textbook-sjp-zg-l11）：截图抄录时把"た/田んぼ"
  简化成了单一的"田んぼ"（借口是"kana 字段没法表示两种读音"），但用户实际
  听录音发现音频里**真的是把"た"和"たんぼ"两种写法/读法都读出来了**，教材
  原文这么写是有理由的，不是排版冗余。**规则**：截图里出现的多写法要素
  （用"/"分隔的备注、括号里的"也作「…」"）原样保留在 `text` 字段里，`kana`
  给主要读音就行，不要因为处理起来麻烦就单方面精简掉信源本来就有的信息——
  拿不准的话跟"其余照抄截图"的默认原则一致：先照抄，真的需要简化再跟用户
  确认，不要自己直接替用户做这个决定。
- **`align_group()` 对文件/音频里第一个题目分组算出来的 `edge_start`，
  比其它分组更容易算偏**——真实案例（textbook-sjp-zg-l11，用户听出来的
  问题）：会话第一句"あのポスター…"开头的"あの"被切掉了一截，课文第3段
  首句"やがて…"开头也是同样情况——两次都是各自音频里**这个题目分组
  自己的第一句**，怀疑是因为文件/时间线最开头缺少"前一个真实内容"作参照，
  对齐算法在定位第一个匹配块时更容易把起点定得偏晚一点。**这跟前面"銭湯/
  戦闘"那条内部切分点坑、"また銭湯"那条外边界窗口坑都不是一回事**：那两条
  都有明确的错误诱因（同音异字混淆、窗口本身开太窄看不到内容），这条目前
  没找到确定诱因，只是经验上"每个题目分组的第一句"、"每段音频最开头的
  内容"值得额外多一次核实，不能假设"用了 `align_group()` 就一定准"。
  **排查方法**：跟其它边界问题一样，对可疑区间跑一次够宽的独立 word-level
  转写，直接对比真实内容的起始时间和 `enriched.json` 里记的 `start`，
  这条坑目前只能靠"生词边界收紧"一节里提到的自动化校验（`verify_clips.py`
  的 LEAD_SILENCE 检查）批量发现，不能假设第一句"大概率没问题"就跳过核实。
  **上面这句关于 `verify_clips.py` 能批量发现的说法后来被证伪了**：真实
  案例（textbook-sjp-zg-l13，用户反馈"开头没有发音"）——课文6个题目分组
  （标题/第1~5段）里有3个（第2/3/4段）的首句 `edge_start` 都算晚了
  0.2~0.42秒，不是只发生在"整份材料真正的第一个分组"，`edge_start` 算
  偏这个问题在**同一课里可以同时发生在好几个题目分组身上**，不是"整篇
  材料只有开头一次风险"。更关键的是，`verify_clips.py` 的 LOW_SIMILARITY/
  LEAD_SILENCE 检查这次**完全没有命中这3处**——因为切掉的只是句子开头
  一两个字（0.2~0.4秒），句子剩下的部分（好几秒）转写完全正常，整句的
  识别相似度依然很高，不会被相似度阈值判定异常；LEAD_SILENCE 检查的是
  "开头静音是不是太长"，这个坑恰恰相反（是开头真实内容被切掉，不是静音
  过长），方向对不上，天生查不出来。**这意味着"每个题目分组的第一句都
  要额外核实"不能指望自动化脚本兜底，必须真的对每一个题目分组的首句都
  单独做一次"字符级 char_times[0] 是否等于/早于 `start`"的检查**（如果
  `align_group()` 对齐成功，`char_times[0] < start` 是明确的证据——真实
  发生过；`char_times[0] == start` 分毫不差也值得怀疑，这种"精确相等"
  往往是对齐算法在缺少"上一个匹配块"可参照时把 `edge_start` 直接退化
  等于窗口起点/`char_times[0]` 强行钳制成 `start` 本身，不代表真的测量
  准了，也要用 RMS 能量剖面或宽窗口 word-level 转写单独核实，不能因为
  两个数字"看起来吻合"就放过）。修复时对每一句单独开一个覆盖"真实前导
  静音+这句完整内容"的宽窗口重新跑 `align_group()`，不要在原窗口基础上
  加一个固定偏移量往前挪（不同句子该往前挪多少差异很大，跟"銭湯/戦闘"
  那条坑一样不能套公式）。
- **两个相邻 token 的 end/start 完全相等（零间隔）不能直接当真实边界照抄，
  必须用静音检测或 VAD 交叉确认——这条表象背后可能是两种完全相反的真相**：
  一种是"这两个词真的连着读、之间没有停顿"（早先"たっぷり/つかる"那条坑，
  正确做法是照抄这个零间隔当边界）；另一种是 Whisper 把后面真实存在的静音
  错误吞进了前一个词的 token 里（真实案例"見込み/主演する"，两词之间其实
  有将近3秒真实停顿，零间隔只是转写artifact）。**这两种真相从 word-level
  时间戳的表象上看一模一样，唯一区分方法是用 `ffmpeg -af silencedetect`
  或 `vad_filter=True` 重新探测这个区间有没有真实静音段**，不能凭"看起来
  是零间隔"就二选一地假设成某一种。
- **人工核对几十上百条边界数据的 token 位置时，出错概率不可忽视，不能把
  "已经很仔细看过一遍 printout" 当成核实完成的标志**——真实案例
  （textbook-sjp-zg-l11）：人工核对生词"彼ら"的真实边界时，printout 里
  明明列着"彼(88.90-90.30)　ら(90.30-91.70)"两行，抄录时手滑只看到了
  "彼"这一行的时间戳当成整个"彼ら"的范围，完全漏看了"ら"字自己的这一行，
  写出来的"修复"反而让这个词的音频完全消失（因为漏了的"ら"那部分被后面的
  "つかむ"词条边界覆盖裁掉了）。**这不是靠"再仔细一点"就能杜绝的问题**——
  当核对量上到几十条时，纯人工读表格出错是正常统计现象，不是能力问题。
  **应对方法**：①每次修复后必须用 `verify_clips.py` 或至少对这一条单独
  重新转写确认，不能只信"人工核对过了"这个状态；②优先信任自动化脚本
  （`align_group()` 窗口搜索）算出来的结果，只在脚本明确失败/结果不合理
  时才退回人工读 printout，而且人工读的结果同样要过自动校验这一关，人工
  核对不能跳过最终校验这一步。
- **Whisper 在完全静音/近似静音的音频上也会"幻听"出看起来合理的文字，
  "转写出了像样的词/字符"不能当成"这个位置真的有对应内容"的证据**——这是
  本 SKILL.md 目前踩过的所有坑里最费时间的一条（真实案例 textbook-sjp-zg-l11：
  为了核实 8 个生词条目的正确边界，反复用 word-level 转写、VAD、不同参数
  的 VAD 阈值probe 了四五轮，每一轮都得到一个"看起来合理"（字符能对上
  期望文本、时间戳前后有间隔）的结果，改完部署后自动校验一查，音量检测
  显示这些位置根本就是静音——**转写模型即使没有真实语音输入，也会倾向于
  输出跟上下文/训练分布相符的"看似合理"的文字**，人不可能靠"这个转写结果
  看起来对"来确认真伪）。**唯一可靠的最终判据是音量/静音检测（`ffmpeg -af
  volumedetect` 看 `max_volume`），不是转写文本本身**——真实案例里，最终
  真正定位到 8 个词正确位置的方法，是先跑 `vad_filter=True` 搭配偏低的
  `threshold`（比如0.15~0.2）和 `min_silence_duration_ms`（比如250~300）做
  segment 级（不是 word 级）转写，让模型自己在整段范围内把真正有语音能量
  的片段圈出来，再看圈出来的片段跟词表顺序对不对得上，比反复调整 word-level
  探测窗口大小/位置更可靠。**判断一个边界是否可信的最终检验步骤**：切出来
  的 `seg-NNN.mp3` 通过 `volumedetect` 看 `max_volume`，正常语音片段一般在
  -1~-15dB 左右（这份录音的经验值，不同录音基准可能不同，可以拿几个已确认
  正确的条目现算一个参考区间），明显更低（这次真实案例里坏的条目普遍在
  -20~-55dB）基本可以判定是静音/近似静音，不管转写结果多么"像样"都不能
  采信，必须重新定位。`verify_clips.py` 现在已经内置了这一层音量检测——每条
  EMPTY/LOW_SIMILARITY 都会自动跑一次 `volumedetect`，跟同一批全部片段的
  `max_volume` 中位数比（低于中位数15dB以上标 `[疑似静音]`，否则标
  `[可能是识别噪声]`），报告里直接看得到标注，不用再额外手动跑一遍。
- **`[可能是识别噪声]`（音量正常）不等于"可以跳过不用管"——音量检测只能
  分辨"这段时间范围里有没有声音"，分辨不出"这段声音是不是这一条该有的内容"，
  一段音频完全可能混进了旁边词/旁白的真实人声，音量完全正常，但内容是错的**
  ——这条是上一条"音量检测"坑的姊妹坑，容易被误当成同一件事，其实是完全
  不同的失败模式，值得单独记录。真实案例（textbook-sjp-zg-l11）：生词
  "〜ら"/"抜く"/"さっと"三条被 `verify_clips.py` 正确标记为 LOW_SIMILARITY，
  但音量检测都判为 `[可能是识别噪声]`（因为切出来的音频里确实有一截响亮的
  真实语音——比如"抜く"切到的那2.96秒音频里，前2.3秒是纯静音，但混进了一小
  段响亮的无关人声，导致 `max_volume` 完全正常），当时把这个标注当成"可以
  跳过"的信号没有深挖，用户实际听后发现全部是真 bug（`〜ら`只发出了元音、
  `抜く`内容完全对不上、`さっと`开头被切掉一截）。逐帧振幅剖面（`wave`模块
  按50ms窗口算RMS，不依赖任何转写/VAD模型，纯粹看真实能量分布）复核后发现，
  这三条的真实边界跟原来标注的边界相差 2~3 秒，混进来的响亮片段是相邻位置
  的真实内容（比如"抜く"当时标的边界几乎完全落在两个词之间的静音停顿里，
  真正的"抜く"发音其实在再往前2秒多的位置）。事后找到一个不依赖音量、更有效
  的信号：**识别出来的文字本身像不像连贯真实的日语**——"はっ!"「ご視聴あり
  がとうございました」「どう?」都是完整通顺的日语词/短语，说明 Whisper 真的
  听到了某处的真实人声，只是不是这一条该有的内容；反过来像"TNM"「SIM」「C」
  这种夹杂拉丁字母/数字的乱码输出，最初以为通常代表 Whisper 在真的很短/生僻
  的孤立词上转写失败、位置本身没问题。`verify_clips.py` 现在会自动做这层判断
  （见脚本文档字符串第5条），LOW_SIMILARITY 报告里每条都会追加 `[命中已知
  静音幻觉套话]`/`[疑似内容错位-像连贯日语]`/`[像ASR对短词的识别局限]` 标注。
  **这个"乱码=位置没问题"的假设后来被证伪了**：生词"将棋"（识别为"ん"）和
  "碁"（识别为"5"）都带着 `[像ASR对短词的识别局限]` 标注、音量也正常（两项
  标注都"正常"），一度被当成"可以跳过"放过，用户实际听后发现两条都是真
  bug——"将棋"的边界整个落在两个词之间的静音段（真实内容在再往前0.86秒处），
  "碁"前面留了2.27秒空白才到真实内容。**根本原因**：乱码输出本身不携带任何
  关于位置对不对的信息——它既可能出现在"位置对、词太短ASR处理不好"（比如
  同一批里的"定年"，重新定位边界后依然识别成"TNM"，但音量剖面确认位置是对
  的），也可能出现在"位置错、残留的静音/噪声让 Whisper 吐出乱码而不是幻觉出
  完整词"（这次的"将棋"/"碁"），**两种场景从识别文本本身完全无法区分**，
  跟"连贯日语 vs 乱码"这条判据能可靠区分"内容错位 vs 识别局限"完全不是一回事
  ——连贯日语判据能生效是因为"听到了别处的真实内容"这件事本身就是强信号，
  乱码则什么信号都不携带，纯粹是"没有更多信息"。**修正后的结论**：`[疑似
  静音]`/`[命中已知静音幻觉套话]`/`[疑似内容错位-像连贯日语]` 三者任意命中
  一个才是真正的"优先处理"信号；`[像ASR对短词的识别局限]` **不是"跳过"的
  许可**，只是"这条没有更强信号、需要跟其它条目一样正常走人工复核流程"，
  尤其是1~2个假名的短生词——这类词天然是 ASR 最不可靠、也最容易被"乱码=
  没问题"这个错误直觉放过的一类，EMPTY 和全部 LOW_SIMILARITY 条目原则上
  都要过一遍人工检查，标注只用来排优先级、不用来判定"要不要看"。人工复核这
  类位置时，`ffmpeg silencedetect` 这类基于阈值判定的工具precision不够
  （容易被响亮的错误内容片段"骗过"，也可能漏掉真实但偏弱的语音），更可靠的
  做法是上面提到的逐帧 RMS 振幅剖面——把整个可疑区间（不只是当前标注的边界，
  前后各扩几秒）按50ms切帧算能量，人工读数值找出真正的语音爆发区间（读音
  突然从底噪 -50dB 左右跳到 -10~-20dB 再回落），再拿这个真实爆发区间去跟
  词表顺序核对是不是对得上这个词。
- **`align_group()`/`refine_boundaries.py` 依赖的 Whisper word-level 时间戳，
  不只是"孤立短clip"才不可靠——即使对整段连续音频（几十秒到一两分钟，带
  完整上下文）跑一次 word-level 转写，某些词（尤其紧跟在一段沉默/停顿之后
  的题目分组第一句）的起始时间戳依然可能比真实起音晚 0.1~0.7 秒，而且这个
  偏差不会随着"换更宽的窗口""换连续转写而不是分段转写""句子拆得更短"这些
  常规改进手段自动消失**——真实案例（textbook-sjp-zg-l14）：课文"求职活动
  概况"这个题目分组的第一句"これは，就職活動を…"，无论是最初的多句合并版
  还是后来按用户要求拆成单句重新走完整流水线之后，`align_group()` 独立算出
  的 edge_start 两次都稳定落在46.3——但用逐帧 RMS 能量剖面核实，真实起音在
  45.80，整整差了0.5秒，这0.5秒的"これは"开头音在两次生成里都被静默切掉了。
  **这说明"把长句拆短"这类改进降低的是这类bug出现的概率，不是把它变成不可能
  ——同一类边界精度问题在同一课里换了一种句子切分粒度还是复现了一次**，
  不能生成完页面后就假设"跑过对齐算法+人工审过一轮=这一类问题已经解决"。
  **唯一被反复验证过真正可靠的判据依然是 RMS 能量剖面（不是任何形式的word-
  level时间戳，不管转写窗口多宽/多连续）**：怀疑一个边界（尤其是每个题目
  分组的第一句、经历过手工resplit重建的句子）不准，直接对这个点前后0.5~1秒
  逐帧算能量，找真实的静音→语音跳变位置，不要相信 `align_group()` 或者任何
  word-level转写报告"这里没问题"就跳过复核。
- **`--data-driven` 是这个 skill 后来才加上的架构（内容单独存 `data.js`，
  不再烘焙进 HTML），已经用旧方式发布的页面要迁移过去，用
  `tools/listening/migrate_to_data_driven.py <index.html>`（从当前已发布、
  当前正确的 HTML 反向抽取内容生成 `data.js`，同时把 `index.html` 换成引用
  这份数据的壳）——**前提是原始 `enriched.json` 已经不在了**（比如按约定
  清理过 `tools/listening/work/` 工作目录），如果原始数据还在，应该直接对
  着它重新跑 `build_page.py ... --data-driven`，反向抽取只能拿到 HTML 里
  已经烘焙进去的信息，精度和完整性都不如从源头重新生成（比如 char_times
  只能从 `data-t` 属性反推，损失了原始浮点精度之外的位数）。写这个反向抽取
  脚本时踩过一个正则坑，值得记录：`sentence_card_html()` 生成的卡片模板里
  `<audio>` 标签出现在卡片自己的 `</div>` **之前**（不是之后），一开始想当
  然地写了 `(.*?)</div>\s*<audio` 当卡片内容的结束锚点，实际匹配到的是卡片
  内部（`.seg-speaker`/`.seg-notes`）更早出现的某个无关 `</div>`，导致 179
  张卡片只抽取出16张（凑巧等于当时带 `data-blanks` 属性的卡片数——这些卡片
  可能因为 `data-blanks` 后面紧跟的属性/内容结构差异侥幸匹配对了，纯属巧合，
  不是设计如此）。**教训**：反向解析已生成 HTML 时，锚点要选模板里位置
  " 真正固定不变、不会跟内部其它同名标签混淆" 的元素（这里应该用 `<audio
  id="aN" ...></audio>\s*</div>` 整体当结束锚点，`<audio>` 标签本身在模板
  里位置唯一、不会跟卡片内部其它 `</div>` 混淆），不能想当然假设"最后一个
  子元素在最外层闭合标签之前"这类未经验证的模板结构假设，写完解析脚本后
  一定要拿抽取出来的数量去跟已知的真实数量（比如 `verify_blank_answers.py`
  之前报告过的卡片总数）交叉核对，数量对不上就是抽取逻辑有问题，不能就地
  信任脚本的"成功"输出。
- **手工绕过 `refine_boundaries.py` 正常流程、直接改某一句的 `start`/`end`
  时，必须同时重算这句的 `char_times`，不能只改边界不改高亮时间戳**——
  `char_times` 是绝对时间戳，跟 `start`/`end` 同一个坐标系，`build_page.py`
  渲染时用 `char_time - s["start"]` 算出跟读高亮的相对时间 `t`。如果只改
  了 `start`（比如按用户反馈手工核实出一个新边界，直接写进 JSON），旧的
  `char_times` 还停留在改之前的绝对值，减出来的 `t` 就会飘（往前挪了
  `start` 会让原本对得上的字变成正数偏大甚至更早的字变成负值，往后挪则
  相反）。真实案例（textbook-sjp-zg-l12）：修复"というと？"这句的边界
  （从 `refine_boundaries.py` 原本给出的 `[20.8,22.03]` 改成宽窗口重新核实
  出的 `[21.62,22.5]`）时只改了 `start`/`end`，没碰 `char_times`，结果
  第一个字"と"算出来的 `t` 变成 `-0.82`（负值，高亮会在音频真正开始前就
  提前触发）——用户直接从页面编辑模式导出的 JSON 里看到这个负数发现的。
  **修法**：手工改动任何一句的 `start`/`end` 之后，如果这句本身带
  `char_times`（会话/课文才有，生词条目没有），必须针对这句（用宽窗口，
  不要用窄窗口——见下面"孤立短clip"那条坑）重新跑一次 `align_group()`
  （单 member 调用也可以，`members=[{"text": s["text"]}]`），拿新的
  `char_times_per_sentence` 结果覆盖旧值，不能只搬运新的 `edge_start`/
  `edge_end` 而把 `char_times` 原样保留。
- **新发现的边界错位类型："两头都被切短"，中间一截真实内容两边谁都没
  覆盖到，不是"一句侵入另一句"那种更常见的重叠型错位**——之前记录的边界
  坑基本都是"A句边界估晚了/估早了，侵占了B句的一部分"，这次真实案例
  （textbook-sjp-zg-l12）是另一种：课文"…という話もある。"（A句）存的
  `end` 是174.08，"現在では…"（B句）存的 `start` 是177.24，中间174.08~
  177.24这3秒多，宽窗口重新转写显示A句真实内容其实一直说到176.38才
  结束（"ある"这个字），B句"現在"也是从176.38就开始了——也就是说这3秒多
  本该分给A句结尾+B句开头的真实语音，在两句各自的 `start`/`end` 里都不
  存在，播放A句听不到完整结尾，播放B句听不到完整开头，这段音频实质上
  "消失"了。**这类坑普通的自动校验都发现不了**：`verify_clips.py` 逐条
  转写比对相似度，A句被裁短的那部分只是让A句的转写内容"变少了"（依然能
  大致对上文本的前半段，相似度不会掉到危险阈值以下），B句同理，两条都
  不会被标记成 EMPTY/LOW_SIMILARITY；`validate_boundaries.py` 只检查
  "相邻句重叠"，`end[i] < start[i+1]`（有间隔、不重叠）完全在它的正常
  范围内，不会报错。**必须靠专门的"间隔扫描"发现**：把 `enriched.json`
  按 `start` 排序，逐个相邻对算 `start[i+1] - end[i]`，超过一个阈值
  （比如1.5~2秒）的就打印出来人工复核——但**光扫出来还不够，间隔本身不是
  bug 的证据**，句子/段落/话题之间本来就该有自然停顿（尤其生词表朗读，
  词与词之间常规就留好几秒），扫出来的每一处都要单独用宽窗口 word-level
  转写核实"这段间隔期间，A句/B句各自的真实内容到底覆盖到哪"，确认两边
  加起来是不是真的漏了中间一截才动手改，不能看到"间隔大"就当成"肯定是
  bug"批量下手改。
- **同音字密集的段落（比如讲解声调/发音的段落，同一批读音反复用不同汉字
  体现，如"は/歯/箸/橋/端"全部读はし），`align_group()` 靠字符做 `difflib`
  对齐的方法会整体失效，不只是切分点算偏，而是常常直接报"对齐质量不够，
  回退"**——之前记录过的"銭湯/戦闘"是 Whisper 偶尔把某个词固定听岔，只
  影响那一个词附近的切分点；这次真实案例（textbook-sjp-zg-l12，课文里
  讲解"箸/橋"声调对立的一段）是 Whisper 在**同一段音频里对同一个读音
  "はし"反复听成不同的汉字**（同一段落先后被听成"歯"/"橋"/"端"/"箸"，
  没有固定规律），期望文本（原文写的"箸"/"橋"）和识别文本（Whisper 吐出
  来的"歯"/"端"）逐字符比对时大片区域完全不重叠，`align_group()` 的整体
  匹配覆盖率被拖到 `MIN_ALIGNMENT_COVERAGE`（0.45）以下直接判定对齐失败，
  连"切分点算偏"这种还能凑合用的结果都拿不到。**这种情况下的修法**：放弃
  对整个多句分组一次性跑 `align_group()`，改成给每一句单独开一个窄一点但
  仍然够宽（覆盖到前后邻句一部分）的转写窗口，**不看字符匹配，直接读
  word-level 转写的时间戳位置手工判断**——这段落里的词大部分是单音节
  假名（は/し），虽然汉字选择不一致，但读音在时间轴上的先后顺序是确定的，
  跟着截图原文的自然阅读顺序去认哪一段音频对应哪一句，比试图让算法做
  字符对齐更可靠。定完边界之后 `char_times` 同样拿不到精确对齐结果，退化
  成按字符数比例线性插值就够（`start + dur * j/len(text)`，`refine_
  boundaries.py` 自己在对齐失败时也是这么兜底的）——这种段落的跟读高亮
  精度本来就不可能做到完美，能大致跟上就行，不值得为了追求精确逐字符
  时间戳投入不成比例的时间。
- **`verify_clips.py` 单独转写一小段切好的 clip，比对着更长的上下文转写
  同一段内容更容易转写失败/幻听——这不代表这段 clip 的边界切错了，只是
  "孤立短音频"本身对 ASR 更不友好，必须靠"换个更宽的窗口重新转写确认
  真实内容位置一致"来排除是不是真 bug，不能只信"这一条单独转写不出来"
  就断定切错**。真实案例（textbook-sjp-zg-l12）：好几个生词条目（競馬/
  冷房/というと/えっ！？等）单独喂给 Whisper 转写效果很差（乱码或者跟
  "視聴ありがとうございました"这类视频结尾套话的幻觉），但把同一段时间
  范围放进一个包含前后邻句的更长窗口一起转写，同一段音频却能被正确
  识别（比如"競馬"在窄窗口里被听成"ケーヴァ"，宽窗口里同一个位置能对上
  "けいば"读音的字符）——说明边界本身没问题，只是缺少上下文的短音频对
  这个模型来说天生识别率低。**判断方法**：怀疑某条 `verify_clips.py`
  报出来的 LOW_SIMILARITY/EMPTY 是不是真 bug，先看这条边界是不是刚刚才
  通过宽窗口转写确认过（如果是，大概率就是"孤立短clip识别率低"这种已知
  限制，不用重新改）；确实心里没底的话，把这条前后各扩几秒重新转写一遍，
  如果宽窗口里同一段音频的内容识别结果能跟期望文本大致对上，就说明边界
  是对的，不用因为窄窗口/单独转写效果差就继续改。**这跟之前"`[像ASR对
  短词的识别局限]`标注不是跳过许可"那条不矛盾**：那条讲的是"乱码本身不
  提供任何位置对错的信息，必须去核实"，这条补充的是"核实的正确方法之一，
  就是换更宽的上下文窗口重新转写，而不是继续在同一个窄窗口里换参数试"。
- **`tools/listening/trim_clip_silence.py`（收紧生词音频前后静音）只对
  没有 `char_times`/`t` 时间戳依赖的生词条目安全，绝对不能跑在会话/课文
  的音频文件上**——那两类句子的跟读高亮 `t` 是"绝对时间戳 − 这句自己
  `start`"算出来的相对值，音频文件内部 t=0 隐含约定等于这句的 `start`，
  如果直接裁掉音频文件开头的一截，这个隐含约定就被破坏了，高亮会全部
  往后飘一个"被裁掉的时长"，而 `data.js` 里存的 `t` 完全不会跟着变。
  真实案例（textbook-sjp-zg-l12）：第一次跑这个脚本时图省事直接对整个
  `audio/` 目录跑（`seg-001.mp3`~`seg-144.mp3` 全部144个文件），而其中
  `seg-001`~`seg-054` 是会话/课文的音频，当场跑完才意识到把这些也裁了
  ——补救是重新跑一遍 `build_page.py` 生成干净未裁剪的音频，再把要裁的
  生词范围（`seg-055`~`seg-144`）单独复制到一个临时目录、只对临时目录跑
  这个脚本，裁完再复制回去覆盖，会话/课文那部分保持原样不动。**这个脚本
  调用前一定要先确认参数目录/文件范围只包含生词条目**，不能图方便直接扔
  整个 `audio/` 目录。另外，静音阈值（默认 `-35dB`）是启发式参数，对
  个别发音很轻/收尾很快的短词（比如这次真实案例里的"弁"）可能裁得比
  预期激进，裁完这一步不能跳过、必须重新跑一遍 `verify_clips.py` 确认
  没有把真实内容裁掉——真实案例里这一课90个生词条目自动裁剪完之后，
  其中"弁"这一条从原本能大致听懂退化成完全听不出内容，靠这次事后的
  `verify_clips.py` 全量重跑才发现，单独手工重新核实边界+更保守的缓冲量
  重切才修好。
- **同一处边界反复用 Whisper 转写核实、结果一直含糊不清时，不要继续在
  "换个窗口/换个参数再转写一次"上打转——应该立刻换成本节前面早就写过的
  "音量/能量剖面才是最终判据"这条原则，不能因为知道这条原则就默认自己
  已经在遵守它**——这是知行不一致的真实案例，不是没意识到方法本身。真实
  案例（textbook-sjp-zg-l12）：というと？/ありがとうございます/漁業 这
  几条最初被 `verify_clips.py` 标记问题后，一连好几轮都是"用户反馈问题→
  换个窗口重新转写→识别结果还是含糊/乱码→归因成'孤立短clip转写天生不
  可靠，边界大概率没问题'→暂时搁置"，每一轮都在转写文本上找答案，没有
  一次真的去看这几条切出来的音频本身的音量——直到用户直接反馈"没有发音"
  （不是"听着不像"，是"根本没声音"）才被迫换方法：跑一遍 `ffmpeg -i
  seg-NNN.mp3 -af volumedetect` 立刻看出这几条 `max_volume` 全部在
  -18~-33dB（远低于同一批正常条目 -3~-9dB 的水平），基本可以确定边界
  本身就切在了静音/近似静音区，跟内容对不对得上没关系。**比"只看
  `volumedetect` 单一个数"更进一步、能直接定位真实边界在哪的方法**：对
  怀疑区间前后各扩几秒，用 `wave` 模块读裸 PCM 数据（Python 3.11+ 标准库
  `audioop` 已经移除，算 RMS 要么用 `numpy`——`rms = sqrt(mean(samples**2))`
  ——要么退回手写累加，不能再假设 `audioop` 可用），按 50ms 一帧算 RMS
  转 dB，逐帧打印出来（比如 `#` 数量正比于响度画一条简易柱状图），人工
  读数值找"响度从底噪 -40~-50dB 突然跳到 -10~-25dB 再回落"的真实语音爆发
  区间，这个区间往往跟当前存的 `start`/`end` 完全对不上（这次真实案例
  发现所有几条错误边界都精确地落在两个真实爆发区间之间的静音空档里，
  真正的内容在几秒之外）——定位到真实爆发区间之后，直接把 `start`/`end`
  改到这个区间（前后留一点点缓冲）**就是最终答案，不需要再拿转写结果去
  交叉确认**（这次修复后重新转写这几条，效果依然一般，但音量已经证明
  内容本身是对的，不需要转写结果也"看着对"才敢采信）。**给自己定的纪律**：
  同一处边界如果已经用 word-level 转写核实过 2 轮以上还是不确定，第3轮
  不要再转写，直接上能量剖面——这条原则本节前面已经完整写过一次，这次
  只是真实踩了一遍"知道原则但没有养成条件反射去执行"的坑，记录下来提醒
  自己。
- **假名注音（furigana）分段——一个"汉字+送假名"混合词，注音范围不能超过
  连续汉字本身，必须按"连续汉字段"逐段拆开各自标注，中间/结尾已经是假名的
  部分照原样显示，不能跟相邻汉字并进同一个 `<ruby>`**——这条规则从
  `build_page.py` 建立之初就该遵守，但早期的 `_split_trailing_kana()` 只会
  从词尾往回摘送假名、摘到第一个汉字就停，只覆盖"一段汉字+结尾送假名"这
  一种形状（比如"悪かった"→悪/かった、"比べ"→比/べ），遇到有**两段独立
  汉字**的词（真实案例，textbook-sjp-zg-l12"書き間違える"=書+き+間違+
  える）就会出错：从词尾摘到"違"字（汉字）就停手，中间的送假名"き"没被
  摘出来，被错误地并进"書き間違"一整段注音"かきまちが"里。现在换成
  `_split_kana_segments()`（同名函数同时存在于 `build_page.py` 和
  `docs/js/page-renderer.js` 两处，**逻辑必须手动保持同步**，见下面
  "编辑模式绕开 Python"那条）：按"连续汉字"/"连续非汉字"分组，非汉字组
  本身就是假名，用它的首字符去 `hira` 读音字符串里搜索定位，定位到的位置
  之前那一段就是紧邻的前一段汉字的读音。真实案例里踩过的具体坑，处理这类
  分段逻辑时都要留意：
  - **搜索起点必须跳过待定汉字段自己的字符数，不能从当前位置裸搜**——如果
    这段汉字的读音恰好和紧跟着的送假名首字符相同（比如"聞き"，聞→き，
    紧跟的送假名也是き，读音整体"ききまちが"），从当前位置裸搜索"き"会
    在原地就命中，误判成"聞"读音是空、后面吞了一个多余的"き"。搜索起点
    至少要往后跳过这段汉字的字符数（每个汉字至少占1个假名音，没有"零音
    读音"的汉字）。**这条下限本身也有漏洞**：默认假设"每个汉字字符至少
    1拍"，但不少常见汉字单字训读本身就有2拍以上（比如"低"训读ひく是
    2拍），如果这个字读音的**最后一拍**恰好又跟紧跟着的送假名首字符相同
    （"低く"——低→ひく最后一拍是く，紧跟送假名也是く），"至少1拍"这个
    下限不够用，会在还没跳过这个字真实读音之前就撞见这个假字符，注音被
    错误截断（真实案例：textbook-sjp-zg-l12"低く"两处都被注成"ひ"，正确
    应为"ひく"）。这类"2拍字读音尾拍撞上送假名首字符"的情况没法从字符串
    本身推断出正确拍数，只能靠具体知识判断——`build_page.py`/`page-
    renderer.js` 里都加了一张 `_KANJI_MIN_MORA`/`KANJI_MIN_MORA` 表登记
    已知会撞车的字（目前只有"低"），新遇到类似的字往这张表里加，不需要
    也不应该给每个2拍字都预先收录（比如"高"→たか同样2拍，但目前没在
    任何真实句子里撞车，不用未卜先知）。
  - **"々"（叠字符号，少々/次々/人々）不在 CJK 表意文字的 Unicode 主区块
    里，但读音上等同于重复前一个汉字，必须显式并入"算作汉字"的判断**，
    否则会被当成普通送假名字符处理，找不到对应字符直接放弃注音，导致
    "少"丢读音、"々"本身也没有注音。
  - **片假名跟汉字混在一起时（"口コミ"的"コミ"、"キリスト教"的
    "キリスト"），`hira` 读音字符串里存的是平假名，片假名字符不会字面
    出现在里面，直接拿片假名字符去搜是搜不到的**——搜索前用固定 Unicode
    偏移量（片假名/平假名平行区块，偏移0x60）把搜索用的字符转成对应平假名
    再搜，塞进最终 segment 里的还是原始片假名文本，不影响显示。
  - **语法笔记里表示"接词干"的占位符"〜"（〜性/〜力/同〜/高〜这类条目）
    完全不发音，字面也不会出现在 `hira` 里**，同样不能当普通送假名处理
    （会被判定为"搜不到，放弃注音"）。这类占位符要用**两遍算法**处理：
    第一遍过滤掉占位组，用剩下的正常分组算出每段汉字的读音；第二遍按
    **原始顺序**把占位段和读音结果重新交错拼回去——不能在第一遍顺手拼，
    占位符可能出现在待定汉字读音**结算之前**（比如"同〜"，"同"的读音
    要等到整个词处理完才结算，顺手拼的话输出顺序会变成"〜"排在"同"前面，
    跟原文顺序颠倒）。
  - **纯罗马字/全角数字类文本（"DVD"、"第２"）没有通用的字符级读音映射
    可用**——罗马字整体退化成一段处理（跟熟字训一样，没有送假名可当定位
    锚点）；数字（"第２"→だいに，第=だい、２=に）读音强依赖语境，没法
    像片假名那样靠固定字符映射通用化处理，遇到了直接手工拆分对应的 token，
    不用为了单个特例硬造一套数字读音规则。
  - **编辑模式（`edit-mode.js`）允许用户直接在浏览器里给一个词填一个合并
    的 kana 覆盖（比如"聞き間違える"整个填 `kana:"ききまちがえる"`），
    这条路径完全绕开 Python，如果 `docs/js/page-renderer.js` 的渲染逻辑
    自己不会拆分，编辑模式存的合并 token 会照原样渲染成一个 `<ruby>` 盖住
    整段文字——真实案例：用户在编辑模式里验证时就复现了这个问题。`_is_
    kanji()`/`_kata_to_hira_char()`/`_split_kana_segments()` 这几个函数
    因此在 `build_page.py`（Python）和 `page-renderer.js`（JS）两处各有
    一份等价实现，**任何一处改了分段算法，另一处必须手动跟着改**，改完
    建议用 `node -e "..."` 直接跑一遍 JS 版本的输出、对照 Python 版本
    确认完全一致（这个项目里没有自动化的双语言一致性测试，只能人工比对）。
- **跟读高亮的时间粒度——`tokenize_ja()` 早期设计是"一个 pykakasi 分词结果
  = 一个跟读高亮单元"，纯假名的长串（pykakasi 经常把好几个助词/助动词粘成
  一个不可再分的 token，比如"ということになりました"）只配一个时间戳，
  导致播放时这一整串字（真实案例反馈：近十个假名）会一起高亮，观感上完全
  不跟着实际发音节奏走**。根因不是"没有更细的数据"——`refine_boundaries.py`
  的 `align_group()` 算 `char_times` 时本来就是"每个字符 = 它所在识别词的
  起始时间"，Whisper 给日语打的词级时间戳本来就接近逐字/逐音节粒度，只是
  `tokenize_ja()` 只挑了每个 token 第一个字符的时间戳、把后面字符的时间戳
  全丢了。修复思路：
  - 汉字读音段（带 `<ruby>` 注音的那部分）**不再往下拆**，当一个高亮单元
    整体点亮——一个汉字/复合词的读音是连着念出来的，拆到单字反而不自然。
  - 纯假名段（送假名、或者整段没有汉字的 token）用 `_split_plain_by_char_
    times()` 按 `char_times` 里"连续相同时间戳"重新分组，时间戳变化的
    地方断开成新的高亮单元，时间戳相同的地方合并（不会拆得比真实数据的
    粒度更细）。
  - **`tokenize_ja()` 每次只处理"一个 pykakasi 分词结果"内部的字符，天然
    不会跨分词边界合并**——但 pykakasi 偶尔会把同一个 Whisper 识别词从
    中间断开成两个分词（真实案例：「分からない」被切成"分か"/"らないこと
    があるものですね"两段，"から"两个字恰好一个在前一段末尾、一个在后一段
    开头，但 `char_times` 显示这两个字享有完全相同的时间戳，说明 Whisper
    识别成的就是同一个词）。这种情况必须在 `tokenize_ja()` 最后加一道
    **收尾合并**：把相邻的两个"纯文本段（没有 `<ruby>` 注音）"在共享同一个
    真实时间戳时合并回一段，只合并没有汉字读音的部分（有注音的段落不参与，
    避免破坏已经处理好的读音标注范围），且只在两边的 `t` 都存在且相等时
    才合并——没有时间戳的段落之间绝对不能瞎合并，那样会把本来不相关的两个
    分词的文字粘一起，比"没拆开"更糟。
  - **Whisper 自己给日语打的词级时间戳，边界不总是贴合语法词**（真实案例：
    "お世話になりました"被切成"にな"/"りました"、"のほうは"被切成"のほ"/
    "うは"，都是切在了词的中间）——这不是算法拆错了，是 Whisper 对这两段
    文字打的时间戳本来就不一样，如实按时间戳分段的结果。这跟整个项目"信任
    Whisper 时间戳"这条一贯原则是一致的（切句子边界、对齐时间戳全靠这个），
    不需要因为个别语法词切得别扭就去猜测/强行订正——真出现大量语法上明显
    别扭的切分，值得反馈给用户判断要不要针对具体语法搭配再加特例，不要
    自己脑补一套"更懂语法"的合并规则。
  - **同一个字符前后出现多个不同时间戳时，先用能量剖面（RMS）核实一下这段
    音频里是否真的有对应的停顿，不要假设"时间戳不同=一定有真实的听感差异"
    也不要假设"没有停顿=时间戳一定是错的"**——真实案例：「いよいよ」被拆
    成 い/よ/い/よ 四个独立高亮点，去听了对应片段的 RMS 能量曲线，发现是
    一段连续没有停顿的响度，说明这4个时间戳反映的是 Whisper 检测到的音素/
    音节级细节，不是真的有4次停顿，但也不是算法瞎拆——只是最终呈现效果
    是"高亮切换比听感上的自然停顿更频繁"，这是信任 Whisper 细粒度时间戳
    这个设计选择本身带来的、可以接受的副作用，不是 bug。
  - **这次改动依赖 `enriched_combined.json`（或对应的 `enriched_*.json`）
    里的 `char_times` 原始数据，只有这份数据还在的课程才能重新生效**——
    `data.js` 里存的是已经"压缩成一个 token 一个时间戳"之后的最终结果，
    不保留原始逐字符时间戳，没法从 `data.js` 反推回去重新细分。真实案例：
    这次3课里只有最新的一课（`tools/listening/work/` 下 `enriched_*.json`
    还没清理）能重新生成，另外两课这份原始数据已经按"生成完页面之后清理
    工作目录"的约定删掉了，没法在不重新跑一遍 Whisper 对齐的前提下补回
    这份精度。**这进一步说明"生成页面之后就清理 `enriched.json`"这个约定
    要谨慎**——短期内看起来只是省磁盘空间，但等于放弃了"以后还能用这份
    数据做更精细的二次加工"的可能性，如果确定某一课近期还可能有类似的
    二次优化需求，考虑推迟清理或者单独备份这份数据。
  - **重新生成 `data.js` 时不要直接跑完整的 `build_page.py`（会连音频目录
    一起用 `enriched_combined.json` 里的原始边界重新切一遍，静默抹掉后续
    对音频文件做过的静音裁剪等独立于 `enriched.json` 的处理）**——只需要
    重新跑 `tokenize_ja(text, char_times)` 拿到新的 `tokens`，直接替换
    `data.js` 里对应句子的 `tokens` 字段，`audio` 字段和其它内容原样不动，
    不调用 `cut_segments()`，音频目录完全不碰。
