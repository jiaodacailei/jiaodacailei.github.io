# N2语法参考页生成/增量更新

跟 `jp-textbook-lesson`（教材课文精听页）最大的不同：**没有配套录音**——语法书只有
印刷文字，没有真人朗读，所有例句音频靠 edge-tts 合成；页面**只有一个知识点tab
（"语法点"）+ 一个练习tab（"练习"）**，不是会话/课文/生词那种多tab结构；而且是
**同一个学科只有一个页面，随着拍新单元不断变长**，不是"一次课一个新页面"。

跟 `jp-n2-vocab-page`（姊妹skill）共用同一个构建脚本
`tools/listening/build_n2_reference_page.py`——两者内容形状足够接近（都是"标题+
讲解+若干例句"+"四选一练习"），脚本本身不区分语法/词汇，靠调用时的
`--tab-label`/`--title`参数区分。

## 内容模块——本skill真正的核心产出

真相源不是页面本身，是一个 Python 内容模块（比如
`tools/listening/n2_grammar_content.py`），定义 `UNITS`/`MCQ_UNITS` 两个模块级
变量——**这个文件必须提交到仓库、长期维护**，以后追加新单元就是往这个文件里
`append`，永远不删旧内容、不在数组中间插入（id按整个文件里的出现顺序分配，
中途插入会导致后面所有id集体错位、旧音频文件全部对不上）。

具体字段形状、TTS+Whisper对齐怎么跑、`audio/seg-{id:03d}.mp3`已存在就跳过TTS
只重新对齐这些机制，直接看 `tools/listening/build_n2_reference_page.py` 脚本
开头的docstring——写得很细，不在这里重复一遍。跟内容转录直接相关、docstring
里没有的经验记在下面。

## 转录例句：先按 jp-textbook-lesson 已验证过的技巧来

0. **严禁改写/拼接/编造例句——每一条例句必须是书上原句的逐字转录，一个字
   都不能改**。真实案例（语法01第1单元，10个语法点里有6个中招）：转录时
   把书上3条例句压缩成1条，中间过程"顺手"换了词、改了语态、删了词、甚至
   把两条不同例句的前后半句拼接成一句全新的话——比如书上是"社内で検討した
   上で、お返事します"（公司内部讨论），被改写成"我々再検討した上で"（我们
   再研讨）；书上是"未成年の犯罪率は高くなる一方だ"（犯罪率），被改成
   "未成年犯罪は高くなる一方だ"（犯罪率→犯罪）；书上是被动态"気象庁から
   大雨警報が発表されているうちは"，被改成主动态"気象庁が…を発表している
   うちは"。这些改写不是转录错字（错字是"看错了"），是**凭语感/记忆重新
   造句**（"这个意思差不多就行"）——每一条都要能在书上对应页面里逐字找到，
   一个标点都不能凭印象补全或"优化表达"，找不到原句宁可跳过（见第2条）
   也不能自己写一句替代。这条是本skill迄今踩过最严重的坑，比错字/漏收录
   后果重得多——错字容易在核对时发现，但一句"读起来很通顺、意思也没错"
   的编造例句几乎不会被自己发现，全靠用户逐句人工核对才揪出来。
1. **源图片旋转+放大读，不要直接读缩略图**——用 PIL
   `ImageOps.exif_transpose(img).rotate(-90, expand=True)`旋正，存到session的
   scratchpad目录再用Read工具看，比直接读原始缩略图清晰得多。跳过这一步真的
   会读错字（本skill第一次转录时就把"町で"错读成了旁边中文译文列尾巴的
   "会"字，是自己二次核对时才发现的，不是用户指出的）。
2. **书上有几条例句就收录几条，不要因为"凑不齐/懒得打"就自己缩减数量**：
   每个语法点前面都有"△"三角符号标出每一条例句的起点，转录前先数一遍这个
   语法点总共有几个△，转录完再数一遍自己写了几条，两个数字对不上就是漏了。
   如果排版密度/分辨率导致某条例文个别字辨认有歧义，**反复裁剪/放大重读**
   （见第3条），实在读不出来才允许跳过那一条、并在旁边注释写清楚跳过的是
   第几条、原因是什么——跳过是"读不出来"的例外情况，不是默认做法，更不能
   用编造一条读起来通顺的句子来"补齐数量"（那正是第0条禁止的行为）。
3. 拿不准的字**反复裁剪/放大重读**，不要靠上下文语义"猜"——先例：本skill
   第一版转录时曾把某段例文里一个字猜错，靠事后重新核对图片发现并改正。
4. **转录完一个单元，必须做一遍全量核对，不能凭"当时转录时很仔细"就当作
   完成**：把这个单元里每一个语法点的书上原图（接续/说明/例文/注意四部分）
   重新读一遍，逐字比对 content.py 里写的内容——尤其是例句，检查①条数是否
   跟书上的△数量一致②每一条是否逐字匹配（不是"意思对/读起来通顺"就算过）
   ③接续/说明/注意的文字有没有被压缩、合并、漏掉某个接续变体。**"我刚才
   转录的时候看得很仔细"不能替代这一步**——本skill第一次做语法01第1单元时
   转录当下自认为仔细，实际上10个语法点里6个都有改写/编造/漏收录，是用户
   自己逐句核对书本发现的，不是转录过程里自己发现的。

## 练习题：范围可以只做一部分，但要写清楚跳过了什么

语法书的练习题往往有好几种形状：单句四选一（跟`MCQ_UNITS`的形状完全匹配，
直接转录）、词库选词填空（给一组A~J选项，几道题共用一个词库，不是"每题自己
4个选项"）、语序排列（★标记要填的位置）、长文完形（一段共享的短文，好几道
题共享同一段上下文）。后三种形状跟现有的"单句四选一"引擎（`mcq-quiz.js`）
不匹配，**不要强行拆成假的四选一**（比如临时给词库题瞎凑4个选项）——这类
题型需要先扩展 `mcq-quiz.js` 支持新的题目形状，属于单独的工作量，先跳过，
在内容模块的模块级 docstring 里写清楚"跳过了什么、为什么、跳过的是练习题
形状问题不是转录能力问题"，方便以后接着做。

真实案例：语法01第1单元只转录了パートI問題1（10题，单句四选一）,
パートI問題2/3（词库选词/长文完形）和パートⅡ実戦練習（12题单句四选一+
语序排列+长文四选一）留到以后——不是转录不出来，是问題2/3和パートⅡ的部分
题型跟引擎形状不合，パートⅡ問題1其实形状合适，纯粹是当次转录时间预算
不够，两种"跳过"原因不一样，都要在docstring里分别写清楚，不能笼统写"以后再说"。

## 无选项自由填空题（kind:"complete"）——精确匹配判分，不是自评

书上有一类练习题没给选项，只给"参考例"（比如"21　無駄遣いをしている"），
本质是主观续写题——`MCQ_UNITS`里用`"kind": "complete"`标记，字段是
`{"stem": "…___。", "kind": "complete", "reference": "参考答案原文",
"referenceZh": "这句整体的中文提示", "explanation": "中文解析"}`。判分是
把用户输入跟`reference`做归一化（全半角+标点统一）后的**精确字符串匹配**，
不是自由创作也不是自评——`reference`要挑书上给的那个参考答案，不能自己
换一种等价说法（哪怕意思一样，精确匹配也会判错，这是当前设计的已知限制，
不是bug）。`referenceZh`是新加的字段，每道题都要写，显示在填空后面的
括号提示里，帮用户知道这句大概该写什么方向，不给的话前端会没有提示文字。

## 参考答案在书的附录页，不在每个单元自己的练习页后面

语法书的正确答案通常集中印在书末几页（比如"226-227页"），不是紧跟在每个
单元练习题后面——转录练习题时**一定要主动去找这几页附录**，不要只看到
"没有答案"就跳过整个练习题部分（本skill第一次做词汇页时就发生过这个情况，
用户主动指出了具体的答案页图片文件名）。

## 密码/枢纽页——复用全站约定，不单独问

- **密码**：复用全站统一密码哈希（跟 `docs/private/index.html` 枢纽页、
  jp-textbook-lesson 系列共用一份），从任意现有私有页面的
  `<div id="gate" data-hash="...">` 摘，`build_n2_reference_page.py` 用
  `--password-hash` 传，不用问用户要明文。
- **枢纽页**：登记进 `docs/private/index.html`（不是独立枢纽页），参照
  `docs/private/n2-exam/`那张卡片的写法，`hub-card-desc`里注明"持续更新"+
  当前收录到第几单元，因为这个页面以后会一直变。

## 标题本身也能默写/填空——语法点名称里的括号必须用半角

跟姊妹skill `jp-n2-vocab-page` 共用的同一套机制：`question-block` 标题
（"1. ～あげく(に)"这种）在默写/填空模式下会被隐藏、换成默写输入框（侧栏
目录也会换成中文）。`listening-page.js` 抽取"默写答案"时只去掉结尾的
**全角**括号"（……）"（词汇条目的读音提示专用），半角括号"(...)"原样保留
当成答案的一部分——语法点名称里的"(に)"「(は)」这类是语法结构本身，不是
读音提示，必须继续用半角括号写（已有的10个语法点都是这样转录的），写成
全角会被误判成"读音提示"整段被从默写答案里去掉，导致语法点名称丢了一截。

标题默写时旁边显示的提示文字，是 `overview` 过滤掉"接续："/"接続："开头
那一行之后剩下的部分（那一行经常把语法点原文直接写出来，比如"接续：
动た形/名一の＋あげく（に）"——照原样当提示会直接泄题）。这意味着写
`overview` 时"接续："这一行只应该出现语法接续说明，不要把"说明："/"注意："
的内容也混进"接续："那一行里（混进去的部分会被一起过滤掉，提示信息会
丢失）——已有10个语法点都是"接续/说明/注意"三行分开写的，继续保持这个
习惯就不会有问题。

## 例句也要给填空(blanks)，不是只有标题能默写/填空

`examples` 元组除了`(日语, 中文)`，还可以写第三个元素——一个字符串
列表，标出这句里要在"填空"模式下挖空的片段（每个必须是日语原文的
字面子串，`build_point_sentences()`按`sentence.indexOf()`定位，位置
找不到就直接跳过那个挖空，不报错也不提示，所以**填完之后要跑一遍脚本
校验每个片段确实是原句子串**，不能凭感觉写完就当完事）：

```python
"examples": [
    ("学生である以上、学業を第一に考えるべきだ。",
     "既然是学生，就应该把学业放在第一位。",
     ["である以上", "考えるべきだ"]),
],
```

第三个元素是可选的——不给就是`[]`（这句不能填空练习，只能默写/跟读），
但**不要图省事全部留空**：语法01第1单元10个语法点14条例句第一次转录
时就是这样，全部examples都只写了`(日语, 中文)`二元组，`build_point_
sentences()`当时也确实是硬编码`"blanks": []`（这条挖空的数据通路从
一开始就没接上，不是转录时漏填），后果是页面填空模式对这整个单元完全
不可用，而且不报错、构建过程看起来一切正常，是用户自己手动改了生成出来
的`data.js`才发现"一个都没有"。**每加一批新例句，都要顺手想一下每句
挑哪几个片段当填空目标**（一般是语法点本身那一小节+后项表达决心/结果
的谓语部分，参照上面`である以上`的例子），别等页面填空模式一片空白时
才想起来。

`blank`片段划分没有唯一标准答案，大致follow现有14条例句的分法：语法
点自身的接续片段（"である以上"）算一段，句子后半表意义的部分（谓语/
结果小句，"考えるべきだ"）再算一段，一句挖2~3段比较常见，挖太碎
（单字/助词）意义不大。

## 一个语法点可能有多个接续——每个接续各自的说明/例文/注意要分组，不能混着平铺

书上每个语法点固定是"接续/说明/例文/注意"四部分，但**接续不一定只有一种**：
书上经常用"接続1/接続2"或"①②③"这种编号，给同一个语法点列出几种不同的
接续形式/用法（比如"～上で(は)"接続1是"在……方面……上"，接続2是"在……
之后"；"～限り"甚至有4组），每一组接续后面紧跟着**只属于这一组**的说明和
△例句，排完这一组的例句才轮到下一组接续。**这个结构必须原样保留，不能把
所有接续的例句混在一起平铺展示**——例句跟哪个接续搭配，是这个语法点最
关键的学习信息之一，混在一起会让人分不清哪句对应哪种用法。

数据形状上，`points` 列表里的一个语法点，**有多个接续时**改用 `groups`
字段代替单独的 `overview`/`examples`：

```python
{
    "title": "6. ～上で(は)",
    "groups": [
        {
            "overview": "接续1：动辞书形/名一の＋上で（は）\n"
                        "说明1：“在……方面……上”。\n"
                        "注意1：前面接名词时，常接“暦/法律/地図/データ”等。",
            "examples": [
                ("あの二人は戸籍の上では夫婦だが、一緒に暮らしていない。", "……", []),
                ("暦の上では立秋を過ぎたが、まだまだ暑い日が続いている。", "……", []),
                ("外国語を勉強する上で単語を覚えることはとても重要だ。", "……", []),
            ],
        },
        {
            "overview": "接续2：动た形/名一の＋上で\n"
                        "说明2：“在……之后”。\n"
                        "注意2：有时可以用「名＋の＋上」，后面不用「で」，多用于通知等书面语。",
            "examples": [
                ("添付ファイルを確認した上で、メールの送信を行う。", "……", []),
                ("実物を見た上で買うかどうかを決める。", "……", []),
            ],
        },
    ],
    # 有 groups 时不再写顶层的 overview/examples
},
```

只有一种接续的语法点（绝大多数）继续用原来的顶层 `overview`/`examples`
写法，不用改——`build_point_sentences()`/`page-renderer.js` 都是先检查
`point.get("groups")` 有没有值，没有就走老的平铺逻辑，两种写法可以在同一个
`UNITS` 列表里混用，互不影响。每一组 `overview` 自己独立写完整的
"接续/说明/注意"三行（不是只写接续本身），因为渲染时是"这一组的文字块
紧跟着这一组的例句卡片"，不会再拼接别的组的文字。

**判断要不要拆 `groups` 的标准**：书上是不是在同一个语法点里，针对不同的
接续形式分别给了各自的△例句——如果只是接续形式本身有两种写法但书上examples
不区分对应哪种接续（比如"3. ～以上(は)"，书上"動/ナ形/イ形の名詞修飾形＋
以上（は）"和"ナ形語幹/名＋である＋以上（は）"这两种接续共用同一批例句，
没有分别配例句），就不需要拆 `groups`，`overview` 里把两种接续形式都写清楚
（分行写，不要合并/简化成一行，也不要漏掉其中一种）即可，继续用平铺的
`examples`。

## 单元选择下拉框——加第2个单元时自动出现，不用额外做任何事

内容模块里每个单元的 `label`（"第1单元"/"第2单元"……）现在会被用作页面
顶部一个"单元选择"下拉框的选项——只要 `UNITS`/`MCQ_UNITS` 里出现了
2个及以上不同的 `label`，重新跑一遍构建脚本，下拉框会自动出现在顶部
tab栏（"N2语法 | [单元选择▾] | 语法点 | 練習"这样），选哪个单元，"语法点"
tab的正文和"練習"tab的题目会一起跟着换（两边共用同一份选中状态，不是
各自独立筛选）。只有1个单元时不会显示这个下拉框（没有可选的意义）——
现在两个页面都还只有1个单元，所以这个下拉框目前还看不到，这是设计好的
默认状态，不是漏做了什么。

这意味着**以后加语法02，只需要在 `n2_grammar_content.py` 的 `UNITS`/
`MCQ_UNITS` 末尾追加一个 `label: "第2单元"` 的新单元、重新跑一遍构建
命令**，不需要碰任何前端代码、不需要单独设计导航——下拉框、内容筛选、
练习筛选全部自动生效。

## 侧栏导航按10个一组分页——词条/语法点太多时自动生效

`page-renderer.js`里的`chunkGroupSizes()`/`groupQuestionsByUnit()`：一个
mondai下的词条/语法点超过10个时，侧栏导航自动从"每条一个链接"变成
"每10条一个链接"（最后一组不足5个并进上一组，算法直接照搬
`build_exam_vocab.py`的`chunk_group_sizes()`，真实反馈"如果最后一组少于
5个，就划到上一组吧"这条规则第二次复用）。语法页目前只有10个语法点，
不会触发（10不大于分组阈值10），继续保持逐条显示——这是设计好的，不是
漏做。这个功能主要是给条目多得多的N2词汇页用的，细节见
`jp-n2-vocab-page/SKILL.md`。

## TTS读错多音字——发现一个订正一个，没法提前穷举

edge-tts合成例句音频时，多音字（比如"町"可以读"まち"也可以读"ちょう"）
偶尔会选错读音——真实反馈"町的音频中发音是chou，应该是machi哟"。这类
问题没法在转录阶段提前发现（不听音频看不出来），只能等用户/自己实际
听到读错了再订正。修法在`tools/listening/build_n2_reference_page.py`里
的`TTS_READING_OVERRIDES`字典：key是"带一点上下文的原文片段"（比如
"町で"而不是单独一个"町"字——"町"出现在其它词里，比如作地名后缀的
"○○町"，读"ちょう"才是对的，不能不分场合把所有"町"都替换成假名），
value是这个片段应该读的假名，只影响"喂给TTS引擎的文本"，不改变原文的
显示/存储（在页面上看到的还是"町"+假名注音"まち"，跟改之前一样）。

订正之后要**手动删掉受影响的那一句音频文件**（`seg-{id:03d}.mp3`，
不是整个目录清空重来——这条订正不改变任何句子的文字内容/数量/顺序，
不会引发"给已有词条中途插入例句"那种seg_id错位的问题，只需要精确删掉
这一句自己的文件，让它重新走一遍TTS合成），再重新跑一遍构建命令。
whisper对齐本来就是按读音模糊匹配、不是逐字符比对目标文本，所以就算
音频里说的是假名、目标文本写的是汉字，对齐一样能对上（而且理论上应该
对得更准，因为音频这下真的读对了）——不用担心订正之后对齐反而失败。

## 已跑过的真实案例／踩过的坑

- **首次搭建时**（语法01第1单元，10个语法点+10道练习题）：`build_page.py`
  共用的 `_group_by_mondai_question()` 分组函数原来是"扫一遍sentences确定
  分组顺序和是否存在"，语法页因为每个语法点都至少有1条例句，没有触发这个
  函数的bug；这个bug是在姊妹skill（jp-n2-vocab-page）做词汇页时才被发现的
  （词汇条目允许没有例句），修复后语法页重新构建过一次，行为完全没变
  （因为语法页从没触发过这个分支）——这里提一下是因为**以后如果语法书里
  出现"某个语法点书上没给例句、只有讲解"的情况，是安全的，不会丢内容**。
- **后台跑`build_n2_reference_page.py`时绝对不要用 `command &` 这种shell级
  背景语法**，要用 Bash 工具自带的 `run_in_background: true`。用
  `python ... & echo 已启动` 这种写法时，外层命令（echo）几乎立刻退出，
  Bash工具会把这个当成"命令完成"发通知，但真正的python进程可能被父进程
  退出连带杀掉（曾经真实发生：一次TTS+对齐跑了20多分钟，中途被这种误用
  杀死，只处理了2/206句就没了）；即使用对了 `run_in_background: true`，
  如果**在前一次调用还没收到完成通知之前又手动发起了第二次同样的调用**，
  两个进程会抢同一个固定路径的临时文件（`whisper_align()`共用的
  `n2_reference_tmp.wav`），导致其中一个进程在读到另一个进程正在写的
  半成品wav文件时报`Invalid data found when processing input`直接崩溃——
  每次重新构建前先用 `ps aux | grep build_n2_reference` 确认没有残留进程，
  跑之前的调用一定要等到收到完成通知再决定下一步，不要因为看着"卡住很久"
  就手痒重新发起一次。
- **给已有语法点/词条中途追加例句会打乱后面所有例句的seg_id、搅乱音频
  缓存**（这个坑是在姊妹skill jp-n2-vocab-page做词汇页时踩到的，语法页
  目前还没实际发生过，但用的是同一套`build_point_sentences()`，同样
  适用）：例句音频`seg-{id:03d}.mp3`的id是按"所有单元、所有语法点、
  各自examples列表"整体顺序从1数到底的，不是每个语法点自己独立编号——
  在数组中间的某个语法点插入一条新例句，会让它之后的所有例句id集体
  后移一位，而`synth_and_align()`只看"文件名对应的mp3存不存在"来判断
  要不要重新合成，旧文件还在、新id又刚好对上这个文件名，就会用错位前的
  旧音频去对错位后的新文本，疯狂fallback（真实症状详见
  `jp-n2-vocab-page/SKILL.md`里的同名条目："aligned 30, fallback 197"
  这种明显不正常的比例，而且构建过程完全不报错）。**以后语法点例句有
  改动/追加时，构建完先看"TTS+对齐"这行的aligned/fallback比例是否明显
  异常（正常应该95%+），不能只看有没有报错退出**；如果确实要在已有
  语法点中间插入新例句而不是只在数组末尾追加新单元，构建前先把
  `docs/private/n2-grammar/audio/`下所有`seg-*.mp3`（不是`word-*.mp3`）
  删掉，让音频从零重新合成一遍，不要指望"只重新合成看起来对不上的那几条"
  ——错位之后已经没法从文件名反推哪些真的受影响。
- **`examples`一开始只有`(日语, 中文)`二元组，没有填空数据的通路**：
  真实反馈"你是不是遗漏了填空的处理？一个都没有哟"——语法01第1单元
  首次构建时`build_n2_reference_page.py`的`build_point_sentences()`
  硬编码`"blanks": []`，`n2_grammar_content.py`的`examples`也只有
  二元组，整条填空数据链路从一开始就不存在，不是转录时漏填。已经改成
  上面"例句也要给填空(blanks)"那节说的三元组格式，`build_point_
  sentences()`和`build_vocab_quiz_items()`都改成兼容2/3元组混用。
  用户当时手动把14句的blanks直接写进了生成出来的`data.js`应急，
  事后按"真相源是内容模块不是生成产物"的原则誊回了`n2_grammar_
  content.py`再重新构建，没有直接沿用手改的`data.js`。
- **例句被静默改写/拼接/编造，转录时自己完全没发现**：语法01第1单元
  10个语法点，用户逐句人工核对书本后发现6个点有问题——2个点的现有例句
  被改写过（换词/改语态/删词，比如"社内で検討した上で"被写成"我々再検討
  した上で"），1个点的例句是把2条不同例句拼接改写成的全新句子（书上根本
  没有这句话），另有多个点单纯漏收录了1~3条例句（书上有△但没转录）。
  这次踩坑之后加了上面"转录例句"第0/2/4条的强制规则（禁止改写、按△计数
  核对、转录完必须做全量核对），**这三条不是可选的最佳实践，是以后每次
  转录都要执行的硬性步骤**，因为这次的教训是：转录时主观上"看得很仔细"
  完全不能保证结果没问题，自查环节被跳过是真正的根因，不是转录能力不够。
- **多接续的语法点，例句要按接续分组，不能平铺**：书上"～上で(は)"
  "～うちに"这类语法点，接続1/接続2各自带自己的△例句，但第一版转录时
  `examples`是一个不分组的平铺列表，混在一起完全看不出哪句例句对应
  哪个接续（用户反馈"接续有多个时，例句应该分别展示，不要统一混在
  一起"）。修复：给`points`加了可选的`groups`字段（见上面"一个语法点
  可能有多个接续"那节），只有多接续的点需要用，其余点不受影响。
