# 第17课制作日志

来源：《标准日本语》中级第17课（会话「日本取材の成果」/课文「北京の顔」/生词），
会话/课文/生词各一段独立录音，来自截图+音频材料。

## 流程

1. 读截图抄原文（会话30句、课文21句7段、生词137个词，id 1-51为会话+课文，52-188为生词）。
2. `transcribe.py` 打时间戳草稿；生词表因语速较快，沿用 l13/l14 建立的"整段
   word-level转写 + 一次性 `align_group()` 对齐全部生词"方案，一次对齐成功。
3. `refine_boundaries.py` 精修边界。课文7段草稿窗口最初按手工估算的粗跨度切分，
   3处（第3/4/6段）因窗口太紧被切错，改成对所有题目分组统一做"两端各加宽
   5~6秒、clamp到音频总长"的防御性扩窗后重新对齐修复——这个通用修法一次性
   抓出了3处，而不是只修最初注意到的那一处。
4. `validate_boundaries.py` 清理，`audit_boundaries_quietpoint.py --fix` 批量修正
   静音点边界（会话/课文/生词三段分别跑，报告见 `quietpoint_dialogue.txt`/
   `quietpoint_text.txt`/`quietpoint_vocab.txt`）。生词表因词间停顿短，136个
   内部边界里28处被标记"可疑"（rise>6dB且at_B>-40dB），发布前抽样用拼接
   相邻内容重新转写核实，确认切分点跟真实内容对得上，不是误切。
5. `merge_sections.py` 合并三段音频+enriched.json。
6. 合并后发现会话 id7「これは，就職活動を…」附近的中文旁白是**有声播出**的
   （不是静音，这一课的新场景），`align_group()` 把 id7 末尾标点错误对齐到
   旁白音频里，导致 `end` 边界把旁白吃进了片段。用50ms精细RMS能量剖面+
   前后片段重新转写定位真实起止，手动订正 `end` 为24.80并clamp `char_times`，
   `recut_clips.py` 单独重切这一个片段，`patch_sentence_tokens.py` 同步
   `data.js`。
7. `audit_furigana.py`（高危字扫描 + `--all` 全量）人工复核。发现并修了
   `tools/listening/build_page.py` 的 `_resolve_hira()` 一个系统性bug：用
   "返回值是否等于pykakasi默认读音"来判断"规则有没有生效"，在规则的正确
   答案恰好和默认值一样时会误判成"没生效"（这一课的触发场景是"29本/459本"
   这类"数字+本"的量词读音——本该按结尾数字2/4/5/7/9固定读ほん，但当默认值
   碰巧也是ほん时判断逻辑会出错）。改成显式 `None` 哨兵值，`audit_furigana.py`
   的 `_scan_live_text()` 同步更新。全站689句回归测试（git stash A/B对比
   `tokenize_ja()` 输出）确认0处影响，不影响已发布内容。
8. `build_vocab_quiz_data.py` 生成 `quiz_data.json`（137条）。
9. `build_page.py --data-driven --quiz-json` 生成页面。
10. 生成后人工复核发现两处遗留问题并直接改 `data.js`：
    - 「銭市胡同」「磨刀胡同」这两个中文地名，生词条目按中文音读（チェンシー/
      フートン、モータオ/フートン）跟会话里的读音手工统一。
    - 补充 `clauseBounds`（供"选段复读"功能用）——18句有多个语法小句的句子，
      从 `enriched_combined.json` 算好的分句时间戳写回 `data.js`。

## 发布后修订

- 用户反馈会话id1「以上が…」开头被切短：RMS核实真实起音在5.82s左右（原
  边界5.96s），起点提前到5.80s，`recut_clips.py`重切+`patch_sentence_tokens.py`
  同步`data.js`。
- 用户反馈会话原id4「さすが王さんですね。」原文有误：对照原始截图确认没有
  "ですね"，音频本来也只说了"さすが王さん"，是抄录screenshot时的笔误，
  改成「さすが王さん。」。
- 用户反馈"会话标题为什么没有音频"，排查发现`dialogue.m4a`开头约0.14~1.55秒
  是**日语读的课程标题**"日本取材の成果"（之前误判成跟中文旁白一样可以
  丢弃，实际上只有紧接着的"（做大概介绍后）"那段才是中文旁白，标题本身是
  日语，按`_resolve_hira`等既有规则不该排除）——回查l11/l12/l13/l15/l16
  这五课，会话第一句本来就是这种"课程标题朗读"（若者の意識/最終日/
  スピーチの依頼/同級生/結婚披露宴），是这个skill的标准模式，只是这一课
  第一步抄原文时漏掉了。补做：往`enriched_combined.json`最前面插入这条
  title句（`speaker`/`speaker_kana`为`null`，`zh`按"原文译文（课程标题）"
  格式，`blanks`为空，不参与默写/填空），原有全部句子`id`统一+1（1-188→
  2-189），`quiz_data.json`的生词`id`同步+1（52-188→53-189），用
  `build_page.py --data-driven --quiz-json`对着`combined.m4a`整体重新生成
  （不是手工改188个文件名，避免算错偏移量），生成后逐一核对id1（新标题）/
  id2（原id1，确认5.80s边界修复还在）/id5（原id4，确认"ですね"修复还在）/
  id189（原id188，最后一个生词）内容衔接正确。

- 用户紧接着反馈"课文第一句音频前面短了，而且也没有标题的音频"——排查发现
  两个问题：
  1. **课文同样漏了标题朗读**："北京の顔"。跟会话的情况一模一样，`text.m4a`
     开头约0.20~1.50秒是日语朗读的课程标题，之前也被当成可跳过的内容漏抄了。
     处理方式同上：插入title句为课文的新id32，原id32起（含全部课文+全部
     生词）统一+1（32-189→33-190），`quiz_data.json`生词`id`再+1（53-189→
     54-190）。
  2. **`build_page.py --data-driven`重新生成、给全部句子id顺移+1这个操作
     本身踩了一个未记录过的坑**：`cut_segments()`判断"要不要重切某个
     `seg-NNN.mp3`"，用的是"这个文件名已经存在 + 实际时长跟这次期望时长
     差距<0.15秒"，差距在容差内就跳过重切、直接沿用磁盘上的旧文件。这个
     判断在"给同一批句子做纯粹的边界/文字微调"时是安全优化，但**在"给全部
     句子id整体顺移"这种场景下是不安全的**——顺移之后，同一个文件名
     （比如`seg-032.mp3`）对应的是**另一句完全不同的内容**，只要这句新
     内容的期望时长恰好跟磁盘上那个旧文件（本来属于顺移前的另一句）的
     实际时长差在0.15秒以内，就会被误判成"没变、不用重切"，导致这个文件名
     下留着的是错误句子的音频——真实案例：会话第一次插入标题句后，课文
     新id32（"北京のほぼ中心部にある景山公園は…"，期望时长5.92秒）复用了
     磁盘上顺移前那个`seg-032.mp3`（旧课文第2句"休日には…"，实际时长
     5.88秒，差0.04秒在容差内），造成"文字是新句子、音频是另一句"的
     内容错位，而且这类错位**不会被`verify_clips.py`的LOW_SIMILARITY
     判断稳定抓到**（因为"休日には"本身是一句完整、能正常转写的日语，
     相似度比对不会報错——需要靠人工听/对照原文才发现）。**教训**：
     任何一次"给已发布课程的句子`id`做整体顺移/重新编号"的操作，重新跑
     `build_page.py`之前必须先清空`docs/private/<slug>/audio/`目录再生成
     （不能依赖`cut_segments()`的智能跳过），生成后除了比对时长（能查漏，
     但查不出"两句时长恰好接近导致的误判"），还要再抽查几个跨顺移点前后
     位置的id做真实转写核对内容对不对，不能只信时长比对通过。这一次连带
     用清空目录重新生成的方式重做了一遍课文标题插入，重新核对了插入点
     前后（新id32标题本身、新id33即原id32"北京のほぼ…"、新id190即原
     id189最后一个生词）以及此前两处已知修复（新id1会话标题、新id2即
     "以上が…"边界修复、新id5即"さすが王さん"文字修复）全部正确，并对
     全部190条重新跑了一遍时长比对（0处偏差）+`verify_clips.py`全量转写
     （EMPTY 3、LOW_SIMILARITY 29、LEAD_SILENCE 6，逐条跟顺移前的报告
     按文字内容比对，除了两条个体差异——原来EMPTY的"せいぜい"这次识别成
     了乱码假名变成LOW_SIMILARITY、新出现"紫"被误识别成"無料販売"——其余
     全部对应，都是同一批短促孤立生词/独立读音估算的已知误报模式，没有
     出现"整句能被完整识别、内容却对不上"这种真正的内容错位信号）。
     这个坑已经补进`jp-textbook-lesson` skill文档，以后再遇到"顺移id"
     场景会提前避开。

- 用户又连续反馈课文id36/id39开头的"胡同"发音丢了——排查发现是同一个
  系统性模式：只要句子以"胡同"（作为句首词，中文地名读フートン）开头，
  这一课原始`refine_boundaries.py`/`align_group()`算出来的句子起点都
  系统性偏晚，把"胡同"这个词自己的发音整个丢进了"上一句结尾"和"这句
  算出来的起点"之间的空隙里，两句都没收进去。逐个订正id36（124.21s→
  123.62s）/id39（146.51s→145.88s）之后，没有等用户继续逐句反馈，主动
  对全课所有句子间隔（`start - 上一句end`）>0.3秒的位置做了一次系统扫描，
  又额外揪出2处同一模式：id45（185.55s→185.05s）/id48（206.89s→
  206.42s），全部用RMS能量剖面核实真实起音位置后`recut_clips.py`+
  `patch_sentence_tokens.py`修正。扫描顺带核实了另外2处大间隔不是这个
  问题：id2/id9是已知被排除的中文旁白（预期内的大间隔），id50的间隔
  一开始转写误判成有个"ある"卡在间隙里，RMS一看纯粹是静音噪声底，
  转写结果是Whisper在长静音区域的幻觉，不是真实内容。**教训**：这一课
  "胡同"这个词反复触发同一类边界bug（4次独立句子命中），说明"某个特定
  生词/专有名词在句首位置系统性触发对齐算法的边界偏差"这种模式，一旦
  抓到第2次就该主动做全课扫描，而不是被动等用户一句一句挑出来。

- 本课目前没有已知未处理的问题。
